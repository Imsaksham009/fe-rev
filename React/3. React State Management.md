## The Big Picture First (read this once, it ties everything together)

Every state question in React comes down to one thing: **who owns this data, and who needs to see it?** The answer moves you up a ladder — and you only climb as far as you have to:

1. **Local state** (`useState` / `useReducer`) — only one component cares. *This is the default.*
2. **Lifted state** — a few nearby components need to share it, so it moves to their common parent.
3. **Context** — many distant components need it, and it changes rarely (theme, logged-in user).
4. **Global store** (Redux / RTK, or MobX) — widely shared, frequently updated, or complex enough to deserve real tooling.

Two things sit *beside* the ladder, not on it: **server state** (data that lives on a backend — handled by RTK Query / React Query) and **URL state** (filters, page number, selected tab).

**The Redux data flow** — memorize this picture, because almost every Redux question is really asking about one arrow in it:

```
 click "Add to cart"
        │
        ▼
  dispatch(action) ──► middleware ──► reducer ──► new state saved in store
                                                          │
  component re-renders ◄── useSelector re-runs ◄── store notifies subscribers
```

**Running example for this whole file:** a shopping cart — `{ items: [{ id, name, price, qty }] }`. You'll see it as local state, lifted state, Context, plain Redux, RTK, and RTK Query.

## Part 1: React State

### 1. Local State

**What it is:** State owned by a single component (and passed to its children through props), created with `useState` or `useReducer`.

**Why it exists:** Most state only matters to one component — whether a dropdown is open, what's typed in a box, which tab is active. Keeping it inside that component means no global coupling, easy reasoning, and automatic cleanup when the component unmounts.

**Mental model:** A sticky note on your own desk. If only you need it, it doesn't belong on the office noticeboard.

```jsx
function CartDrawer() {
  const [isOpen, setIsOpen] = useState(false); // only this component cares

  return (
    <>
      <button onClick={() => setIsOpen(o => !o)}>Cart</button>
      {isOpen && <CartList />}
    </>
  );
}
```

**Interview line:** "Local state is the default — keep state as close as possible to where it's used, and only widen its scope when another component genuinely needs it."

> ⚠️ Gotcha: Local state is destroyed when the component unmounts. If you find yourself needing it to survive navigation or remounting, that's a signal it belongs higher up (or in a store, or the URL).

---

### 2. Derived State

**What it is:** Any value you can *calculate* from existing state or props. The rule: **don't store it as separate state — compute it during render.**

**Why it exists (why the rule matters):** Storing a derived value creates two sources of truth that can drift out of sync, and syncing them with `useEffect` + `setState` adds an extra render on every change. A value computed during render is *always* correct by construction.

**Mental model:** A spreadsheet formula. The "Total" cell is `=SUM(items)` — you'd never type the total by hand and then also try to keep it updated yourself.

```jsx
// ❌ Redundant state + effect to keep it in sync
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);
useEffect(() => {
  setTotal(items.reduce((sum, i) => sum + i.price * i.qty, 0));
}, [items]);

// ✅ Derive it — always correct, no extra render
const [items, setItems] = useState([]);
const total = items.reduce((sum, i) => sum + i.price * i.qty, 0);
```

**Interview line:** "If a value can be computed from state or props, compute it during render instead of storing it — that removes a whole class of out-of-sync bugs. If the calculation is genuinely expensive, wrap it in `useMemo`."

> ⚠️ Gotcha: `useState(props.value)` uses the prop only as the *initial* value — later prop changes are silently ignored. It's derived-state's most common trap. Either read the prop directly, or reset the component by changing its `key`.

---

### 3. Lifting State

**What it is:** Moving state up to the nearest common parent of the components that need it, then passing it down as props (and passing setters/callbacks down for updates).

**Why it exists:** React data flows one way, parent → child, so siblings can't share state directly. A shared parent is the meeting point. (You saw this in the React Fundamentals file — here it's the *second rung* of the ladder.)

**Mental model:** Two roommates share one thermostat in the hallway instead of each owning a separate one.

```jsx
function Shop() {
  const [items, setItems] = useState([]);
  const addItem = (item) => setItems(prev => [...prev, item]);

  return (
    <>
      <ProductList onAdd={addItem} />   {/* writes to the cart */}
      <CartBadge count={items.length} /> {/* reads from the cart */}
    </>
  );
}
```

**Interview line:** "When siblings need the same state, lift it to their closest common parent — and if that starts forcing props through three or more layers, it's time for the next rung: Context or a store."

> ⚠️ Gotcha: Lifting too high "just in case" makes unrelated components re-render whenever that state changes. Lift only as far as the *closest* common parent.

---

### 4. Context (the idea)

**What it is:** React's built-in way to make a value available to *any* component below a certain point in the tree, without passing it as a prop through every level in between.

**Why it exists:** To solve props drilling — when a value like the current user or theme is needed by a deeply nested component, threading it through five components that don't use it is noise and a maintenance burden.

**Mental model:** A radio broadcast. Anyone tuned in (`useContext`) hears it directly — nobody has to relay the message person to person.

```jsx
const UserContext = createContext(null);

<UserContext.Provider value={user}>   {/* broadcast */}
  <App />
</UserContext.Provider>

const user = useContext(UserContext);  // tune in, anywhere below
```

**Interview line:** "Context lets a value skip the prop chain and reach any descendant directly — but it only *delivers* a value; the state itself still comes from `useState` or `useReducer`."

> ⚠️ Gotcha: Context is **not a state manager**. It doesn't hold, update, or optimize state — it's purely a delivery mechanism. This one distinction is the root of the Context-vs-Redux question (#8, #19).

## Part 2: Context Deep Dive

### 5. How Context Works

**What it is:** Three pieces working together:

- `createContext(defaultValue)` — creates the context. The default is used **only** if there's no Provider above the consumer.
- `<Ctx.Provider value={...}>` — supplies a value to everything below it.
- `useContext(Ctx)` — reads the value from the *nearest* Provider above.

When the Provider's `value` changes (compared with `Object.is`), React re-renders **every component that consumes that context**.

**Why it's built this way:** It's a simple broadcast model — a Provider publishes, consumers subscribe, and React skips all the components in between.

**Mental model:** A bulletin board. Whenever the notice changes, everyone subscribed to that board gets pinged — whether or not the part of the notice they care about was the part that changed.

```jsx
const ThemeContext = createContext('light'); // default: used only with no Provider

function App() {
  const [theme, setTheme] = useState('dark');

  // memoize so consumers only re-render when theme actually changes
  const value = useMemo(() => ({ theme, setTheme }), [theme]);

  return (
    <ThemeContext.Provider value={value}>
      <Page />
    </ThemeContext.Provider>
  );
}

function ThemeButton() {
  const { theme, setTheme } = useContext(ThemeContext);
  return <button onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}>{theme}</button>;
}
```

> Note: In React 19 you can render `<ThemeContext value={...}>` directly instead of `<ThemeContext.Provider>` — both work.

**Interview line:** "Context is a Provider/consumer pair: the Provider supplies a value, `useContext` reads the nearest one, and whenever the value changes by reference, every consumer re-renders."

> ⚠️ Gotcha #1 — the inline-object trap: `value={{ theme, setTheme }}` creates a *new object every render* of the Provider's component, so all consumers re-render even when `theme` didn't change. Memoize the value with `useMemo`.
>
> ⚠️ Gotcha #2: `React.memo` on an *intermediate* component doesn't stop a *consumer* from re-rendering on a context change — the consumer is subscribed directly.
>
> ⚠️ Gotcha #3: There's no selector. A component reading `{ user, theme }` from one context re-renders when *either* changes. Fix: split into separate contexts (or separate `state` and `dispatch` contexts), and keep context values low-frequency.

---

### 6. When to Use Context

**What it is:** A rule of thumb for what belongs in Context: values that are **read by many components** and **change rarely**.

**Why it exists:** Because Context re-renders every consumer on any change (#5), it's efficient for slow-moving, app-wide values and a poor fit for fast-moving ones.

**Mental model:** Context is for *weather*, not *traffic* — ambient information that's the same for everyone and changes slowly. Live traffic (fast-changing data) needs a different system.

| Good fit                            | Poor fit                                                     |
| ----------------------------------- | ------------------------------------------------------------ |
| Theme (light/dark)                  | Text typed into an input (changes per keystroke)             |
| Current logged-in user              | Mouse position, scroll position, animation values            |
| Language / locale                   | Large lists with frequent updates                            |
| Feature flags, app config           | Server data (use RTK Query / React Query)                    |
| Injecting a dependency (API client) | Complex state with many update types (use a reducer + store) |

A clean pattern is wrapping `useContext` in a custom hook with a guard, so misuse fails loudly:

```jsx
const AuthContext = createContext(null);

export function useAuth() {
  const ctx = useContext(AuthContext);
  if (ctx === null) throw new Error('useAuth must be used inside <AuthProvider>');
  return ctx;
}
```

**Interview line:** "I use Context for low-frequency, app-wide values like theme, auth user, or locale. For fast-changing or complex state, Context's re-render-everything behavior becomes a cost, and a store with selector-based subscriptions is a better fit."

> ⚠️ Gotcha: One giant `AppContext` holding everything means every consumer re-renders on *any* change to anything. Split contexts by concern.

---

### 7. Context vs Props

**What it is:** Two ways to get data into a component — **props** (explicit, passed parent → child) and **Context** (implicit, read from the nearest Provider above).

**Why the comparison matters:** Context is often reached for too early. Props have real advantages that Context gives up in exchange for convenience.

**Mental model:** Props are a letter addressed to a specific person. Context is a public announcement — everyone in earshot can act on it, but you can't tell just by looking at the listener where it came from.

|                       | Props                                | Context                                           |
| --------------------- | ------------------------------------ | ------------------------------------------------- |
| Data flow             | Explicit, visible at every call site | Implicit, hidden inside the component             |
| Traceability          | Easy — follow the props             | Harder — find the nearest Provider               |
| Reusability / testing | Easy — just pass props              | Component silently depends on a Provider existing |
| Re-render behavior    | Normal parent → child cascade       | Every consumer re-renders on value change         |
| Best for              | Direct parent → child data          | Ambient data many distant components need         |

**The third option — composition.** Often the real goal is just "avoid drilling," and you can do that by passing *elements* instead of data:

```jsx
// Instead of drilling `user` through Layout → Sidebar → Profile:
function App() {
  const user = useUser();
  return <Layout sidebar={<Profile user={user} />} />;  // Profile is built here, at the top
}
function Layout({ sidebar }) {
  return <aside>{sidebar}</aside>;  // Layout never touches `user`
}
```

**Interview line:** "Props for direct, explicit data flow; Context for ambient values many distant components need. And before reaching for either just to dodge drilling, I try component composition — passing elements as `children` or props."

> ⚠️ Gotcha: Reaching for Context to avoid one or two levels of drilling trades a small, visible inconvenience for a hidden dependency. Drilling only becomes a real problem around three-plus levels, or when many unrelated components need the value.

---

### 8. Context vs Redux

**What it is:** Context is a **delivery mechanism** (get a value to distant components). Redux is a **state-management system** (a store, strict update rules, tooling, and a subscription model). They're often compared because both avoid props drilling — but they solve different problems.

**Why the confusion exists:** Context + `useReducer` looks like a tiny Redux:

```jsx
const CartContext = createContext(null);

function CartProvider({ children }) {
  const [state, dispatch] = useReducer(cartReducer, { items: [] });
  const value = useMemo(() => ({ state, dispatch }), [state]);
  return <CartContext.Provider value={value}>{children}</CartContext.Provider>;
}
```

That's a fine pattern for small cases. But there's a key difference in **who re-renders**:

- With Context: *every* component consuming `CartContext` re-renders on *any* cart change.
- With Redux: `useSelector(s => s.cart.items.length)` subscribes to **one slice** — the component re-renders only when *that selected value* changes.

Redux also adds: DevTools with action history and time travel, a middleware system for async/side effects, and a single enforced pattern that scales across large teams.

**Mental model:** Context is the delivery truck. Redux is the entire postal system — sorting, tracking, rules, and the truck.

**Interview line:** "Context passes values down; Redux is a full state-management system. Context plus `useReducer` covers small apps, but Redux's selector-based subscriptions, DevTools, and middleware pay off as state and team size grow."

> ⚠️ Gotcha: "Redux is just Context" is wrong. `react-redux`'s `<Provider>` *does* use Context — but only to pass the **store instance** down. Actual state updates reach components through a subscription mechanism, not through changing context values. That's precisely why Redux doesn't have Context's re-render-everything problem.

## Part 3: Redux & Redux Toolkit

### 9. Store

**What it is:** A single JavaScript object that holds the **entire app state tree**, plus three methods: `getState()`, `dispatch(action)`, and `subscribe(listener)`.

**Why it exists:** One source of truth makes state predictable — you always know where to look, it's easy to inspect, log, persist, or replay, and no two parts of the app can disagree about what the data is.

**Mental model:** A company's central ledger. Everyone reads from the same book, and nobody scribbles in it directly — changes go through a formal request process (#10–#12).

```js
import { configureStore } from '@reduxjs/toolkit';

const store = configureStore({
  reducer: { cart: cartReducer },
});

store.getState();   // { cart: { items: [] } }
store.dispatch({ type: 'cart/itemAdded', payload: { id: 1, name: 'Mouse', price: 499, qty: 1 } });
store.subscribe(() => console.log('state changed'));
```

**Interview line:** "The store is the single object holding the whole app state tree — you read it with `getState`, change it only via `dispatch`, and listen for changes with `subscribe`. React-Redux hooks are built on top of those."

> ⚠️ Gotcha: Never mutate state you get from the store (`store.getState().cart.items.push(...)`). It bypasses reducers, and since the reference doesn't change, nothing re-renders. Also, `createStore` is deprecated — modern code uses `configureStore`.

---

### 10. Actions

**What it is:** Plain objects describing **what happened**, with a required `type` string and an optional `payload`. An **action creator** is just a function that builds one.

**Why it exists:** It turns every state change into an explicit, named event. That gives you a readable history of the app ("itemAdded, itemRemoved, checkoutStarted"), easy debugging, and replayable behavior.

**Mental model:** A form you hand to the clerk describing an *event* — "customer added item 42" — rather than telling the clerk how to edit the ledger.

```js
// action — plain object
{ type: 'cart/itemAdded', payload: { id: 1, name: 'Mouse', price: 499, qty: 1 } }

// action creator — function that builds it
const itemAdded = (item) => ({ type: 'cart/itemAdded', payload: item });
```

**Interview line:** "Actions are plain objects describing what happened — a `type` plus an optional `payload` — and they're the only way to express an intent to change state."

> ⚠️ Gotcha: Name actions as *events* (`itemAdded`), not *setters* (`setItems`) — that's the official Redux style recommendation. Also keep payloads **serializable** (no functions, Promises, or class instances) or DevTools and persistence break.

---

### 11. Reducers

**What it is:** A **pure function** `(state, action) => newState` that decides how state changes in response to an action.

**Why it exists:** Purity is the whole point. A pure reducer gives the same output for the same input, so state changes are predictable, trivially unit-testable, and support time-travel debugging. Returning a *new* object is also how React-Redux detects that something changed.

The three rules: **(1)** never mutate `state`, **(2)** no side effects — no API calls, `Date.now()`, or `Math.random()` inside, **(3)** always return the existing state for unknown actions.

**Mental model:** A vending machine. Same coin, same button — always the same result. It doesn't phone anyone or change the machine's internals mid-transaction; it just produces the outcome.

```js
function cartReducer(state = { items: [] }, action) {
  switch (action.type) {
    case 'cart/itemAdded':
      return { ...state, items: [...state.items, action.payload] };
    case 'cart/itemRemoved':
      return { ...state, items: state.items.filter(i => i.id !== action.payload) };
    default:
      return state; // unknown action — return the same state
  }
}
```

**Interview line:** "A reducer is a pure function from `(state, action)` to new state — no mutation, no side effects — which is what makes Redux predictable, testable, and debuggable."

> ⚠️ Gotcha: Mutating inside a reducer (`state.items.push(x); return state;`) returns the *same reference*, so React-Redux sees "no change" and never re-renders. And spread only copies one level — deeply nested updates need every level copied, which is exactly the pain Immer removes in RTK (#16).

---

### 12. Dispatch

**What it is:** The function that sends an action to the store. It's the **only** way to trigger a state change. In components, `useDispatch()` gives you the store's `dispatch`.

**Why it exists:** A single entry point enforces one-way data flow and gives middleware (#14) a place to intercept. The full trip: `dispatch(action)` → middleware chain → reducers → new state → subscribers notified.

**Mental model:** The mail slot at the clerk's office. Every request — no exceptions — goes through it.

```jsx
function AddToCart({ product }) {
  const dispatch = useDispatch();
  return (
    <button onClick={() => dispatch(itemAdded({ ...product, qty: 1 }))}>
      Add to cart
    </button>
  );
}
```

**Interview line:** "`dispatch` is the only way to change store state — it sends an action through middleware to the reducers, then notifies subscribers so connected components can update."

> ⚠️ Gotcha: A plain `dispatch(action)` is synchronous — by the time it returns, the reducer has run. Anything async (API calls) needs middleware like thunk, because a plain action can't be a Promise or a function.

---

### 13. Selectors

**What it is:** Functions that read or derive data from store state — `state => state.cart.items`. Components use them via `useSelector`.

**Why it exists:** Three reasons:

1. **Encapsulation** — components don't hardcode the state shape; if it changes, you update one selector.
2. **Derived data** — compute things like the cart total in one reusable place (this is derived state from #2, at store level).
3. **Targeted subscriptions** — `useSelector` re-runs on every store update, but re-renders the component only if the selected value changed (compared with `===`).

**Mental model:** A window onto one shelf of the vault. You only look at the shelf you care about, and you only get called over when *that shelf* changes.

```js
// plain selectors
const selectItems = (state) => state.cart.items;
const selectCount = (state) => state.cart.items.length;

// memoized derived selector (createSelector comes from Reselect, re-exported by RTK)
import { createSelector } from '@reduxjs/toolkit';

const selectTotal = createSelector(
  [selectItems],
  (items) => items.reduce((sum, i) => sum + i.price * i.qty, 0) // recomputes only if `items` changed
);

// in a component
const total = useSelector(selectTotal);
```

**Interview line:** "Selectors read and derive data from the store; `useSelector` subscribes a component to just that selected value, so it re-renders only when the result changes — and `createSelector` memoizes expensive derivations."

> ⚠️ Gotcha: `useSelector(s => s.cart.items.filter(i => i.qty > 1))` returns a **new array on every call**, so the component re-renders on *every* store update. Select the raw data and derive it with a memoized selector instead. (Recent `react-redux` versions warn about this in dev.) Selecting the entire `state` has the same problem.

---

### 14. Middleware

**What it is:** Code that sits **between `dispatch` and the reducer**, able to inspect, modify, delay, or replace actions. The shape is `store => next => action => { ... }`.

**Why it exists:** Reducers must stay pure (#11), so side effects — async calls, logging, analytics — need somewhere else to live. Middleware is Redux's extension point for exactly that.

**Mental model:** Airport security checkpoints between check-in (dispatch) and boarding (the reducer). Each checkpoint can inspect you, hold you up, reroute you, or wave you through with `next(action)`.

```js
const logger = (store) => (next) => (action) => {
  console.log('dispatching', action.type);
  const result = next(action);           // pass it on to the next middleware / reducer
  console.log('next state', store.getState());
  return result;
};
```

The most important middleware is **Redux Thunk**: it lets you dispatch a *function* instead of an action, which is how async logic gets a home. RTK includes it by default.

**Interview line:** "Middleware wraps `dispatch` — it's where side effects like async calls and logging live, since reducers have to stay pure. Thunk is the standard one, and it's built into Redux Toolkit."

> ⚠️ Gotcha: If a middleware doesn't call `next(action)`, the action is swallowed and the reducer never sees it. Also, order matters — middleware runs in the order you list it.

---

### 15. Redux Toolkit (RTK)

**What it is:** The official, recommended toolset for writing Redux. It wraps core Redux with `configureStore`, `createSlice`, `createAsyncThunk`, `createEntityAdapter`, **RTK Query**, and bundles **Immer** for safe "mutating" syntax.

**Why it exists:** Hand-written Redux had heavy boilerplate — action type constants, action creators, switch-statement reducers, manual immutable updates, and manual store/DevTools/thunk setup — plus easy-to-make mistakes like accidental mutation. RTK bakes in the best practices so you write less and break less.

**Mental model:** Redux is the engine; RTK is the car built around it. Same engine, but you're not assembling the parts by hand.

```js
const store = configureStore({
  reducer: { cart: cartReducer }, // combineReducers is done for you
});
// Included by default: thunk middleware, Redux DevTools,
// and dev-time checks for accidental mutation and non-serializable values.
```

**Interview line:** "Redux Toolkit is the official way to write Redux — same concepts, but it removes the boilerplate and bakes in Immer, thunk, DevTools, and safety checks."

> ⚠️ Gotcha: RTK is not a *replacement* for Redux — it's Redux underneath. Store, actions, reducers, and dispatch all still exist; RTK just gives you better tools for writing them.

---

### 16. `createSlice`

**What it is:** A helper that bundles everything for one feature — its name, initial state, reducers — and **auto-generates the action creators and action types**. It uses Immer, so you can write code that looks like mutation while RTK produces a correct immutable update.

**Why it exists:** It collapses four separate things (action types, action creators, reducer, initial state) into one declaration — and removes the spread-everything ceremony.

**Mental model:** A meal kit box — recipe (reducers), ingredients (initial state), and labeled packets (actions) all delivered together, ready to cook.

Compare with the plain reducer from #11:

```js
import { createSlice } from '@reduxjs/toolkit';

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] },
  reducers: {
    itemAdded(state, action) {
      state.items.push(action.payload);          // looks like mutation — Immer makes it safe
    },
    itemRemoved(state, action) {
      state.items = state.items.filter(i => i.id !== action.payload);
    },
  },
});

export const { itemAdded, itemRemoved } = cartSlice.actions; // auto-generated action creators
export default cartSlice.reducer;
```

`itemAdded(item)` produces `{ type: 'cart/itemAdded', payload: item }` — the type is `${name}/${reducerKey}`.

**Interview line:** "`createSlice` generates the reducer and action creators from one definition, and Immer lets me write update logic in a mutating style that's converted to safe immutable updates under the hood."

> ⚠️ Gotcha #1: "Mutating" syntax is only safe **inside `createSlice` / `createReducer`**, where the state is an Immer draft. In a plain hand-written reducer it's still a real bug.
>
> ⚠️ Gotcha #2: In one reducer case, either mutate the draft **or** return a new value — never both. Immer throws if you do.

---

### 17. `createAsyncThunk`

**What it is:** An RTK helper that creates a thunk for async work and **automatically dispatches three actions** around a promise: `pending`, `fulfilled`, and `rejected`.

**Why it exists:** The "loading → success / error" pattern is identical for nearly every API call. Writing those three actions and their handlers by hand each time is repetitive; this standardizes it.

**Mental model:** A courier tracking system. You get status events — "picked up" (pending), "delivered" (fulfilled), "delivery failed" (rejected) — and react to each, instead of standing at the door waiting.

```js
export const fetchCart = createAsyncThunk(
  'cart/fetchCart',                          // action type prefix
  async (userId, { rejectWithValue }) => {
    const res = await fetch(`/api/cart/${userId}`);
    if (!res.ok) return rejectWithValue('Failed to load cart');
    return res.json();                       // becomes action.payload on fulfilled
  }
);

// inside createSlice — handle the three lifecycle actions:
extraReducers: (builder) => {
  builder
    .addCase(fetchCart.pending,   (state) => { state.status = 'loading'; })
    .addCase(fetchCart.fulfilled, (state, action) => {
      state.status = 'succeeded';
      state.items = action.payload;
    })
    .addCase(fetchCart.rejected,  (state, action) => {
      state.status = 'failed';
      state.error = action.payload ?? action.error.message;
    });
},

// in a component
dispatch(fetchCart(userId));
```

**Interview line:** "`createAsyncThunk` wraps an async function and dispatches pending, fulfilled, and rejected actions automatically, which I handle in the slice's `extraReducers` — it removes the manual loading/error boilerplate."

> ⚠️ Gotcha: The promise returned by `dispatch(thunk())` **always resolves** — even on failure, it resolves with the *rejected action*. Use `.unwrap()` (`await dispatch(fetchCart(id)).unwrap()`) if you want normal try/catch behavior. And for plain data fetching, RTK Query (#18) is usually the better tool.

### 18. RTK Query Basics

**What it is:** RTK's built-in **data-fetching and caching layer**. You declare your endpoints once with `createApi`, and it generates React hooks that handle loading and error state, caching, request deduplication, refetching, and cache invalidation for you.

**Why it exists:** Fetching server data by hand with thunks means re-implementing loading flags, error handling, caching, and refetch logic for every endpoint — and it treats server data as if it were client state (#22). RTK Query is purpose-built for that job.

**Mental model:** A smart librarian with a desk cache. Ask for the same book twice and they hand you the copy already on the desk; when a new edition arrives (a mutation invalidates the tag), they fetch a fresh one.

```js
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';

export const shopApi = createApi({
  reducerPath: 'shopApi',
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['Cart'],
  endpoints: (builder) => ({
    getCart: builder.query({
      query: (userId) => `cart/${userId}`,
      providesTags: ['Cart'],              // "this data is tagged Cart"
    }),
    addItem: builder.mutation({
      query: (item) => ({ url: 'cart', method: 'POST', body: item }),
      invalidatesTags: ['Cart'],           // "after this, refetch anything tagged Cart"
    }),
  }),
});

export const { useGetCartQuery, useAddItemMutation } = shopApi; // auto-generated hooks

// store setup — BOTH the reducer and the middleware are required
configureStore({
  reducer: { [shopApi.reducerPath]: shopApi.reducer },
  middleware: (getDefault) => getDefault().concat(shopApi.middleware),
});

// component — no manual loading flags, no useEffect
const { data, isLoading, error } = useGetCartQuery(userId);
const [addItem] = useAddItemMutation();
```

**Interview line:** "RTK Query is Redux Toolkit's data-fetching layer — I define endpoints once and get hooks with built-in loading and error states, caching, deduplication, and tag-based invalidation, so I'm not hand-writing thunks and loading flags for server data."

> ⚠️ Gotcha: Forgetting `shopApi.middleware` in the store breaks caching, invalidation, and polling — the reducer alone isn't enough. Also, the cache is keyed by endpoint + arguments, and unused data is dropped after 60 seconds by default (`keepUnusedDataFor`).

## Part 4: Interview Comparisons

### 19. Context vs Redux

*(Mechanics explained in #8 — this is the quick-fire version.)*

|                              | Context                                            | Redux (RTK)                                            |
| ---------------------------- | -------------------------------------------------- | ------------------------------------------------------ |
| What it is                   | A way to*deliver* a value                        | A full state-management system                         |
| Dependency                   | Built into React                                   | Extra library                                          |
| Re-render granularity        | All consumers of that context, on any value change | Selector-based — only when the selected value changes |
| DevTools / time travel       | No                                                 | Yes                                                    |
| Async / side-effect patterns | You build them yourself                            | Thunk, RTK Query, listener middleware                  |
| Boilerplate                  | Low                                                | Low–medium with RTK                                   |
| Best for                     | Theme, auth user, locale — low-frequency          | Complex, frequently updated, widely shared state       |

**Decision rule:** Low-frequency, app-wide values → Context. Frequently updated, complex, or widely shared state that benefits from tooling → Redux.

**Interview line:** "They solve different problems — Context delivers values, Redux manages state. I'd use Context for theme or auth, and Redux for complex shared domain state where selector-based updates and DevTools matter. Plenty of real apps use both."

> ⚠️ Gotcha: Don't frame it as either/or. The strongest answer acknowledges that most production apps mix them.

### 20. Redux vs Redux Toolkit

|                         | Plain Redux                                                                  | Redux Toolkit                                     |
| ----------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------- |
| Store setup             | `createStore` + `applyMiddleware` + DevTools wiring (deprecated pattern) | `configureStore` — one call, sensible defaults |
| Reducers                | `switch` statements, manual spreading                                      | `createSlice` + Immer, "mutating" syntax        |
| Action types & creators | Written by hand                                                              | Auto-generated                                    |
| Async logic             | Install and configure thunk yourself                                         | Thunk built in +`createAsyncThunk`              |
| Data fetching           | Hand-rolled loading flags + caching                                          | RTK Query                                         |
| Safety checks           | None                                                                         | Dev-time mutation & serializability checks        |
| Boilerplate             | High                                                                         | Low                                               |

**What each RTK piece replaces** — the mapping interviewers love:

- `configureStore` → `createStore` + `applyMiddleware` + `combineReducers` + DevTools setup
- `createSlice` → action type constants + action creators + switch reducer
- Immer → manual `{ ...spread }` immutable updates
- `createAsyncThunk` → hand-written thunks dispatching three lifecycle actions
- RTK Query → hand-rolled fetch + loading state + caching

**Interview line:** "Redux Toolkit isn't a different tool — it's the official, opinionated way to write Redux. Same store, actions, and reducers, but with far less boilerplate and safer defaults. Redux's own docs recommend RTK for all new code."

> ⚠️ Gotcha: Be ready for "have you used plain Redux?" Knowing the mapping above shows you understand what RTK is *abstracting* — not just how to call it.

### 21. Local State vs Global State

|          | Local state                                | Global state                                        |
| -------- | ------------------------------------------ | --------------------------------------------------- |
| Scope    | One component (and its children via props) | Available across the app                            |
| Tools    | `useState`, `useReducer`               | Redux/RTK, MobX, (Context for low-frequency)        |
| Lifetime | Dies when the component unmounts           | Lives as long as the store                          |
| Cost     | Cheap, simple                              | More setup, more indirection                        |
| Examples | Modal open, input draft, hover, active tab | Auth session, cart, notifications, user preferences |

**Signals to go global:** many distant components need it; several unrelated places update it; it must survive navigation/unmounting; you want DevTools, undo, or persistence.
**Signals to stay local:** one component or subtree cares; it's short-lived UI state.

**Interview line:** "Default to local state and only promote it when the need is real — lift it, then Context, then a global store. Global state is powerful but adds indirection, so it should be earned, not assumed."

> ⚠️ Gotcha: "Put everything in Redux" is a smell. Storing per-keystroke input text or a modal's open flag globally adds boilerplate and needless re-renders for no benefit. Also remember a third home for some state: the **URL** (filters, pagination, selected tab) — shareable and refresh-proof for free.

### 22. Server State vs Client State

|                                              | Client state                                | Server state                                  |
| -------------------------------------------- | ------------------------------------------- | --------------------------------------------- |
| Who owns it                                  | The browser / your app                      | The backend                                   |
| Access                                       | Synchronous                                 | Asynchronous                                  |
| Can go stale?                                | No — you're the only writer                | Yes — someone else can change it             |
| Shared by others?                            | No                                          | Yes — multiple users/devices                 |
| Needs caching, dedup, refetch, invalidation? | No                                          | Yes                                           |
| Examples                                     | Modal open, selected tab, form draft, theme | Product list, cart from the API, user profile |
| Tools                                        | `useState`, Context, Redux/MobX           | RTK Query, React Query, SWR                   |

**Why the distinction matters:** Server data is really a *cached copy of something you don't own*. Managing it like client state — `dispatch(setProducts(data))` plus your own `isLoading` flags — means re-inventing caching, deduplication, and invalidation badly. Dedicated tools handle all of that.

**Interview line:** "Client state is owned by the app and synchronous; server state is a cached copy of remote data that can go stale. They need different tools — I keep server state in RTK Query or React Query and reserve Redux or local state for genuine client state."

> ⚠️ Gotcha: Copying fetched data into local state (`useState(data)`) creates a stale duplicate — the derived-state trap from #2 all over again. Read from the query hook directly.

## Part 5: Bonus (MobX)

*You have MobX on your resume but it wasn't in the topic list — interviewers will ask about it, so here's the essentials.*

### 23. MobX vs Redux

**What it is:** MobX is a state-management library built on **observable state and automatic dependency tracking**. You mutate observable state directly; components wrapped in `observer` automatically re-render when — and only when — the specific observables they *read* change.

**Why it exists:** It offers a less ceremonial alternative to Redux: no action objects, no reducers, no manual selectors. The library tracks who depends on what for you.

**Mental model:** A spreadsheet. Cells (observables) hold values; formulas (computed values) recalculate automatically when the cells they reference change — you never manually say "update the total."

```jsx
import { makeAutoObservable } from 'mobx';
import { observer } from 'mobx-react-lite';

class CartStore {
  items = [];

  constructor() {
    makeAutoObservable(this); // fields → observable, getters → computed, methods → actions
  }

  add(item) { this.items.push(item); }                                     // direct mutation is fine
  get total() { return this.items.reduce((s, i) => s + i.price * i.qty, 0); } // computed (auto-cached)
}

const cart = new CartStore();

const CartTotal = observer(() => <p>Total: {cart.total}</p>); // re-renders only when `total` changes
```

|                           | Redux (RTK)                          | MobX                                            |
| ------------------------- | ------------------------------------ | ----------------------------------------------- |
| Style                     | Explicit, functional                 | Implicit, reactive / OOP-friendly               |
| Updates                   | Immutable, via dispatched actions    | Direct mutation of observables (inside actions) |
| Stores                    | One central store                    | Often multiple stores                           |
| Re-render tracking        | You define it with selectors         | Automatic — tracks what each`observer` reads |
| Predictability / DevTools | Very high — action log, time travel | Lower ceremony, but less enforced structure     |
| Boilerplate               | Low (RTK) to high (plain)            | Low                                             |

**Interview line:** "Redux is explicit and predictable — single store, immutable updates, every change is a logged action. MobX is implicit and reactive — I mutate observables, and components wrapped in `observer` re-render automatically for exactly what they read. Redux favors predictability and tooling; MobX favors less boilerplate and fine-grained updates."

> ⚠️ Gotcha #1: A component that reads observables but isn't wrapped in `observer` **won't update** — it has no subscription.
>
> ⚠️ Gotcha #2: Dereference observables *inside* the `observer` component. Pulling a value out early (e.g., destructuring a primitive in a parent and passing it down) reads it outside the tracking scope, so later changes won't be noticed.

## Quick self-test before an interview

Go topic by topic, cover the answer, and explain it out loud in under 30 seconds. Then do these four harder drills — they're the ones interviewers actually pose:

1. **Trace one action.** From memory, narrate what happens when a user clicks "Add to cart": `dispatch` → middleware → reducer → new state → subscribers notified → `useSelector` re-runs → component re-renders *only if* the selected value changed. Name what's pure and what isn't.
2. **The comparison round.** Give a 30-second answer for each: Context vs Redux, Redux vs RTK, local vs global state, server vs client state. Lead with the *decision rule*, not the definition.
3. **Debug it.** Why does `useSelector(s => s.items.filter(...))` re-render on every store update? Why does `value={{ theme, setTheme }}` re-render every context consumer? Why does mutating inside a plain reducer do nothing on screen?
4. **Justify your stack.** Be ready for "why Redux/RTK on your resume?" — cover what problem it solved (shared cart/auth state), what RTK removed compared to plain Redux, and where you'd use RTK Query instead of a thunk. If asked about MobX, contrast the explicit-vs-implicit trade-off from #23.

If you can do all four without notes, state management is solid.
