## Part 1: Array Methods

### 1. Mutating vs Non-Mutating — the single most important distinction

**Why it matters:** Interviewers ask this because mutating a shared array by accident is a real, common bug — especially in React, where mutating state directly breaks re-renders (see the Odds & Ends file).

| Mutates the original                      | Does NOT mutate (returns new)                                                                             |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `push`, `pop`, `shift`, `unshift` | `slice`, `concat`                                                                                     |
| `splice`                                | `map`, `filter`, `flat`, `flatMap`                                                                |
| `sort`, `reverse`                     | `join`, `reduce`                                                                                      |
| `fill`, `copyWithin`                  | `find`, `findIndex`, `some`, `every`, `includes`, `indexOf`                                   |
| direct index assignment`arr[0] = x`     | `toSorted`, `toReversed`, `toSpliced`, `with` (ES2023 — non-mutating twins of the mutating ones) |

**How to remember without a table:** methods that primarily exist to **read/derive** something don't mutate. Methods whose whole *job* is to change the array's shape (`push`, `splice`, `sort`) do.

```js
const arr = [3, 1, 2];
const sorted = arr.sort(); // mutates arr AND returns the same reference
console.log(arr === sorted); // true — same array, not a copy!

const arr2 = [3, 1, 2];
const sorted2 = arr2.toSorted(); // ES2023 — doesn't touch arr2
console.log(arr2, sorted2); // [3,1,2] [1,2,3]
```

**Interview line:** "If a method's job is to reorder/add/remove elements in place, it mutates and usually returns something other than a fresh array (or returns the same reference); if its job is to compute a result, it returns a new array and leaves the original untouched."

### 2. `slice` vs `splice`

**`slice(start, end)`** — **non-mutating.** Returns a shallow copy of a portion, `end` excluded. Negative indices count from the end.

**`splice(start, deleteCount, ...itemsToInsert)`** — **mutates.** Removes `deleteCount` elements starting at `start`, optionally inserts new ones there, and **returns the removed elements** (as an array).

```js
const arr = [1, 2, 3, 4, 5];
console.log(arr.slice(1, 3));   // [2, 3] — copy, arr untouched
console.log(arr);               // [1, 2, 3, 4, 5] — unchanged

const arr2 = [1, 2, 3, 4, 5];
const removed = arr2.splice(1, 2, "a", "b"); // remove 2 items at index 1, insert "a","b" there
console.log(arr2);    // [1, "a", "b", 4, 5] — mutated
console.log(removed); // [2, 3] — what got removed
```

**Memory trick:** "**S**lice **s**tays safe (copies). s**P**lice **p**unches a hole (mutates)."

**Interview line:** "`slice` copies out a range without touching the original; `splice` cuts into the original array in place and hands back whatever it removed."

### 3. `find` vs `findIndex` vs `findLast` vs `filter`

All four take a predicate `(element, index, array) => boolean`, but differ in **what they return** and **how many results**.

```js
const users = [{ id: 1, active: false }, { id: 2, active: true }, { id: 3, active: true }];

users.find(u => u.active);      // { id: 2, active: true } — FIRST match, or undefined
users.findIndex(u => u.active); // 1 — index of first match, or -1
users.findLast(u => u.active);  // { id: 3, active: true } — LAST match (ES2023)
users.filter(u => u.active);    // [{id:2,...}, {id:3,...}] — ALL matches, as an array
```

**How to pick the right one:** "I need the item" → `find`. "I need where it is" → `findIndex`. "I need all of them" → `filter`. "I need the item, but searching from the end" → `findLast`.

**Interview line:** "`find`/`findIndex` stop at the first match and return the element or its index; `filter` doesn't stop — it collects every match into a new array."

---

### 4. `some` vs `every`

Both take a predicate and return a **boolean** — the difference is the quantifier, and both **short-circuit** (stop early once the answer is decided).

```js
const nums = [2, 4, 6, 7, 8];

nums.some(n => n % 2 !== 0);  // true — at least one odd number (stops at 7)
nums.every(n => n % 2 === 0); // false — not all even (stops at 7)

[].some(x => true);  // false — vacuously false, nothing to satisfy it
[].every(x => false); // true — vacuously true, nothing to violate it
```

**Mental model:** `some` is an "OR" across the array (any true → true). `every` is an "AND" across the array (any false → false).

> ⚠️ Gotcha: on an **empty array**, `every` returns `true` and `some` returns `false` — this trips people up because it feels backwards until you think of it as vacuous truth.

**Interview line:** "`some`/`every` both short-circuit — `some` stops as soon as it finds a `true`, `every` stops as soon as it finds a `false`."

---

### 5. `includes` vs `indexOf`

Both check for a value's presence — the real difference is **how they handle `NaN`**.

```js
[1, 2, NaN].includes(NaN); // true  — includes uses SameValueZero, which treats NaN as equal to itself
[1, 2, NaN].indexOf(NaN);  // -1    — indexOf uses ===, and NaN === NaN is false
```

**When to use which:** `includes` → just need a boolean, and it's correct for `NaN`. `indexOf` → need the position, but remember it can never find `NaN`.

**Interview line:** "`includes` is the one to reach for when checking presence, specifically because it's the only one of the two that works correctly for `NaN` — `indexOf` uses strict equality, which `NaN` always fails against itself."

---

### 6. `flat` / `flatMap`

**`flat(depth = 1)`** — flattens nested arrays up to `depth` levels. `Infinity` flattens completely.

```js
[1, [2, [3, [4]]]].flat();      // [1, 2, [3, [4]]] — default depth 1
[1, [2, [3, [4]]]].flat(2);     // [1, 2, 3, [4]]
[1, [2, [3, [4]]]].flat(Infinity); // [1, 2, 3, 4]
```

**`flatMap(fn)`** — maps, then flattens **one level** — but does it in a single pass, more efficient than chaining `.map().flat()` separately.

```js
[1, 2, 3].flatMap(x => [x, x * 2]); // [1, 2, 2, 4, 3, 6]
// same as [1,2,3].map(x => [x, x*2]).flat(), but one pass instead of two
```

**Real use case:** turning "one item → zero or more items" — e.g., splitting each sentence into words: `sentences.flatMap(s => s.split(" "))`.

### 7. `Array.from` / `Array.of` / `Array.isArray`

**`Array.from(arrayLike, mapFn?)`** — builds a real array from an **iterable** (Set, Map, string) or an **array-like** (has a `.length`, like `arguments` or a `NodeList`) — things that aren't real arrays and can't use array methods directly.

```js
Array.from("abc");                       // ["a", "b", "c"] — strings are iterable
Array.from({ length: 3 }, (_, i) => i*2); // [0, 2, 4] — array-like + generator function
Array.from(new Set([1, 2, 2, 3]));       // [1, 2, 3] — Set → array
```

**Common real use:** `Array.from(document.querySelectorAll(".item"))` — a `NodeList` isn't a real array, so it doesn't have `.map`/`.filter` until converted.

**`Array.of(...items)`** — creates an array **from its arguments as elements**. Exists to fix `Array()`'s weird single-number-argument behavior.

```js
Array(7);      // [ <7 empty items> ] — length 7, no actual elements! (a trap)
Array.of(7);   // [7] — one element, the number 7
Array.of(1, 2, 3); // [1, 2, 3]
```

**`Array.isArray(x)`** — the only reliable way to check if something is really an array (see Part 1 of the next file for why `typeof` fails here).

---

### 8. `.at(index)`

**What it is:** Index access that supports **negative numbers** — cleaner than `arr[arr.length - 1]`.

```js
const arr = [10, 20, 30];
arr.at(-1);        // 30 — last element
arr[arr.length - 1]; // 30 — same thing, more verbose
arr.at(0);          // 10 — positive works too, just like arr[0]
```

Also works on strings: `"hello".at(-1)` → `"o"`.

### 9. `sort()` — the one everyone gets wrong

**The trap:** `sort()` with no comparator converts every element to a **string** and compares them lexicographically (UTF-16 code unit order) — not numerically.

```js
[10, 2, 1].sort();            // [1, 10, 2] ❌ — "1" < "10" < "2" as strings
[10, 2, 1].sort((a, b) => a - b); // [1, 2, 10] ✅ — numeric comparator
```

**How the comparator works:** `(a, b) => a - b` — if negative, `a` comes first; if positive, `b` comes first; if zero, order unchanged (between those two).

```js
arr.sort((a, b) => a - b);            // ascending numbers
arr.sort((a, b) => b - a);            // descending numbers
arr.sort((a, b) => a.name.localeCompare(b.name)); // alphabetical strings (locale-aware)
```

**Stability (ES2019+):** `sort` is guaranteed **stable** — elements that compare equal keep their original relative order. Before ES2019 this wasn't guaranteed across engines.

**Interview line:** "`sort` without a comparator does string comparison, which silently breaks number sorting — always pass `(a, b) => a - b` (or the reverse) for numbers."

## Part 2: String Methods

### 10. `slice` vs `substring` vs `substr`

|                           | Negative indices                       | If start > end                     | Status                        |
| ------------------------- | -------------------------------------- | ---------------------------------- | ----------------------------- |
| `slice(start, end)`     | Counts from the end                    | Returns`""`                      | Preferred                     |
| `substring(start, end)` | Treated as`0`                        | **Swaps them** automatically | Still fine, less intuitive    |
| `substr(start, length)` | Start counts from end (length doesn't) | N/A — second arg is a length      | **Deprecated** — avoid |

```js
"hello world".slice(-5);        // "world"
"hello world".substring(-5, 5); // "hello" — negative clamps to 0, so substring(0,5)
"hello world".substr(-5, 3);    // "wor" — deprecated, avoid in new code
```

**Interview line:** "I default to `slice` — it handles negative indices predictably, unlike `substring`, and unlike `substr` it's not deprecated."

### 11. Search & Check Methods

```js
"Hello World".includes("World");   // true — substring present anywhere
"Hello World".startsWith("Hello"); // true
"Hello World".endsWith("World");   // true

"Hello".includes("hello"); // false — case-sensitive! (.toLowerCase() first if needed)
```

---

### 12. Padding & Trimming

```js
"5".padStart(3, "0");   // "005" — common for formatting (e.g., "05" for a day)
"5".padEnd(3, "0");     // "500"

"  hi  ".trim();        // "hi"
"  hi  ".trimStart();   // "hi  "
"  hi  ".trimEnd();     // "  hi"
```

**Real use case for `padStart`:** formatting numbers with leading zeros — clock displays, IDs, dates.

---

### 13. Replace & Split

**`replace(pattern, replacement)`** — replaces the **first** match only, unless `pattern` is a regex with the global flag `/g`.
**`replaceAll(pattern, replacement)`** — always replaces every match (ES2021). If `pattern` is a regex, it **must** have the `/g` flag or it throws.

```js
"a-a-a".replace("a", "b");    // "b-a-a" — only the first
"a-a-a".replaceAll("a", "b"); // "b-b-b" — all of them
"a-a-a".replace(/a/g, "b");   // "b-b-b" — /g makes replace() act like replaceAll
```

**`split(separator, limit?)`** — splits into an array; `limit` caps how many pieces you get back (it doesn't just truncate the string first — it stops collecting after `limit` pieces).

```js
"a-b-c-d".split("-");     // ["a","b","c","d"]
"a-b-c-d".split("-", 2);  // ["a","b"] — only the first 2 pieces
```

## Part 3: Object Static Methods

### 14. `Object.keys` / `values` / `entries`

```js
const user = { name: "Saksham", role: "engineer" };

Object.keys(user);   // ["name", "role"]
Object.values(user); // ["Saksham", "engineer"]
Object.entries(user); // [["name","Saksham"], ["role","engineer"]]
```

**Why `entries` matters:** it's the bridge that turns an object problem into an array problem — you saw this pattern already for `pick`/`omit`/`invert` in the Logic file (`Object.entries` → `map`/`filter` → `Object.fromEntries`).

All three only include **own, enumerable** properties — not inherited ones from the prototype chain.

---

### 15. `Object.assign`

**What it is:** Shallow-copies (merges) properties from one or more source objects into a **target** object. **Mutates the target and returns it.**

```js
const target = { a: 1 };
const result = Object.assign(target, { b: 2 }, { c: 3 });
console.log(target === result); // true — target itself was mutated
console.log(target);            // { a: 1, b: 2, c: 3 }

// To avoid mutating anything, use an empty object as target:
const merged = Object.assign({}, obj1, obj2); // same idea as {...obj1, ...obj2}
```

> ⚠️ Same shallow-copy gotcha as spread (JS Core file, topic 1): nested objects are still shared references after `Object.assign`.

**Interview line:** "`Object.assign` mutates its first argument — if I don't want that, I pass `{}` as the target, which is exactly what spread syntax does under the hood."

---

### 16. `Object.defineProperty` / Property Descriptors / Getters & Setters

**What it is:** Normal property assignment (`obj.x = 1`) creates a property that is **writable, enumerable, and configurable** by default. `Object.defineProperty` lets you control each of those explicitly.

| Descriptor       | Controls                                                             |
| ---------------- | -------------------------------------------------------------------- |
| `value`        | The actual value                                                     |
| `writable`     | Can it be reassigned?                                                |
| `enumerable`   | Does it show up in`for...in`, `Object.keys`, `JSON.stringify`? |
| `configurable` | Can it be deleted or redefined?                                      |

```js
const obj = {};
Object.defineProperty(obj, "id", {
  value: 42,
  writable: false,
  enumerable: false,
  configurable: false,
});

obj.id = 100;             // silently fails (non-strict) — writable: false
console.log(obj.id);      // 42 — unchanged
console.log(Object.keys(obj)); // [] — hidden from enumeration
console.log(JSON.stringify(obj)); // {} — hidden from serialization too
```

**Getters/setters** — properties that run code on read/write instead of storing a plain value:

```js
const person = {
  first: "Saksham",
  last: "Verma",
  get fullName() {
    return `${this.first} ${this.last}`; // computed on every read, no parentheses needed
  },
  set fullName(value) {
    [this.first, this.last] = value.split(" ");
  },
};

console.log(person.fullName); // "Saksham Verma" — called like a property, not a method
person.fullName = "New Name";
console.log(person.first);    // "New"
```

**Interview line:** "Plain assignment gives you writable/enumerable/configurable by default; `defineProperty` lets you lock a property down — this is also how getters/setters and things like `Vue`'s old reactivity system are implemented under the hood."

---

### 17. `Object.fromEntries`

**What it is:** The inverse of `Object.entries` — builds an object from an array (or any iterable, like a `Map`) of `[key, value]` pairs.

```js
Object.fromEntries([["a", 1], ["b", 2]]); // { a: 1, b: 2 }

const map = new Map([["x", 1], ["y", 2]]);
Object.fromEntries(map); // { x: 1, y: 2 } — quick Map → plain object conversion

// Combine with entries + filter/map, as in the Logic file's pick/omit:
const params = new URLSearchParams("?a=1&b=2");
Object.fromEntries(params); // { a: "1", b: "2" } — common real-world use
```

---

### 18. `Object.create` / `Object.getPrototypeOf`

**What it is:** `Object.create(proto)` creates a new object with `proto` explicitly set as its prototype — you saw this already in the JS Core file's Prototype topic. `Object.getPrototypeOf(obj)` is the modern, correct way to read an object's prototype (prefer it over `obj.__proto__`).

```js
const animal = { eats: true };
const dog = Object.create(animal);
console.log(Object.getPrototypeOf(dog) === animal); // true

const noProtoObj = Object.create(null); // an object with NO prototype at all
console.log(noProtoObj.toString); // undefined — doesn't even inherit Object.prototype
```

**Real use for `Object.create(null)`:** a "pure" dictionary/map object with zero inherited properties — avoids surprises if a key happens to be named `toString` or `constructor`.

## Part 4: Number & JSON

### 19. `parseInt` / `parseFloat` vs `Number()`

**The core difference:** `parseInt`/`parseFloat` parse **leading** numeric characters and stop at the first invalid one. `Number()` requires the **entire** string to be a valid number, or it returns `NaN`.

```js
parseInt("123abc");   // 123 — stops at "a"
Number("123abc");     // NaN — whole string isn't a valid number

parseFloat("3.14abc"); // 3.14
Number("3.14abc");     // NaN

Number("");    // 0    — empty string converts to 0 (a classic gotcha)
parseInt("");  // NaN
Number("  42  "); // 42 — Number trims whitespace
```

**`parseInt` always takes a radix as the second argument in good code:**

```js
parseInt("10", 2);  // 2  — binary "10" = decimal 2
parseInt("10", 16); // 16 — hex "10" = decimal 16
parseInt("010");    // 10 — modern engines treat a "0" prefix as decimal (historically some engines read it as octal — always pass radix 10 explicitly to be safe and clear)
```

**Interview line:** "`parseInt`/`parseFloat` parse as much as they can from the front and ignore the rest; `Number()` is all-or-nothing — I use `Number()` for validating full user input, and `parseInt` when I expect a numeric prefix, like reading `'20px'`."

### 20. `JSON.stringify(value, replacer, space)`

**What gets silently dropped or changed** (this is the part that matters for interviews, and explains why `JSON.parse(JSON.stringify(x))` is a broken deep-clone method — see the Logic file):

```js
JSON.stringify({
  a: 1,
  b: undefined,        // dropped entirely (key removed)
  c: function () {},   // dropped entirely
  d: Symbol("x"),       // dropped entirely
  e: [undefined, function () {}], // inside an ARRAY, becomes null instead of being dropped
});
// '{"a":1,"d":[null,null]}'
```

**`replacer`** — a function `(key, value) => newValue` to transform/filter values, or an **array of key names to keep**:

```js
JSON.stringify({ a: 1, b: 2, c: 3 }, ["a", "c"]); // '{"a":1,"c":3}' — only these keys
```

**`space`** — a number (spaces) or string, for pretty-printing:

```js
JSON.stringify({ a: 1, b: 2 }, null, 2);
// '{\n  "a": 1,\n  "b": 2\n}'
```

**`Date` objects** get converted via their `.toJSON()` method (which calls `.toISOString()`), so they survive as strings — but come back as **strings**, not `Date` objects, when parsed.

**Throws** on circular references — `TypeError: Converting circular structure to JSON`.

---

### 21. `JSON.parse(text, reviver)`

**`reviver`** — a function `(key, value) => newValue`, called **bottom-up** (innermost values first) for every key, letting you transform values as they're parsed — e.g., turning date strings back into real `Date` objects.

```js
const json = '{"name":"Saksham","createdAt":"2026-09-25T10:00:00.000Z"}';

const data = JSON.parse(json, (key, value) => {
  if (key === "createdAt") return new Date(value);
  return value;
});
console.log(data.createdAt instanceof Date); // true
```

**Interview line:** "`JSON.stringify` silently drops functions, `undefined`, and symbols, and turns `Date`s into ISO strings — which is exactly why round-tripping through JSON is a broken way to deep clone or preserve types."
