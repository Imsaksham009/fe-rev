## The Big Picture First (read this once, it ties everything together)

JavaScript is **single-threaded** — it has one call stack and can do one thing at a time. But the browser is not single-threaded. When you call `setTimeout` or `fetch`, JS hands that work to the **browser** (Web APIs), keeps running your code, and later the browser says "done, here's your callback."

Those callbacks don't jump onto the stack immediately — they wait in **queues**. The **event loop** is the traffic cop that decides which queued callback runs next, and only when the call stack is empty.

**Promises** are just a cleaner way to express "a value that will exist later," and their callbacks go into a special high-priority queue (the microtask queue).

Keep this picture in mind: **Stack → Web APIs → Queues → Event Loop → back to Stack.**

## Part 1: Promises

### 1. What is a Promise?

**What it is:** A Promise is an object that represents the **eventual result** of an async operation. Instead of passing a callback into a function (callback style), the function returns a Promise, and you attach callbacks to it.

**Why it exists:** Callbacks nested inside callbacks ("callback hell") are hard to read, and error handling has to be repeated at every level. Promises flatten this into a chain and give one place to catch errors.

**Mental model:** A restaurant buzzer. You order (start the async task), get a buzzer (the Promise) immediately, and go sit down (your code continues). When the food is ready, the buzzer goes off (resolve) — or you're told they ran out (reject).

```js
const promise = new Promise((resolve, reject) => {
  // this function (the "executor") runs IMMEDIATELY and synchronously
  setTimeout(() => {
    const success = true;
    if (success) resolve("data");     // fulfilled
    else reject(new Error("failed")); // rejected
  }, 1000);
});

promise.then(data => console.log(data)); // "data" after 1s
```

> ⚠️ Gotcha: The executor function runs **synchronously** the moment you call `new Promise(...)`. Only the `.then` callbacks are async. This shows up in output questions all the time.

---

### 2. Promise States

**What it is:** A Promise is always in one of three states:

| State         | Meaning                                          |
| ------------- | ------------------------------------------------ |
| `pending`   | Initial state — not done yet                    |
| `fulfilled` | Completed successfully, has a**value**     |
| `rejected`  | Failed, has a**reason** (usually an Error) |

"**Settled**" = either fulfilled or rejected (i.e., no longer pending).

**Key rule:** A promise settles **only once**. After it's fulfilled or rejected, it's locked forever. Further `resolve`/`reject` calls are silently ignored.

```js
const p = new Promise((resolve, reject) => {
  resolve("first");
  resolve("second"); // ignored
  reject("error");   // ignored
});
p.then(console.log); // "first"
```

**Interview line:** "A promise starts pending and settles exactly once, to either fulfilled with a value or rejected with a reason — after that its state is immutable."

---

### 3. `.then()`

**What it is:** `.then(onFulfilled, onRejected)` registers callbacks for when the promise settles. The important part: **`.then()` always returns a NEW promise.** That's what makes chaining possible.

What the new promise resolves to depends on what your callback does:

| Inside the`.then` callback you... | The returned promise...            |
| ----------------------------------- | ---------------------------------- |
| return a normal value`x`          | fulfills with`x`                 |
| return nothing                      | fulfills with`undefined`         |
| return a promise                    | waits for it and adopts its result |
| throw an error                      | rejects with that error            |

```js
Promise.resolve(5)
  .then(x => x * 2)             // returns 10 → next promise fulfills with 10
  .then(x => console.log(x));   // 10
```

> ⚠️ Gotcha: `.then` callbacks are **always async**, even if the promise is already resolved. `Promise.resolve(1).then(...)` still runs its callback later, as a microtask.

---

### 4. Promise Chaining

**What it is:** Since every `.then()` returns a new promise, you can line them up so each step receives the previous step's result. This replaces nested callbacks.

**Mental model:** An assembly line — each station receives what the previous one handed over. If you forget to `return`, the next station receives `undefined`.

```js
// ❌ Callback hell
getUser(id, user => {
  getPosts(user, posts => {
    getComments(posts[0], comments => { /* ... */ });
  });
});

// ✅ Promise chain — flat
getUser(id)
  .then(user => getPosts(user))        // return the promise!
  .then(posts => getComments(posts[0]))
  .then(comments => console.log(comments))
  .catch(err => console.error(err));   // one catch for all steps
```

> ⚠️ Most common bug: forgetting `return` inside `.then`.
>
> ```js
> .then(user => { getPosts(user); })   // ❌ no return → next .then gets undefined,
>                                      //    and doesn't wait for getPosts
> .then(user => getPosts(user))        // ✅ arrow with no braces returns implicitly
> ```

**Interview line:** "Chaining works because `.then` returns a new promise that resolves with whatever the callback returns — returning a promise makes the chain wait for it."

---

### 5. `.catch()`

**What it is:** `.catch(fn)` is shorthand for `.then(undefined, fn)`. It handles a rejection from **anywhere above it** in the chain — the error "skips" all `.then` callbacks until it finds a `.catch`.

**Key behavior:** `.catch` also returns a new promise. If the catch handler returns normally, the chain **recovers** and continues as fulfilled.

```js
Promise.reject(new Error("boom"))
  .then(() => console.log("skipped"))       // skipped — chain is rejected
  .catch(err => {
    console.log("caught:", err.message);     // "caught: boom"
    return "recovered";
  })
  .then(val => console.log(val));            // "recovered" — chain continues normally
```

**Mental model:** A rejection is a ball rolling down the chain, bouncing past every `.then` until a `.catch` catches it. Once caught, the chain is back to normal.

> ⚠️ Gotcha: A `.catch` only catches errors from **above** it. Errors thrown in a `.then` *after* the last `.catch` are unhandled.

---

### 6. `.finally()`

**What it is:** Runs a callback when the promise settles — fulfilled **or** rejected. Used for cleanup (hide loader, close connection).

**Key behaviors:**

- The callback receives **no arguments** (it doesn't know if it succeeded or failed).
- It **passes through** the original value/error — its return value is ignored.
- Exception: if `finally` throws (or returns a rejected promise), that error replaces the original result.

```js
setLoading(true);
fetchData()
  .then(data => render(data))
  .catch(err => showError(err))
  .finally(() => setLoading(false)); // runs either way

Promise.resolve(1)
  .finally(() => 2)          // return value ignored
  .then(v => console.log(v)); // 1
```

**Interview line:** "`finally` is for cleanup — it gets no arguments and passes the original result through unchanged, unless it throws."

---

### 7. async/await

**What it is:** Syntax sugar over promises that lets you write async code that *reads* like sync code.

- An `async` function **always returns a promise**. Returning `x` = returning `Promise.resolve(x)`. Throwing = returning a rejected promise.
- `await` pauses **only that async function** until the promise settles, then gives you the value (or throws the error).

**Mental model:** `await` means "pause this function here, go do other stuff, and come back to this exact line when the promise is ready." The rest of the program keeps running — **`await` doesn't block the thread**, it only suspends the one function.

**What really happens under the hood:** Everything after an `await` is effectively put into a `.then()` callback. So the code after `await` runs as a **microtask**.

```js
async function getData() {
  console.log("A");
  const res = await fetch("/api");  // pauses getData, NOT the whole program
  console.log("C");                 // runs later, like inside .then()
  return res.json();
}

getData();
console.log("B");
// Output: A, B, C
```

```js
// These two are equivalent:
async function f() { return 1; }
function f() { return Promise.resolve(1); }
```

> ⚠️ Gotcha: Code **before** the first `await` in an async function runs **synchronously**. Only code after `await` is deferred.

**Interview line:** "async/await is sugar over promises — an async function always returns a promise, and code after `await` resumes as a microtask once the awaited promise settles."

---

### 8. Error Handling

**With promises:** use `.catch()` at the end of the chain.

**With async/await:** use `try/catch` — a rejected promise under `await` throws like a normal error.

```js
async function load() {
  try {
    const res = await fetch("/api/user");
    if (!res.ok) throw new Error(`HTTP ${res.status}`); // fetch doesn't reject on 404/500!
    const data = await res.json();
    return data;
  } catch (err) {
    console.error("Failed:", err.message);
    throw err; // re-throw if the caller should know
  } finally {
    console.log("done");
  }
}
```

**Important gotchas interviewers love:**

1. **`fetch` does NOT reject on HTTP errors (404, 500).** It only rejects on network failure. You must check `res.ok` yourself.
2. **`try/catch` without `await` doesn't catch async errors:**

   ```js
   try {
     fetchData(); // ❌ no await — the rejection happens later, outside this try
   } catch (e) { /* never runs */ }

   try {
     await fetchData(); // ✅
   } catch (e) { /* catches it */ }
   ```
3. **Errors thrown inside a `setTimeout` inside a promise are NOT caught by the promise:**

   ```js
   new Promise(() => {
     setTimeout(() => { throw new Error("x"); }, 0); // uncaught! runs outside the executor
   }).catch(() => console.log("never"));
   ```

   The throw happens later, in a different call stack. Use `reject(...)` instead of `throw` in async callbacks.
4. **Unhandled rejections:** A rejected promise with no `.catch` triggers an `unhandledrejection` event (browser) / warning or crash (Node). Always handle them.

**Interview line:** "Use `.catch` for chains, `try/catch` with `await` — and remember `fetch` only rejects on network failure, so check `res.ok`."

## Part 2: Promise Utilities

All four take an **iterable of promises** (non-promise values are treated as already-resolved) and return **one** promise. Think of them as four different "wait strategies."

### 9. `Promise.all`

**What it does:** Waits for **all** to fulfill. Resolves with an array of results **in the same order as the input** (not completion order). **Rejects immediately** as soon as **any one** rejects (fail-fast).

**When to use:** Multiple independent requests that are **all required** — e.g., load user + settings + permissions before showing a page.

```js
const [user, posts] = await Promise.all([
  fetchUser(),   // takes 2s
  fetchPosts(),  // takes 1s
]);
// total ≈ 2s (parallel), not 3s. Results are in input order.
```

> ⚠️ Gotcha: When `Promise.all` rejects, the other promises **keep running** — they're not cancelled. Their results are just ignored. (To actually cancel, use AbortController.)

> Edge: `Promise.all([])` resolves immediately with `[]`.

---

### 10. `Promise.allSettled`

**What it does:** Waits for **all** to settle, no matter what. **Never rejects.** Resolves with an array of result objects:

- `{ status: "fulfilled", value: ... }`
- `{ status: "rejected", reason: ... }`

**When to use:** You want everything that succeeded, and to handle failures individually — e.g., a dashboard where one failing widget shouldn't break the others.

```js
const results = await Promise.allSettled([fetchA(), fetchB(), fetchC()]);

results.forEach(r => {
  if (r.status === "fulfilled") render(r.value);
  else showWidgetError(r.reason);
});
```

---

### 11. `Promise.race`

**What it does:** Settles as soon as the **first** promise **settles** — whether it fulfills **or** rejects. Whichever finishes first wins.

**When to use:** Timeouts (race the request against a timer).

```js
const result = await Promise.race([
  fetch("/api"),
  new Promise((_, reject) => setTimeout(() => reject(new Error("Timeout")), 5000)),
]);
```

> Edge: `Promise.race([])` stays **pending forever**.

---

### 12. `Promise.any`

**What it does:** Resolves with the **first fulfilled** promise — **ignores rejections**. Only rejects if **all** reject, with an `AggregateError` (which has an `.errors` array).

**When to use:** Redundant sources — fetch from multiple mirrors/CDNs and use whichever succeeds first.

```js
try {
  const data = await Promise.any([fetchFromCDN1(), fetchFromCDN2()]);
} catch (e) {
  console.log(e instanceof AggregateError); // true — all failed
  console.log(e.errors);                     // array of all rejection reasons
}
```

---

### 13. Cheat Sheet — the four side by side

| Method         | Resolves when                      | Rejects when                      | Result                             |
| -------------- | ---------------------------------- | --------------------------------- | ---------------------------------- |
| `all`        | **all** fulfill              | **first** rejection         | array of values (input order)      |
| `allSettled` | **all** settle               | never                             | array of`{status, value/reason}` |
| `race`       | **first to settle** fulfills | **first to settle** rejects | single value                       |
| `any`        | **first** fulfillment        | **all** reject              | single value /`AggregateError`   |

**Memory trick:**

- `all` → "all or nothing"
- `allSettled` → "report card for everyone"
- `race` → "first across the line, win or crash"
- `any` → "first success, I don't care about failures"

**Bonus — `Promise.all` polyfill (very commonly asked):**

```js
function promiseAll(promises) {
  return new Promise((resolve, reject) => {
    const results = [];
    let completed = 0;

    if (promises.length === 0) return resolve([]);

    promises.forEach((p, index) => {
      Promise.resolve(p)             // handles non-promise values too
        .then(value => {
          results[index] = value;    // index, NOT push — preserves input order
          completed++;
          if (completed === promises.length) resolve(results);
        })
        .catch(reject);              // first rejection rejects everything
    });
  });
}
```

Key points to say out loud: use `index` not `push` (order), count completions (don't check `results.length` — sparse array trap), wrap with `Promise.resolve` for plain values.

## Part 3: Event Loop

This is the single most important section for output questions. Learn the pieces, then the algorithm.

### 14. Call Stack

**What it is:** Where JS actually executes code — one function frame at a time, LIFO. (Covered in JS Core.) The crucial fact for async: **the event loop can only push a queued callback when the call stack is completely empty.**

That's why this blocks everything:

```js
setTimeout(() => console.log("timer"), 0);
const start = Date.now();
while (Date.now() - start < 3000) {} // blocks the stack for 3s
// "timer" logs after 3s, not 0ms — the stack was never empty
```

---

### 15. Web APIs

**What it is:** Features provided by the **browser** (not the JS engine): `setTimeout`, `setInterval`, `fetch`, DOM events, `XMLHttpRequest`, geolocation, etc. They run **outside** the JS thread.

**Flow:** You call `setTimeout(cb, 1000)` → JS hands the timer to the browser and moves on immediately → browser counts 1000ms → browser puts `cb` into the macrotask queue → event loop moves it to the stack when it's empty.

**Mental model:** Web APIs are assistants. JS says "remind me in 1 second" and goes back to work. The assistant doesn't interrupt — they leave a note in the inbox (queue).

> ⚠️ `setTimeout(fn, 0)` does **not** mean "run immediately." It means "run after at least 0ms, **once the stack is empty and all microtasks are done**." The delay is a **minimum**, not a guarantee.

---

### 16. Callback Queue / Macrotask Queue (same thing)

**Naming confusion cleared up:** "Callback queue," "task queue," and "macrotask queue" all refer to the **same idea** — the regular queue for callbacks from Web APIs. Different tutorials use different names.

**What goes here (macrotasks):**

- `setTimeout`, `setInterval` callbacks
- DOM event callbacks (click, input…)
- I/O, `MessageChannel`
- `setImmediate` (Node only)

**Key rule:** The event loop takes **only ONE macrotask** per loop iteration, then checks microtasks again.

---

### 17. Microtask Queue

**What goes here (microtasks):**

- `.then` / `.catch` / `.finally` callbacks
- Code after `await` in async functions
- `queueMicrotask(fn)`
- `MutationObserver` callbacks
- (`process.nextTick` in Node — it has its own queue that runs even before promise microtasks)

**Key rule:** Microtasks have **higher priority**. After the stack empties, the event loop runs **ALL** microtasks — including new ones added *while* draining — before touching any macrotask.

**Mental model:** Microtasks are VIP guests. After every piece of work, the bouncer lets in the *entire* VIP line (even people who just joined it) before letting in **one** regular guest.

> ⚠️ Consequence: an infinite microtask loop **freezes the page** (rendering never gets a turn), just like a `while(true)`:
>
> ```js
> function loop() { Promise.resolve().then(loop); }
> loop(); // page hangs — the microtask queue never empties
> ```
>
> An infinite `setTimeout` loop does NOT freeze the page, because the browser gets to render between macrotasks.

---

### 18. Event Loop Execution Order — THE ALGORITHM

Memorize these 5 steps. Every output question is just applying them.

```
1. Run all synchronous code (the current script) until the call stack is empty.
2. Run ALL microtasks — keep going until the microtask queue is empty
   (including microtasks queued during this step).
3. (Browser) Render if needed — requestAnimationFrame, style, layout, paint.
4. Take ONE macrotask from the queue and run it.
5. Go back to step 2.
```

**One-line version:** *Sync → all micro → (render) → one macro → all micro → one macro → ...*

**Diagram:**

```
   ┌──────────────┐        ┌─────────────────┐
   │  Call Stack  │ ─────► │    Web APIs     │  (timers, fetch, events)
   └──────▲───────┘        └────────┬────────┘
          │                         │ callback ready
          │                         ▼
          │               ┌──────────────────────┐
          │               │  Macrotask Queue     │  setTimeout, events
          │               └──────────────────────┘
          │               ┌──────────────────────┐
          │               │  Microtask Queue     │  .then, await, queueMicrotask
          │               └──────────────────────┘
          │                         │
          └──── Event Loop ◄────────┘
     (only pushes when stack is EMPTY; drains ALL micro before ONE macro)
```

### 19. How to Solve Output Questions (the method)

Don't guess. Trace with **three columns** on paper (or in your head):

```
SYNC OUTPUT  |  MICROTASK QUEUE  |  MACROTASK QUEUE
```

**Steps:**

1. Read top to bottom. For each line:
   - `console.log` in sync code → write it in output **now**.
   - `new Promise(executor)` → the executor runs **now** (sync).
   - `.then(cb)` on an already-resolved promise → push `cb` to **microtask** queue.
   - `.then(cb)` on a pending promise → `cb` waits; it's queued when that promise resolves.
   - `setTimeout(cb)` → push `cb` to **macrotask** queue.
   - `await x` inside async fn → everything after it in that function goes to the **microtask** queue (once `x` resolves); the function exits for now.
2. Stack empty → run microtasks one by one (front to back). Any new micro/macro tasks they create go to the **back** of their queue.
3. Microtask queue empty → run **one** macrotask → back to step 2.

**Rules of thumb:**

- `new Promise` executor = **sync**.
- Code before the first `await` = **sync**.
- A chained `.then` is only queued **after** the previous `.then` runs → two independent chains **interleave** (a1, b1, a2, b2).
- A `setTimeout` created inside a microtask goes to the back of the macrotask queue.
- A promise created inside a `setTimeout` runs **right after that timeout** (before the next timeout).

### 20. Output Practice (cover the answer, trace first)

**Q1 — The basic one**

```js
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3));
console.log(4);
```

<details><summary>Answer</summary>

`1 4 3 2`
Sync: 1, 4. Micro: 3. Macro: 2.

</details>

---

**Q2 — Promise executor is sync**

```js
console.log("A");
new Promise(resolve => {
  console.log("B");
  resolve();
  console.log("C");
}).then(() => console.log("D"));
console.log("E");
```

<details><summary>Answer</summary>

`A B C E D`
The executor runs synchronously — `resolve()` doesn't stop it, so C still logs. Only `.then` is deferred.

</details>

---

**Q3 — The classic**

```js
console.log("script start");
setTimeout(() => console.log("setTimeout"), 0);
Promise.resolve()
  .then(() => console.log("promise1"))
  .then(() => console.log("promise2"));
console.log("script end");
```

<details><summary>Answer</summary>

`script start → script end → promise1 → promise2 → setTimeout`
promise2 is queued when promise1 runs — still in the same microtask drain, so both run before the timeout.

</details>

---

**Q4 — async/await**

```js
async function a() {
  console.log("a1");
  await b();
  console.log("a2");
}
async function b() {
  console.log("b");
}
console.log("start");
a();
console.log("end");
```

<details><summary>Answer</summary>

`start a1 b end a2`
Everything before `await` runs sync — including calling `b()`, which logs "b" synchronously. "a2" is after the await → microtask.

</details>

---

**Q5 — Two chains interleave**

```js
Promise.resolve()
  .then(() => console.log("a1"))
  .then(() => console.log("a2"));

Promise.resolve()
  .then(() => console.log("b1"))
  .then(() => console.log("b2"));
```

<details><summary>Answer</summary>

`a1 b1 a2 b2`
Initially the micro queue holds [a1, b1]. Running a1 queues a2 at the back → [b1, a2]. Running b1 queues b2 → [a2, b2].

</details>

---

**Q6 — Microtasks inside macrotasks**

```js
setTimeout(() => {
  console.log("t1");
  Promise.resolve().then(() => console.log("p-inside-t1"));
}, 0);

setTimeout(() => console.log("t2"), 0);

Promise.resolve().then(() => {
  console.log("p1");
  setTimeout(() => console.log("t3"), 0);
});
```

<details><summary>Answer</summary>

`p1 t1 p-inside-t1 t2 t3`
Sync: nothing logged. Micro: p1 (queues t3 at the BACK of macro queue → [t1, t2, t3]).
Macro t1 → queues micro → micro queue drained immediately → p-inside-t1. Then t2, then t3.

</details>

---

**Q7 — Mixed await + setTimeout**

```js
async function main() {
  console.log(1);
  await null;
  console.log(2);
  setTimeout(() => console.log(3), 0);
  await Promise.resolve();
  console.log(4);
}
main();
console.log(5);
```

<details><summary>Answer</summary>

`1 5 2 4 3`
1 sync → await pauses main → 5 sync. Micro: 2, schedule timer (3), await again → micro: 4. Then macro: 3.

</details>

---

**Q8 — catch recovers the chain**

```js
Promise.reject("err")
  .then(() => console.log("then"))
  .catch(e => console.log("catch", e))
  .then(() => console.log("after catch"));
```

<details><summary>Answer</summary>

`catch err → after catch`
The first `.then` is skipped. After `.catch` handles it, the chain is fulfilled again.

</details>

---

**Q9 — finally passes through**

```js
Promise.resolve(1)
  .finally(() => 2)
  .then(v => console.log(v));

Promise.reject(new Error("x"))
  .finally(() => console.log("cleanup"))
  .catch(e => console.log("caught", e.message));
```

<details><summary>Answer</summary>

`cleanup → 1 → caught x`
First microtask round: `finally` of chain 1 runs silently (returns 2, ignored), then chain 2's finally logs "cleanup". Chain 1's `.then` then logs `1`, then chain 2's `.catch` logs "caught x". (The exact interleaving is a detail — the key takeaways are: finally's return value is ignored, and the rejection passes through finally to catch.)

</details>

---

**Q10 — The big mixed one (interview favorite)**

```js
console.log("1");

setTimeout(() => console.log("2"), 0);

const p = new Promise(resolve => {
  console.log("3");
  resolve();
});

p.then(() => {
  console.log("4");
  setTimeout(() => console.log("5"), 0);
}).then(() => console.log("6"));

queueMicrotask(() => console.log("7"));

(async () => {
  console.log("8");
  await p;
  console.log("9");
})();

console.log("10");
```

<details><summary>Answer</summary>

`1 3 8 10 4 7 9 6 2 5`

- **Sync:** 1, 3 (executor), 8 (before await), 10.
- **Micro queue after sync:** [4, 7, 9]
- Run 4 → queues 6 at the back, schedules timer 5. Then 7, then 9, then 6.
- **Macro queue:** [2, 5] → 2, then 5.

</details>

---

**Q11 — Bonus / hard: returning a promise from `.then`**

```js
Promise.resolve()
  .then(() => { console.log(1); return Promise.resolve(2); })
  .then(v => console.log(v));

Promise.resolve()
  .then(() => console.log(3))
  .then(() => console.log(4))
  .then(() => console.log(5))
  .then(() => console.log(6));
```

<details><summary>Answer</summary>

`1 3 4 5 2 6`
Returning a promise (instead of a plain value) from `.then` costs **2 extra microtask ticks** before the outer promise adopts its value. Rare in interviews — if asked, the key line is: "returning a thenable adds extra microtask hops for unwrapping."

</details>

## Part 4: Real-World Async Problems

These come up in machine coding rounds and "how would you handle…" questions. Especially relevant for React.

### 21. Race Conditions

**What it is:** When multiple async operations run at once and the result depends on **which finishes first** — not the order you started them. In frontend, it almost always means: **an older request's response arrives after a newer one, and overwrites it.**

**Classic scenario — search box:**

```
User types "re"   → request A sent (slow, 800ms)
User types "rea"  → request B sent (fast, 200ms)
B returns → shows results for "rea" ✅
A returns → overwrites with results for "re" ❌ (UI shows wrong results)
```

**Mental model:** You asked two people for directions. The second person answered first, then the first person's (outdated) answer came in and you followed that one instead.

**Fixes (from simplest to best):**

1. Track the latest request and ignore anything older (next section).
2. Cancel the previous request with `AbortController` (section 23–24).
3. Debounce input to reduce the number of requests (reduces but does **not** eliminate the race).

---

### 22. Stale API Responses

**What it is:** The *result* of a race condition — a response that's no longer relevant (the user changed the input, the component unmounted, or the ID changed) but still gets applied to state.

**Fix 1 — Request ID / "latest wins" check (framework-agnostic):**

```js
let latestRequestId = 0;

async function search(query) {
  const requestId = ++latestRequestId;
  const results = await fetchResults(query);

  if (requestId !== latestRequestId) return; // a newer request started — ignore this one
  render(results);
}
```

**Fix 2 — The React `ignore` flag in useEffect cleanup (very common in interviews):**

```jsx
useEffect(() => {
  let ignore = false;

  fetchUser(userId).then(data => {
    if (!ignore) setUser(data); // only apply if this effect is still current
  });

  return () => {
    ignore = true; // runs when userId changes or component unmounts
  };
}, [userId]);
```

**Why it works:** Each effect run has its own `ignore` variable (closure!). When `userId` changes, React runs the old effect's cleanup → the old closure's `ignore` becomes `true` → its late response gets dropped.

**Interview line:** "Stale responses happen when an older request resolves after a newer one. I either track the latest request and ignore outdated ones, or cancel the old request with AbortController in the effect cleanup."

---

### 23. Request Cancellation

**What it is:** Actually stopping an in-flight request, not just ignoring its result.

**Why it's better than ignoring:**

- Saves bandwidth and server work.
- The browser can free the connection (browsers limit concurrent connections per domain).
- Cleaner: no "ghost" responses to guard against.

**When you need it:** Search-as-you-type, navigating away from a page, closing a modal that was loading data, component unmount, user clicking "Cancel" on an upload.

The standard tool is `AbortController`.

---

### 24. AbortController

**What it is:** A built-in browser API for cancelling async operations. Two parts:

- `controller` — the remote control. Call `controller.abort()` to cancel.
- `controller.signal` — you pass this to the operation (e.g., `fetch`) so it can listen for the cancel.

**What happens on abort:** The `fetch` promise **rejects with a `DOMException` named `"AbortError"`**. You should check for this and **not** treat it as a real error.

**Mental model:** The controller is a TV remote; the signal is the TV's receiver. Hand the receiver to `fetch`, keep the remote, press stop whenever you want.

```js
const controller = new AbortController();

fetch("/api/data", { signal: controller.signal })
  .then(res => res.json())
  .then(data => console.log(data))
  .catch(err => {
    if (err.name === "AbortError") {
      console.log("Request cancelled"); // expected — not a real error
    } else {
      console.error(err);
    }
  });

controller.abort(); // cancel it
```

**Search box with cancellation:**

```js
let controller = null;

async function search(query) {
  controller?.abort();              // cancel the previous request
  controller = new AbortController();

  try {
    const res = await fetch(`/api/search?q=${query}`, { signal: controller.signal });
    const data = await res.json();
    render(data);
  } catch (err) {
    if (err.name !== "AbortError") showError(err);
  }
}
```

**In React:**

```jsx
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/user/${userId}`, { signal: controller.signal })
    .then(res => res.json())
    .then(setUser)
    .catch(err => {
      if (err.name !== "AbortError") setError(err);
    });

  return () => controller.abort(); // cancel on userId change / unmount
}, [userId]);
```

> Note: A controller is **single-use** — once aborted, it stays aborted. Create a new one per request.
> Bonus: `AbortSignal.timeout(5000)` creates a signal that auto-aborts after 5s (rejects with a `"TimeoutError"`).

**Interview line:** "I create an AbortController per request, pass its signal to fetch, and call `abort()` in the cleanup — the fetch rejects with an AbortError, which I filter out from real errors."

### 25. Timeout

**What it is:** Failing a request if it takes too long, instead of letting the user wait forever. `fetch` has **no built-in timeout** option.

**Approach 1 — `Promise.race` with a timer:**

```js
function withTimeout(promise, ms) {
  let timerId;
  const timeout = new Promise((_, reject) => {
    timerId = setTimeout(() => reject(new Error("Timeout")), ms);
  });

  return Promise.race([promise, timeout])
    .finally(() => clearTimeout(timerId)); // don't leave the timer hanging
}

await withTimeout(fetch("/api"), 5000);
```

> ⚠️ Gotcha: `Promise.race` **doesn't cancel** the losing request — the fetch keeps running in the background. You only stop *waiting* for it.

**Approach 2 — AbortController (actually cancels the request):**

```js
async function fetchWithTimeout(url, ms) {
  const controller = new AbortController();
  const timerId = setTimeout(() => controller.abort(), ms);

  try {
    const res = await fetch(url, { signal: controller.signal });
    return res;
  } finally {
    clearTimeout(timerId);
  }
}

// Modern shortcut:
fetch(url, { signal: AbortSignal.timeout(5000) });
```

**Interview line:** "`Promise.race` with a timer gives up waiting but doesn't stop the request; AbortController with a timeout actually cancels it — that's the better choice for fetch."

### 26. Retry

**What it is:** Automatically re-trying a failed request, because many failures are temporary (network blip, server overloaded, 503).

**Best practice — exponential backoff:** Wait longer between each attempt (e.g., 500ms → 1s → 2s) so you don't hammer a struggling server.

**What NOT to retry:** 4xx client errors (400, 401, 404) — retrying won't fix a bad request. Retry network errors and 5xx/429.

```js
const sleep = ms => new Promise(resolve => setTimeout(resolve, ms));

async function fetchWithRetry(url, retries = 3, delay = 500) {
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      const res = await fetch(url);
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      return await res.json();
    } catch (err) {
      if (attempt === retries) throw err;      // out of retries — give up
      await sleep(delay * 2 ** attempt);        // 500, 1000, 2000...
    }
  }
}
```

**Recursive version (also common in interviews):**

```js
function retry(fn, retries = 3) {
  return fn().catch(err => {
    if (retries === 0) throw err;
    return retry(fn, retries - 1);
  });
}

retry(() => fetch("/api"));
```

> Note: pass a **function** (`() => fetch(...)`), not a promise — a promise has already started and can't be re-run.

**Interview line:** "Retry with exponential backoff, only for transient errors like network failures, 5xx, or 429 — never for 4xx — and cap the number of attempts."

### 27. Parallel vs Sequential Requests

**Sequential** — each request waits for the previous one. Total time = **sum** of all.
**Parallel** — all requests start together. Total time = **the slowest one**.

**Rule:** If requests are **independent**, run them in parallel. Only go sequential when a request **depends** on the previous result.

```js
// ❌ Sequential (accidentally slow) — ~3s if each takes 1s
const user = await fetchUser();
const posts = await fetchPosts();
const settings = await fetchSettings();

// ✅ Parallel — ~1s
const [user, posts, settings] = await Promise.all([
  fetchUser(),
  fetchPosts(),
  fetchSettings(),
]);

// ✅ Sequential when there's a real dependency
const user = await fetchUser();
const posts = await fetchPosts(user.id); // needs user.id
```

**Key insight:** A promise starts running the moment it's **created**, not when you `await` it. So this is also parallel:

```js
const userPromise = fetchUser();   // starts now
const postsPromise = fetchPosts(); // starts now
const user = await userPromise;
const posts = await postsPromise;
```

**The `forEach` trap (very common):**

```js
// ❌ forEach does NOT wait for async callbacks
ids.forEach(async id => {
  await deleteItem(id);
});
console.log("done"); // logs BEFORE anything is deleted

// ✅ Sequential — one at a time, in order
for (const id of ids) {
  await deleteItem(id);
}

// ✅ Parallel — all at once, wait for all
await Promise.all(ids.map(id => deleteItem(id)));
```

`forEach` ignores the promises your callback returns, so nothing awaits them.

**Middle ground — limited concurrency:** Firing 1000 requests at once in parallel can overload the browser/server. A **promise pool** runs at most N at a time (common machine coding question):

```js
async function runWithLimit(tasks, limit) {
  const results = [];
  let index = 0;

  async function worker() {
    while (index < tasks.length) {
      const current = index++;               // claim the next task
      results[current] = await tasks[current]();
    }
  }

  const workers = Array.from({ length: limit }, () => worker());
  await Promise.all(workers);
  return results;
}

// tasks = array of FUNCTIONS returning promises
await runWithLimit(urls.map(url => () => fetch(url)), 3);
```

Why `index++` is safe here: JS is single-threaded, so reading and incrementing `index` happens synchronously with no other worker running in between.

**Interview line:** "Independent requests go in parallel with `Promise.all`; dependent ones go sequential. Never use `forEach` with async — use `for...of` for sequential or `map` + `Promise.all` for parallel, and a pool when I need to limit concurrency."

### 28. Putting It Together — the "production-grade fetch"

If an interviewer asks "how would you make a robust data fetch," this is the checklist to talk through:

1. **Cancellation** — AbortController, abort on unmount / new request.
2. **Stale response guard** — latest-request check or abort.
3. **Timeout** — `AbortSignal.timeout` or a timer + abort.
4. **Retry** — exponential backoff for transient errors only.
5. **Error handling** — check `res.ok`, filter out `AbortError`, show user-friendly errors.
6. **Loading state** — set in `finally`.
7. **Parallelize** independent calls with `Promise.all` / `allSettled`.
