## Part 1: Equality & Type Coercion

### 1. `==` vs `===`

**What it is:** `===` (strict equality) compares value **and type** — no conversion. `==` (loose equality) **converts one or both sides** to a common type first, then compares.

**Mental model:** `===` asks "are these identical, no questions asked?" `==` asks "could these reasonably be made equal?" and tries to make them match before answering.

```js
1 === "1";  // false — different types, no conversion
1 == "1";   // true — "1" is converted to 1 first

null === undefined; // false — different types
null == undefined;  // true — special-cased to equal each other, and ONLY each other
```

**Interview line:** "Always use `===` in real code — `==`'s coercion rules are a common bug source. The one exception people allow is `x == null`, which cleanly checks for both `null` and `undefined` in one go."

---

### 2. Truthy / Falsy

**What it is:** Every value is truthy or falsy when used somewhere a boolean is expected (`if`, `&&`, `||`, `!!`).

**The complete falsy list — only 8 values, memorize all of them:**

```
false, 0, -0, 0n (BigInt zero), "", null, undefined, NaN
```

**Everything else is truthy** — including `"0"` (non-empty string), `[]` (empty array), `{}` (empty object), `" "` (space).

```js
if ("0") console.log("truthy!");   // runs — non-empty string
if ([]) console.log("truthy!");    // runs — objects are always truthy
if ({}) console.log("truthy!");    // runs
```

**Interview line:** "Only 8 falsy values in JS, and they're all primitives — every object and array, even empty ones, is truthy."

---

### 3. Coercion Rules — the ones interviewers actually test

**The core rule for `+`:** if **either** side is a string, `+` does **string concatenation**. Otherwise, it does numeric addition (converting both sides to numbers first).

```js
1 + "1";     // "11" — string wins
1 + 2 + "3"; // "33" — left to right: 1+2=3 (number), then 3+"3"="33"
"1" + 2 + 3; // "123" — "1"+2="12" (string), then "12"+3="123"
1 + true;    // 2 — true → 1 (no string involved, so numeric)
1 + null;    // 1 — null → 0
1 + undefined; // NaN — undefined → NaN
```

**Other operators (`-`, `*`, `/`) always convert to numbers** — there's no string-concatenation special case for them:

```js
"5" - 2;   // 3 — "5" converted to number
"5" * "2"; // 10
"abc" - 1; // NaN
```

**Array/object to primitive — trickier, asked to check real understanding:**

```js
[] + [];        // "" — both arrays → "" (empty string), concatenated
[] + {};        // "[object Object]" — [] → "", {} → "[object Object]"
{} + [];        // 0 (in a statement context — {} is parsed as an empty BLOCK, then +[] → +"" → 0)
[1, 2] + [3, 4]; // "1,23,4" — arrays → "1,2" and "3,4", then string concat
```

**Why arrays become strings:** an array's default conversion calls `.toString()`, which is `.join(",")`.

**Boolean conversion table (for `if`/`!!`):**

| Value                                                      | Boolean   |
| ---------------------------------------------------------- | --------- |
| `""`, `0`, `NaN`, `null`, `undefined`, `false` | `false` |
| `"0"`, `[]`, `{}`, any non-empty string              | `true`  |

**Interview line:** "`+` checks for a string on either side first — if there's one, it concatenates; otherwise everything is converted to a number. The other math operators always coerce to numbers."

---

### 4. Famous Coercion Gotchas (rapid-fire — predict these instantly)

```js
[] == false;        // true  — [] → "" → 0, false → 0, 0 == 0
"" == 0;             // true  — "" → 0
[] == "";            // true  — [] → ""
[] == ![];           // true  — ![] is false (arrays are truthy, ! flips it), then [] == false
NaN === NaN;          // false — NaN is never equal to anything, including itself
0.1 + 0.2 === 0.3;    // false — floating point precision (0.1+0.2 = 0.30000000000000004)
typeof NaN;           // "number" — NaN IS a number type, just an invalid one
typeof null;          // "object" — famous historical bug, never fixed (backwards compatibility)
null == undefined;    // true
null === undefined;   // false
[1] == 1;             // true  — [1] → "1" → 1
```

**How to check equality correctly for the tricky ones:**

```js
Number.isNaN(x);              // correct way to check for NaN
Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON; // correct float comparison
Object.is(NaN, NaN);          // true — Object.is fixes the NaN case (but NOT +0/-0... wait, it's the opposite)
Object.is(0, -0);             // false — Object.is treats +0 and -0 as different (unlike ===)
```

**`Object.is()` vs `===` — the two differences:**

```js
NaN === NaN;      // false
Object.is(NaN, NaN); // true

0 === -0;          // true
Object.is(0, -0);  // false
```

Everywhere else, they behave the same. `Object.is` is what React uses internally to compare state/props.

**Interview line:** "Most of these gotchas trace back to one rule: `==` converts non-primitives to primitives (arrays/objects → strings, mostly), then applies the same-type comparison. If I can explain the conversion step, I can predict the result — which is why I just use `===` and skip the guessing."

### 5. Quick Self-Check

Predict these before checking (answers immediately below, no peeking):

```js
console.log(1 < 2 < 3);      // ?
console.log(3 > 2 > 1);      // ?
console.log("5" + 3 - 2);    // ?
console.log(+"5" + +"3");    // ?
```

<details><summary>Answers</summary>

- `1 < 2 < 3` → `true` — evaluates left to right: `(1 < 2)` is `true`, then `true < 3` → `1 < 3` → `true`.
- `3 > 2 > 1` → `false` — `(3 > 2)` is `true`, then `true > 1` → `1 > 1` → `false`. (Classic trap!)
- `"5" + 3 - 2` → `51` → `"53" - 2` = `51` — `+` concatenates first (`"5"+3`="53"), then `-` converts back to number.
- `+"5" + +"3"` → `8` — unary `+` converts each string to a number first, so this is pure numeric addition.

</details>

## Part 2: Event Delegation

### 6. Event Bubbling & Capturing

**What it is:** When an event fires on an element, it doesn't just run handlers on that element — it travels through the DOM tree in phases:

1. **Capturing phase** — from `window` down to the target element.
2. **Target phase** — the event reaches the actual clicked element.
3. **Bubbling phase** — from the target back up to `window`. (This is the default phase handlers listen on.)

**Mental model:** Drop a pebble in a pond (capturing = the ripple travels inward first in some models, but simpler: think of shouting in a building). Bubbling is more intuitive: click a button inside a div inside body — the click event "bubbles up" like a bubble rising through water, triggering listeners on the button, then the div, then body, in that order.

```html
<div id="outer">
  <button id="inner">Click</button>
</div>
```

```js
outer.addEventListener("click", () => console.log("outer"));
inner.addEventListener("click", () => console.log("inner"));

// clicking the button logs: "inner" then "outer" (bubbling, the default)
```

**To listen during capturing instead of bubbling:** pass `true` (or `{ capture: true }`) as the third argument:

```js
outer.addEventListener("click", () => console.log("outer capture"), true);
// now "outer capture" logs BEFORE "inner"
```

**Interview line:** "Events capture down from the root, hit the target, then bubble back up — listeners default to the bubble phase, which is why a click on a child element also triggers its ancestors' click listeners."

---

### 7. `target` vs `currentTarget`, and `stopPropagation`

**`event.target`** — the actual element that triggered the event (where the user clicked).
**`event.currentTarget`** — the element the listener is **attached to** (changes based on which handler is running).

```js
outer.addEventListener("click", (e) => {
  console.log(e.target);         // <button id="inner"> — where you clicked
  console.log(e.currentTarget);  // <div id="outer"> — where THIS listener lives
});
```

**`stopPropagation()`** — stops the event from continuing to bubble (or capture) further.
**`stopImmediatePropagation()`** — also stops **other listeners on the same element** from running.
**`preventDefault()`** — stops the browser's default action (form submit, link navigation, checkbox toggle) — unrelated to propagation, often confused with it.

```js
inner.addEventListener("click", (e) => {
  e.stopPropagation(); // outer's click handler will NOT run
  console.log("inner only");
});
```

**Interview line:** "`target` is where the event started, `currentTarget` is where the currently-running handler is attached — they're the same only when you click the element the listener is directly on."

---

### 8. Event Delegation (the actual pattern)

**What it is:** Instead of attaching a listener to every child element, attach **one** listener to a common parent, and use `event.target` to figure out which child was actually clicked.

**Why it's better:**

1. **Performance** — one listener instead of hundreds (e.g., a list of 1000 items).
2. **Works on dynamically added elements** — no need to re-bind listeners when new children are added, because the listener lives on the parent, which already exists.

```js
// ❌ Without delegation — a listener per item, breaks for items added later
document.querySelectorAll(".item").forEach(item => {
  item.addEventListener("click", () => console.log("clicked", item.textContent));
});

// ✅ With delegation — one listener, works for future items too
document.getElementById("list").addEventListener("click", (e) => {
  const item = e.target.closest(".item"); // find the nearest .item ancestor (or itself)
  if (!item) return;                      // click landed outside any .item
  console.log("clicked", item.textContent);
});
```

**Why `.closest()` instead of checking `e.target` directly:** If the item contains nested elements (like an icon inside the button), `e.target` might be that icon, not the item itself. `.closest()` walks up from the target to find the matching ancestor.

**Real-world use cases:** a todo list (delete/complete buttons on each row), a table with row actions, an infinite-scroll feed, any list rendered from an API where items get added/removed dynamically.

**Interview line:** "Delegation puts one listener on a stable parent and reads `event.target` to identify which child was clicked — better for performance with long lists and automatically works for elements added after the listener was set up."

## Part 3: Design Patterns

**Why these get asked:** Interviewers want to see if you write code that scales past a single file — patterns are named solutions to recurring problems.

### 9. Module Pattern

**What it is:** Uses an IIFE (and closures) to create **private state** and expose only a public API — encapsulation before ES modules existed.

```js
const Counter = (function () {
  let count = 0; // private — not accessible from outside

  return {
    increment() { return ++count; },
    reset() { count = 0; },
    getCount() { return count; },
  };
})();

Counter.increment(); // 1
Counter.count;       // undefined — truly private, no way to reach it directly
```

**Mental model:** A vending machine — you interact with the buttons (public API), never directly with the internal mechanism (private state).

**Today:** ES modules (`import`/`export`) give you this natively — each module's top-level variables are private unless exported. The IIFE version still shows up in older codebases and bundler output.

---

### 10. Singleton Pattern

**What it is:** Ensures a class/object has **only one instance**, and provides a global point of access to it.

```js
class Database {
  static #instance; // private static field

  constructor() {
    if (Database.#instance) {
      return Database.#instance; // already exists → return the existing one
    }
    this.connection = "connected";
    Database.#instance = this;
  }
}

const db1 = new Database();
const db2 = new Database();
console.log(db1 === db2); // true — same instance
```

**Simpler version with a module (common in real apps — e.g., a shared API client or Redux store):**

```js
// apiClient.js
class ApiClient { /* ... setup ... */ }
export default new ApiClient(); // the module itself only runs once, so this IS a singleton
```

**Use cases:** a database connection, a global config object, a logging service, a Redux/Zustand store — anything where you want exactly one shared instance app-wide.

**Interview line:** "A singleton restricts a class to one instance — in JS, the simplest version is just exporting an already-created instance from a module, since modules are cached and only evaluated once."

---

### 11. Observer Pattern (a.k.a. Pub-Sub)

**What it is:** An object (the **subject**/**publisher**) maintains a list of dependents (**observers**/**subscribers**) and notifies them automatically when something changes — without the subject needing to know any details about them.

**Mental model:** A YouTube channel. You subscribe once; whenever the channel uploads, every subscriber gets notified automatically — the channel doesn't need to know who you are.

```js
class EventEmitter {
  #events = {};

  on(eventName, callback) {
    if (!this.#events[eventName]) this.#events[eventName] = [];
    this.#events[eventName].push(callback);
    return () => this.off(eventName, callback); // return an unsubscribe function
  }

  off(eventName, callback) {
    this.#events[eventName] = (this.#events[eventName] || []).filter(cb => cb !== callback);
  }

  emit(eventName, ...args) {
    (this.#events[eventName] || []).forEach(callback => callback(...args));
  }
}

const emitter = new EventEmitter();
const unsubscribe = emitter.on("userLoggedIn", (user) => console.log(`Welcome, ${user}`));
emitter.emit("userLoggedIn", "Saksham"); // "Welcome, Saksham"
unsubscribe(); // stop listening
```

**Where you already use this:** `addEventListener` IS the observer pattern. So is Node's `EventEmitter`. So is Redux (`store.subscribe`), and RxJS Observables are a more powerful version of the same idea.

**Interview line:** "Observer pattern decouples the thing that changes from the things that react to it — a subject holds a list of callbacks and calls all of them when an event happens. `addEventListener`, Redux's `subscribe`, and Node's `EventEmitter` are all this pattern."

---

### 12. Factory Pattern

**What it is:** A function that creates and returns objects, hiding the creation logic — used when object creation involves conditional logic or you want to avoid `new` scattered everywhere.

```js
function createUser(type, name) {
  if (type === "admin") {
    return { name, role: "admin", permissions: ["read", "write", "delete"] };
  }
  if (type === "guest") {
    return { name, role: "guest", permissions: ["read"] };
  }
  return { name, role: "user", permissions: ["read", "write"] };
}

const admin = createUser("admin", "Saksham");
```

**Mental model:** A restaurant kitchen — you order "pizza" (the type), and the kitchen (factory) handles all the steps to produce it. You never need to know the recipe.

**vs Constructor/Class:** A constructor always creates one specific type via `new`. A factory can decide **which** type of object to return based on input, and doesn't require `new` at all.

**Interview line:** "A factory function centralizes and hides object-creation logic — useful when the exact shape or type of object depends on some condition, instead of spreading `if/else` + `new` calls across the codebase."

---

### 13. Quick Reference — patterns in one table

| Pattern          | Solves                                  | JS example you already know               |
| ---------------- | --------------------------------------- | ----------------------------------------- |
| Module           | Private state, public API               | IIFE, ES modules                          |
| Singleton        | Exactly one shared instance             | `export default new Thing()`            |
| Observer/Pub-Sub | Decoupled reactions to change           | `addEventListener`, Redux, EventEmitter |
| Factory          | Conditional/centralized object creation | any`createX()` function                 |

## Part 4: Browser Observers

**Why these matter:** They're the modern, **performant** alternative to constantly polling (`setInterval`) or listening to noisy events (`scroll`, `resize`) to detect changes. All three follow the same shape: create an observer with a callback, tell it what to watch, and it calls you back **asynchronously** when something happens — off the main thread's critical path.

### 14. IntersectionObserver

**What it is:** Tells you when an element **enters or exits the viewport** (or another container) — without you having to calculate scroll positions by hand.

**Use cases:** lazy-loading images, infinite scroll ("load more" when the last item is visible), triggering animations when a section scrolls into view, ad visibility tracking.

```js
const observer = new IntersectionObserver(
  (entries) => {
    entries.forEach(entry => {
      if (entry.isIntersecting) {
        console.log("visible:", entry.target);
        loadImage(entry.target);
        observer.unobserve(entry.target); // stop watching once loaded — don't reload repeatedly
      }
    });
  },
  { threshold: 0.5 } // fire when 50% of the element is visible
);

document.querySelectorAll("img[data-src]").forEach(img => observer.observe(img));
```

**Why it beats a `scroll` listener:** `scroll` fires dozens of times a second and forces you to manually call `getBoundingClientRect()` (which is expensive — it forces layout recalculation). `IntersectionObserver` runs asynchronously and is handled efficiently by the browser itself.

**Interview line:** "IntersectionObserver reports visibility changes asynchronously without manual scroll-position math — it's the standard way to do lazy loading and infinite scroll without hurting scroll performance."

---

### 15. MutationObserver

**What it is:** Watches a DOM subtree and fires a callback when it changes — attributes added/removed, child nodes added/removed, text content changed.

**Use cases:** reacting to DOM changes made by a third-party script/widget you don't control, building dev tools, syncing a UI when something outside your framework's control mutates the DOM.

```js
const observer = new MutationObserver((mutations) => {
  mutations.forEach(mutation => {
    console.log(mutation.type, mutation.target); // "childList" / "attributes" / etc.
  });
});

observer.observe(document.getElementById("app"), {
  childList: true,   // watch for added/removed children
  attributes: true,  // watch for attribute changes
  subtree: true,     // watch descendants too, not just direct children
});

// later:
observer.disconnect(); // stop watching
```

**Interview line:** "MutationObserver reacts to DOM mutations asynchronously in a batch, rather than you polling `innerHTML` — mostly used for integrating with code outside your control, since in React/Vue apps you'd normally just react to state changes directly."

---

### 16. ResizeObserver

**What it is:** Fires when an **element's size** changes — not the window's size (that's the `resize` event on `window`), but any specific element, including ones resized by content changes, not just the user dragging the browser edge.

**Use cases:** responsive components that adapt based on their own container width (container queries before CSS had them), redrawing a canvas/chart when its wrapper resizes, resizable sidebars/panels.

```js
const observer = new ResizeObserver((entries) => {
  entries.forEach(entry => {
    const { width, height } = entry.contentRect;
    console.log(`New size: ${width}x${height}`);
    redrawChart(width, height);
  });
});

observer.observe(document.getElementById("chart-container"));
```

**Interview line:** "ResizeObserver watches a specific element's size, not just the window — essential for components like charts that need to redraw when their own container resizes, regardless of why (sidebar toggle, content change, window resize)."

---

### 17. Quick Reference — the three observers

| Observer                 | Watches                              | Typical use                                |
| ------------------------ | ------------------------------------ | ------------------------------------------ |
| `IntersectionObserver` | Element entering/leaving viewport    | Lazy load, infinite scroll                 |
| `MutationObserver`     | DOM tree changes (nodes, attributes) | React to external DOM mutations            |
| `ResizeObserver`       | An element's size                    | Responsive components, redrawing on resize |

**Common thread to mention:** "All three replace inefficient polling/scroll/resize-listener patterns with an async, browser-optimized callback — and all three need `.disconnect()` / `.unobserve()` in cleanup (e.g., a `useEffect` return) to avoid leaks."

## Part 5: Memory Leaks

### 18. Common JS Memory Leak Patterns

**The core idea (from JS Core's Garbage Collection topic):** anything still **reachable** from a root can't be garbage collected — even if you don't "need" it anymore. Leaks happen when references outlive their usefulness.

**1. Forgotten timers/intervals:**

```js
// ❌ If this component/page goes away, the interval — and everything it references — lives on
setInterval(() => updateUI(largeData), 1000);

// ✅ Always clear it
const id = setInterval(() => updateUI(largeData), 1000);
clearInterval(id); // when done (e.g., useEffect cleanup)
```

**2. Forgotten event listeners:**

```js
// ❌ element removed from DOM, but the listener (and its closure) is still referenced
window.addEventListener("resize", handleResize);

// ✅ remove it when no longer needed
window.removeEventListener("resize", handleResize);
```

In React, this is the #1 reason to return a cleanup function from `useEffect`.

**3. Detached DOM nodes:**

```js
// A node removed from the DOM but still referenced in JS stays in memory
let cachedNode = document.getElementById("item");
cachedNode.remove(); // removed from the page...
// ...but `cachedNode` still holds a reference — the whole node (and its children) leaks
cachedNode = null; // now it can actually be collected
```

**4. Closures accidentally holding large data:**

```js
function setup() {
  const hugeArray = new Array(1000000).fill("data");

  return function smallHandler() {
    console.log("click"); // doesn't use hugeArray at all...
  };
  // ...but if hugeArray were referenced anywhere in the returned function,
  // the whole array would be kept alive as long as smallHandler exists
}
```

The fix is usually just not capturing more than you need, or nulling out large references once done with them.

**5. Global variables (accidental):**

```js
function leak() {
  accidentalGlobal = "I'm on the window object forever"; // forgot `let`/`const`
}
```

Strict mode (from JS Core) throws on this instead of silently creating a global — one more reason to always use it.

**Interview line:** "Most JS leaks come down to a reference outliving its usefulness — a timer, a listener, or a detached DOM node still held onto by a variable or closure. The fix is almost always the same: clean up in the teardown path (`clearInterval`, `removeEventListener`, nulling references) — which is exactly what a `useEffect` cleanup function is for."

---

### 19. How to Detect a Leak (good to mention, rarely asked to demo)

- **Chrome DevTools → Memory tab** → take a heap snapshot, perform the suspected action a few times, take another snapshot, compare — objects that keep growing in count are the leak.
- **Performance tab** → record while repeating an action → look for a memory graph that keeps climbing and never drops after garbage collection runs.
- Look specifically for **detached DOM tree** entries in a heap snapshot — Chrome labels them exactly that.

## Part 6: WeakMap & WeakSet

### 20. WeakMap / WeakSet

**What it is:** Like `Map`/`Set`, but keys (WeakMap) or values (WeakSet) must be **objects**, and those references are **weak** — they don't prevent garbage collection. If nothing else references that object, it's collected, and its entry silently disappears from the WeakMap/WeakSet too.

**The key practical differences from `Map`/`Set`:**

- Not iterable — no `.keys()`, `.values()`, `.forEach()`, no `.size`. (Because entries can vanish at any moment due to GC, iterating wouldn't be reliable.)
- Only `.get()`, `.set()`, `.has()`, `.delete()` (WeakMap) or `.add()`, `.has()`, `.delete()` (WeakSet).
- Keys/values **must** be objects — `weakMap.set("string", x)` throws.

**Mental model:** A regular `Map` holding an object as a key is like gripping someone's hand tightly — you're keeping them from leaving (from being garbage collected) even if everyone else let go. A `WeakMap` is a light touch on the shoulder — if everyone else lets go, they can still walk away (get collected), and the WeakMap doesn't stop that or even notice.

```js
let user = { name: "Saksham" };
const map = new Map();
map.set(user, "some metadata");
user = null;
// `user` object is STILL in memory — the Map holds a strong reference → memory leak risk

let user2 = { name: "Saksham" };
const weakMap = new WeakMap();
weakMap.set(user2, "some metadata");
user2 = null;
// user2's object CAN be garbage collected — WeakMap doesn't keep it alive
```

**Real use cases:**

1. **Attaching private/extra data to an object without modifying it or causing a leak** — e.g., caching computed results per DOM node, where you want the cache entry to disappear automatically when the node is removed.
   ```js
   const domDataCache = new WeakMap();
   function processNode(node) {
     if (domDataCache.has(node)) return domDataCache.get(node);
     const result = expensiveComputation(node);
     domDataCache.set(node, result);
     return result;
   }
   // if `node` is later removed from the DOM and has no other references,
   // its cache entry is automatically cleaned up too — no manual bookkeeping
   ```
2. You already used this pattern for **circular reference tracking** in the deep-clone polyfill (Logic + Polyfills file) — the `WeakMap` there ensures cloned objects don't leak just because they were used as keys during cloning.
3. Tracking "private" data associated with class instances (a pattern from before private class fields `#` existed).

**Interview line:** "WeakMap/WeakSet hold weak references to object keys — entries don't prevent garbage collection and disappear automatically when nothing else references the key. That trade-off — no iteration, object-only keys — is exactly what makes them safe for caching data tied to an object's lifetime, like per-DOM-node metadata, without causing a leak."

## Part 7: Immutability

### 21. `Object.freeze` / `Object.seal`

**`Object.freeze(obj)`:**

- Prevents adding, removing, or **reassigning** any property.
- In non-strict mode, a failed write **fails silently**; in strict mode it **throws** a `TypeError`.
- **Shallow only** — nested objects inside a frozen object are still fully mutable.

```js
const config = Object.freeze({ apiUrl: "https://api.example.com", nested: { debug: true } });

config.apiUrl = "hacked";     // silently fails (or throws in strict mode)
console.log(config.apiUrl);   // unchanged

config.nested.debug = false;  // ✅ this WORKS — freeze doesn't go deep
console.log(config.nested.debug); // false — mutated!

console.log(Object.isFrozen(config)); // true
```

**`Object.seal(obj)`:** A lighter restriction — prevents adding/removing properties, but **existing properties can still be reassigned** (just not deleted).

```js
const sealed = Object.seal({ a: 1 });
sealed.a = 2;       // ✅ works — reassignment allowed
sealed.b = 3;       // ❌ fails — can't add new properties
delete sealed.a;    // ❌ fails — can't remove
```

**Deep freeze (the follow-up they usually ask for):**

```js
function deepFreeze(obj) {
  Object.getOwnPropertyNames(obj).forEach(key => {
    const value = obj[key];
    if (value !== null && typeof value === "object" && !Object.isFrozen(value)) {
      deepFreeze(value); // recurse into nested objects first
    }
  });
  return Object.freeze(obj);
}
```

**Comparison table:**

|                   | Add props | Remove props | Reassign existing | Mutate nested           |
| ----------------- | --------- | ------------ | ----------------- | ----------------------- |
| `Object.seal`   | ❌        | ❌           | ✅                | ✅                      |
| `Object.freeze` | ❌        | ❌           | ❌                | ✅ (unless deep-frozen) |

### 22. Why Immutability Matters for React

**The core reason:** React (and most state-management libraries) detect changes using **`Object.is` / shallow reference comparison**, not deep value comparison — that's what makes checking "did this change?" fast (O(1) instead of walking the whole object).

```js
// ❌ Mutating state directly — React can't detect this changed
state.user.name = "New Name";
setUser(state.user); // SAME reference as before → React sees no change → doesn't re-render

// ✅ Create a new object/reference
setUser({ ...state.user, name: "New Name" }); // new reference → React detects the change → re-renders
```

**This is exactly why:**

- `setState`/`useState` updates should always create new objects/arrays (spread, `.map`, `.filter` — never `.push`, direct index assignment, or nested mutation).
- `React.memo`, `useMemo`, `useCallback` all rely on this same shallow-reference check — which is also why a new `{}` or `() => {}` literal created fresh on every render breaks memoization even when the "content" is identical.
- Libraries like Immer exist specifically to let you *write* mutation-style code (`state.user.name = "New Name"`) while it produces a new immutable object underneath — best of both worlds.

**Interview line:** "React compares state by reference (`Object.is`), not deep value — so mutating an object in place and passing the same reference back means React can't tell anything changed. That's why all React state updates create new objects/arrays instead of mutating existing ones."
