# Part 1: Browser Architecture

The big picture first. Everything in this Part is one pipeline:

```
HTML  → DOM ─┐
              ├→ Render Tree → Layout → Paint → Composite → 🖥️ Pixels
CSS   → CSSOM ┘
```

## 1.1 Browser rendering process

**What it is:** The steps the browser takes to turn HTML/CSS/JS bytes into pixels on screen. Roughly: parse HTML → build DOM → parse CSS → build CSSOM → combine into render tree → layout → paint → composite.

**Mental model:** A restaurant kitchen. HTML is the order slip (what to make), CSS is the plating instructions (how it looks), and the render tree is the final plan the chef actually cooks from. Layout = deciding where each item sits on the plate, paint = making it, composite = assembling layers and sending it out.

**Why it matters:** Every performance question ("why is my page slow / janky?") maps to a stage in this pipeline. Knowing the stage tells you the fix.

```js
// Which stage does each line trigger?
el.style.width = "200px";      // Layout → Paint → Composite
el.style.color = "red";        // Paint → Composite (no layout)
el.style.transform = "scale(1.2)"; // Composite only (cheapest)
```

**Interview line:** *"The browser parses HTML into the DOM and CSS into the CSSOM, merges them into a render tree, then runs layout, paint and composite. Knowing which stage a change triggers tells me how expensive it is."*

## 1.2 DOM (Document Object Model)

**What it is:** An in-memory **tree of objects** representing the HTML document. The browser parses the HTML text and builds nodes (elements, text, comments). JS uses the DOM API to read and change the page.

**Mental model:** HTML is the blueprint on paper. The DOM is the actual 3D building you can walk into and rearrange.

**Why it matters:** The DOM is built **incrementally** as HTML streams in. A `<script>` without `async`/`defer` **blocks parsing** because JS might modify the DOM.

```js
const ul = document.querySelector("ul");
const li = document.createElement("li");
li.textContent = "New item";
ul.appendChild(li);   // DOM changed → browser may need to re-layout / repaint
```

⚠️ **Gotcha:** DOM ≠ page source. "View source" shows the original HTML; DevTools "Elements" shows the *live DOM* after JS ran. Also, the DOM includes things the HTML doesn't (e.g., auto-inserted `<tbody>`).

⚠️ **Gotcha:** `defer` = download in parallel, run after parsing, in order. `async` = run as soon as downloaded, any order.

**Interview line:** *"The DOM is the browser's live, in-memory tree representation of the HTML. JS manipulates it, and scripts can block DOM construction unless they use async or defer."*

## 1.3 CSSOM (CSS Object Model)

**What it is:** A tree of all the CSS rules and computed styles, built from stylesheets (external, `<style>`, inline). It decides what style each element ends up with (cascade + specificity + inheritance).

**Mental model:** The DOM is *what* is on the page; the CSSOM is the *style guide* saying how each thing should look.

**Why it matters:** CSS is **render-blocking**. The browser won't paint until the CSSOM is ready (otherwise you'd see a flash of unstyled content). CSS also **blocks JS execution** that comes after it, since JS might query styles.

```html
<!-- Blocks rendering until downloaded & parsed -->
<link rel="stylesheet" href="styles.css" />

<!-- Non-blocking trick for non-critical CSS -->
<link rel="stylesheet" href="print.css" media="print" />
```

⚠️ **Gotcha:** Unlike the DOM, the CSSOM can't be built incrementally in a useful way, because later rules can override earlier ones. The browser needs the whole thing.

**Interview line:** *"The CSSOM is the tree of parsed style rules. CSS is render-blocking, so I keep critical CSS small and defer the rest."*

## 1.4 Render tree

**What it is:** DOM + CSSOM combined, containing **only what's visible**, each node with its computed styles.

**Mental model:** The DOM is the full guest list; the render tree is only the guests who actually showed up to the party.

**Key differences from the DOM:**

- `display: none` elements are **not** in the render tree.
- `visibility: hidden` elements **are** (they take up space, just invisible).
- Non-visual nodes (`<head>`, `<script>`, `<meta>`) are excluded.
- Pseudo-elements (`::before`, `::after`) **are** included even though they aren't in the DOM.

```css
.a { display: none; }        /* removed from render tree, no space */
.b { visibility: hidden; }   /* in render tree, space reserved, not painted */
.c { opacity: 0; }           /* in render tree, painted invisible, still clickable! */
```

**Interview line:** *"The render tree is the DOM merged with the CSSOM, minus invisible nodes like display:none. It's what layout and paint actually work from."*

## 1.5 Critical rendering path (CRP)

**What it is:** The minimum sequence of steps needed to get the **first pixels** on screen: HTML → DOM, CSS → CSSOM, → render tree → layout → paint. "Optimizing the CRP" = making that first render happen faster.

**Mental model:** The shortest route to the airport. Anything on the route that blocks traffic (big CSS files, sync scripts) delays your arrival.

**How to optimize (the "why" behind each):**

- **Minimize critical resources**: fewer blocking files means less waiting.
- **Inline small critical CSS**, load the rest async, so the first paint doesn't wait on a big stylesheet.
- **`defer` / `async` scripts**, so JS doesn't block HTML parsing.
- **Preload key assets** (`<link rel="preload">`), so the browser fetches fonts/hero images early.
- **Reduce bytes**: minify, compress (gzip/brotli), code-split.

```html
<link rel="preload" href="/font.woff2" as="font" crossorigin />
<script src="/app.js" defer></script>
```

⚠️ **Gotcha:** Related metrics: **FCP** (first content painted), **LCP** (largest element painted), **TTI/INP** (interactivity). CRP mostly improves FCP/LCP.

**Interview line:** *"The critical rendering path is the sequence from bytes to first pixels. I optimize it by shrinking and deferring render-blocking CSS and JS, and preloading what's critical."*

## 1.6 Layout (a.k.a. Reflow)

**What it is:** The stage where the browser calculates the **exact size and position** of every element in the render tree, based on the viewport, box model, and CSS (flex, grid, floats…).

**Mental model:** An architect measuring the floor plan: how wide is each room, and where does each wall go?

**Why it matters:** Layout is expensive because elements affect each other. Changing one element's size can push its siblings and children around (a cascade). Layout runs on the first load and *again* whenever geometry changes.

**Triggers:** changing `width`, `height`, `margin`, `padding`, `font-size`, `display`, `position`; adding/removing DOM nodes; resizing the window.

**Interview line:** *"Layout computes the geometry of every element. It's costly because one change can ripple through the tree, so I avoid unnecessary geometry changes."*

## 1.7 Paint

**What it is:** Filling in pixels: colors, text, borders, shadows, images. The browser records draw instructions per element (in stacking order) and rasterizes them.

**Mental model:** The painter now colors in the floor plan the architect drew.

**Triggers (without layout):** `color`, `background`, `box-shadow`, `border-radius`, `outline`, `visibility`.

⚠️ **Gotcha:** Paint can be expensive for big areas, gradients, blurs, and shadows. DevTools → Rendering → "Paint flashing" highlights repainted regions.

**Interview line:** *"Paint fills in the visual details like colors and shadows. It's cheaper than layout but still costly for large or complex areas."*

## 1.8 Composite

**What it is:** The browser splits the page into **layers**, rasterizes each separately, then the **GPU stacks them together** in the right order to make the final image.

**Mental model:** Transparent sheets stacked on a projector. You can slide one sheet around without redrawing the others.

**Why it matters:** Because layers are already drawn, moving/fading/scaling a layer needs **only compositing**, skipping layout and paint. That's why `transform` and `opacity` animations are smooth.

```css
.box {
  transition: transform 0.3s;
  will-change: transform;   /* hint: promote to its own layer */
}
.box:hover { transform: translateX(100px); }  /* composite-only */
```

**Interview line:** *"Compositing stacks pre-painted layers on the GPU. Transform and opacity changes only need compositing, which is why they're the smoothest properties to animate."*

# Part 2: Performance

## 2.1 Reflow

**What it is:** Same as **layout**, re-run. The browser recalculates geometry because something changed the size or position of elements.

**Mental model:** Move one piece of furniture and you may need to re-arrange the whole room.

**Why it matters:** A reflow **always** leads to a repaint after. It's the most expensive of the common operations, and it can cascade to children, siblings and ancestors.

**Common triggers:** changing dimensions/margins/fonts, adding/removing elements, changing window size, and **reading layout properties** (see layout thrashing).

**Interview line:** *"Reflow recalculates element geometry. It's expensive and always followed by repaint, so I batch DOM changes and prefer transform-based animations."*

## 2.2 Repaint

**What it is:** Redrawing pixels when visual style changes but geometry doesn't (color, background, shadow, visibility).

**Mental model:** Repainting a wall a new color without moving the wall.

**Rule of thumb:** `Reflow ⊃ Repaint`. Every reflow causes a repaint, but a repaint doesn't need a reflow.

| Change                                    | Layout | Paint | Composite |
| ----------------------------------------- | ------ | ----- | --------- |
| `width`, `margin`, `top`            | ✅     | ✅    | ✅        |
| `color`, `background`, `box-shadow` | ❌     | ✅    | ✅        |
| `transform`, `opacity`                | ❌     | ❌    | ✅        |

**Interview line:** *"Repaint redraws visuals without changing geometry. It's cheaper than reflow, and transform/opacity skip both."*

## 2.3 Layout thrashing

**What it is:** Repeatedly **mixing DOM reads and writes** in a loop, forcing the browser to recalculate layout again and again (a "forced synchronous layout").

**Mental model:** A waiter who takes one order, runs to the kitchen, returns, takes the next order, runs back... instead of collecting all orders first.

**Why it happens:** Writing to styles marks layout as "dirty". Then reading something like `offsetHeight` forces the browser to flush pending changes and recalculate *right now* to give you an accurate answer. In a loop, that's N layouts instead of 1.

```js
// ❌ Thrashing: read → write → read → write ...
items.forEach(el => {
  const h = el.offsetHeight;        // READ (forces layout)
  el.style.height = h + 10 + "px";  // WRITE (invalidates layout)
});

// ✅ Batch: all reads first, then all writes
const heights = items.map(el => el.offsetHeight);           // READS
items.forEach((el, i) => el.style.height = heights[i] + 10 + "px"); // WRITES
```

⚠️ **Gotcha:** Properties that force layout when read: `offsetWidth/Height`, `clientWidth/Height`, `scrollTop`, `getBoundingClientRect()`, `getComputedStyle()`.

**Interview line:** *"Layout thrashing is interleaving DOM reads and writes so the browser re-runs layout each iteration. I fix it by batching all reads before all writes, or scheduling writes in requestAnimationFrame."*

## 2.4 GPU compositing

**What it is:** Offloading certain visual work (moving, scaling, rotating, fading) to the **GPU** by promoting elements to their own **compositor layers**. The GPU is great at transforming textures fast, without asking the main thread.

**Mental model:** Instead of repainting a painting every time you move it, you put the painting on a cart and just push the cart.

**Why it matters:** Composite-only animations run on the **compositor thread**, so they stay smooth even if the main thread (JS) is busy.

**How to get it:** `transform` and `opacity` (auto-promoted while animating), or hint with `will-change`.

```css
.card { will-change: transform; }          /* hint */
.card.slide { transform: translateX(200px); }
```

⚠️ **Gotcha:** Don't spam `will-change` / `translateZ(0)`. Every layer costs GPU memory. Too many layers = worse performance, especially on mobile.

**Interview line:** *"GPU compositing moves animated elements to their own layers so transform and opacity changes skip layout and paint and run off the main thread. I use it sparingly since layers cost memory."*

## 2.5 `requestAnimationFrame`

**What it is:** `requestAnimationFrame(cb)` asks the browser to run `cb` **right before the next repaint** (usually 60 times/sec, synced to the display refresh).

**Mental model:** Instead of shouting updates whenever you feel like it (`setTimeout`), you wait for the bus (the next frame) and board together.

**Why it matters:**

- Syncs work with the browser's render cycle, so no wasted or torn frames.
- **Pauses in background tabs**, saving CPU/battery.
- Great place to do batched DOM *writes* (avoids thrashing).

```js
function animate(timestamp) {
  el.style.transform = `translateX(${(timestamp / 10) % 300}px)`;
  requestAnimationFrame(animate);   // schedule next frame
}
const id = requestAnimationFrame(animate);
// cancelAnimationFrame(id);  // to stop
```

```js
// Throttle scroll handler to once per frame
let ticking = false;
window.addEventListener("scroll", () => {
  if (!ticking) {
    requestAnimationFrame(() => { updateUI(); ticking = false; });
    ticking = true;
  }
});
```

⚠️ **Gotcha:** rAF callbacks run **before paint**, not after. Also, it's not a timer: don't use it for logic that must run at exact intervals.

**Interview line:** *"requestAnimationFrame runs my callback just before the next repaint, keeping animations in sync with the display and pausing in background tabs. It's the right tool for animations and batched DOM writes."*

# Part 3: Events

## 3.1 Event propagation

**What it is:** When an event fires on an element, it doesn't just hit that element. It **travels through the DOM** in three phases: **capturing → target → bubbling**.

**Mental model:** A message delivered in an office building. It goes *down* from the lobby (window) to the person's desk (target), and then *back up* through every floor.

```
window → document → html → body → div → button   (1. capturing ↓)
                                        button   (2. target)
button → div → body → html → document → window   (3. bubbling ↑)
```

**Why it matters:** This is what lets a parent react to a child's click, and it's the basis of event delegation.

**Interview line:** *"Events propagate in three phases: capture from the root down to the target, the target phase, then bubble back up. Listeners fire during bubbling by default."*

## 3.2 Capturing

**What it is:** The **downward** phase, from `window` to the target's parent. Listeners run here only if registered with `capture: true`.

**Mental model:** Security checking you at each door on the way *in*.

```js
parent.addEventListener("click", () => console.log("parent capture"), true);
// same as { capture: true }
```

**Use cases:** intercepting events before they reach children, and events that don't bubble (e.g., `focus`, `blur` can be captured).

**Interview line:** *"Capturing is the top-down phase. It's opt-in via the capture flag and useful for intercepting events early or handling non-bubbling ones like focus."*

## 3.3 Target

**What it is:** The phase where the event reaches the **element that actually triggered it** (`event.target`).

**Key distinction:**

- `event.target` = the element that **triggered** the event (deepest clicked element).
- `event.currentTarget` = the element the **listener is attached to**.

```js
ul.addEventListener("click", (e) => {
  console.log(e.target);        // the <li> (or <span> inside it) you clicked
  console.log(e.currentTarget); // always the <ul>
});
```

⚠️ **Gotcha:** If a `<li>` contains a `<span>` and you click the span, `e.target` is the span, not the li. Use `e.target.closest("li")` in delegation.

**Interview line:** *"target is the element where the event originated, while currentTarget is the element the handler is attached to. They differ whenever an event bubbles."*

## 3.4 Bubbling

**What it is:** The **upward** phase, from the target back up to `window`. **Default** for `addEventListener` (capture = false).

**Mental model:** A bubble rising through water, touching every layer on the way up.

```js
outer.addEventListener("click", () => console.log("outer"));
inner.addEventListener("click", () => console.log("inner"));
// click inner → logs: inner, then outer
```

⚠️ **Gotcha:** Some events **don't bubble**: `focus`, `blur`, `mouseenter`, `mouseleave`, `load`. Use `focusin`/`focusout` or `mouseover`/`mouseout` if you need bubbling versions.

**Interview line:** *"Bubbling sends the event from the target up through its ancestors. It's the default phase for listeners, though some events like focus and mouseenter don't bubble."*

## 3.5 Event delegation

**What it is:** Attaching **one listener on a parent** instead of many on children, then using `event.target` to figure out which child was clicked. Works *because* of bubbling.

**Mental model:** One receptionist at the front desk instead of a doorbell on every apartment.

**Why it's useful:**

- **Less memory**: 1 listener vs. 1000.
- **Works for dynamic elements** added later, with no need to re-attach listeners.
- Simpler cleanup.

```js
document.querySelector("#list").addEventListener("click", (e) => {
  const item = e.target.closest("li[data-id]");
  if (!item) return;                // click wasn't on an item
  console.log("Clicked item", item.dataset.id);
});
```

⚠️ **Gotcha:** Doesn't work for events that don't bubble. Also, if any child calls `stopPropagation()`, the parent never hears about it.

**Interview line:** *"Event delegation puts a single listener on a parent and uses event.target to identify the child. It saves memory and handles dynamically added elements, thanks to bubbling."*

## 3.6 `preventDefault`

**What it is:** Cancels the browser's **default action** for an event (following a link, submitting a form, checkbox toggling) **without** stopping propagation.

**Mental model:** The message still travels, but you cancel the action it was going to trigger.

```js
form.addEventListener("submit", (e) => {
  e.preventDefault();          // stop page reload
  sendWithFetch(new FormData(form));
});

link.addEventListener("click", (e) => e.preventDefault()); // link won't navigate
```

⚠️ **Gotcha:** On **passive** listeners (`{ passive: true }`, default for `touchstart`/`wheel` on many browsers), `preventDefault()` is ignored. Passive listeners promise the browser you won't cancel scrolling, which lets it scroll smoothly without waiting on your JS.

**Interview line:** *"preventDefault stops the browser's built-in behavior, like form submission or link navigation, but the event still propagates."*

## 3.7 `stopPropagation`

**What it is:** Stops the event from continuing to **other elements** in the propagation path. Other listeners on the *same* element still run. `stopImmediatePropagation()` also blocks those.

**Mental model:** Closing the door behind the message so no one further along hears it.

```js
child.addEventListener("click", (e) => {
  e.stopPropagation();     // parent's click listener won't fire
});
```

| Method                                  | Stops propagation?            | Stops default action? |
| --------------------------------------- | ----------------------------- | --------------------- |
| `preventDefault()`                    | ❌                            | ✅                    |
| `stopPropagation()`                   | ✅                            | ❌                    |
| `stopImmediatePropagation()`          | ✅ (+ same-element listeners) | ❌                    |
| `return false` (in `onclick=` attr) | ✅                            | ✅                    |

⚠️ **Gotcha:** Overusing `stopPropagation` is a code smell. It breaks delegation, analytics, and "click outside to close" logic elsewhere in the app. Prefer checking `e.target` instead.

**Interview line:** *"stopPropagation prevents the event from reaching other elements in the path, while preventDefault only cancels the default action. They're independent, and I avoid stopPropagation unless necessary since it breaks delegation."*

# Part 4: Storage

## 4.1 LocalStorage

**What it is:** Key-value string storage that **persists** across tabs and browser restarts until cleared. ~5 MB per origin. **Synchronous**.

**Mental model:** A sticky note on your fridge. It stays until you remove it, and anyone in the house (same origin) can read it.

```js
localStorage.setItem("theme", "dark");
localStorage.getItem("theme");          // "dark"
localStorage.setItem("user", JSON.stringify({ id: 1 })); // objects need stringify
JSON.parse(localStorage.getItem("user"));
localStorage.removeItem("theme");
```

⚠️ **Gotchas:**

- Only **strings**. Objects become `"[object Object]"` unless you `JSON.stringify`.
- **Synchronous** = blocks the main thread. Don't store huge data.
- **Not secure**: any JS on the page (including XSS attacks) can read it. Don't store tokens here if you can avoid it.
- Not available in Web Workers. Shared across tabs (`storage` event notifies other tabs).

**Interview line:** *"localStorage is persistent, synchronous, origin-scoped string storage of about 5MB. It's fine for preferences, but not for sensitive data since any script can read it."*

## 4.2 SessionStorage

**What it is:** Same API as localStorage, but scoped to **one tab** and cleared when the tab closes.

**Mental model:** A whiteboard in a meeting room. Wiped when the meeting (tab) ends, and other rooms (tabs) can't see it.

```js
sessionStorage.setItem("draft", "Hello");
```

**Use cases:** multi-step form state, temporary UI state per tab.

⚠️ **Gotcha:** Survives a page **refresh** but not closing the tab. Opening the same site in a new tab gives a *fresh* sessionStorage.

**Interview line:** *"sessionStorage is like localStorage but per-tab and cleared when the tab closes. It's good for temporary, tab-specific state."*

## 4.3 Cookies

**What it is:** Small (~4KB) key-value data the **server can set** and the browser **automatically sends with every request** to that domain.

**Mental model:** A wristband at a festival. Staff (server) put it on you, and you show it at every gate (request) automatically.

```js
document.cookie = "theme=dark; max-age=3600; path=/; Secure; SameSite=Lax";
```

```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Strict; Max-Age=3600
```

**Important attributes (know these!):**

| Attribute                 | What it does                                                                         |
| ------------------------- | ------------------------------------------------------------------------------------ |
| `HttpOnly`              | JS**cannot** read it, which protects against XSS theft                         |
| `Secure`                | Sent over HTTPS only                                                                 |
| `SameSite`              | `Strict`/`Lax`/`None` controls cross-site sending, so it protects against CSRF |
| `Max-Age` / `Expires` | Lifetime. Without it, it's a*session cookie*                                       |
| `Domain` / `Path`     | Scope of where it's sent                                                             |

⚠️ **Gotcha:** Cookies add weight to **every request**, so keep them small. `SameSite=None` requires `Secure`.

**Interview line:** *"Cookies are small pieces of data the browser automatically attaches to requests. For auth, I'd use HttpOnly, Secure and SameSite flags so scripts can't read them and cross-site requests are limited."*

## 4.4 IndexedDB (basics)

**What it is:** A low-level, **asynchronous**, transactional **NoSQL database** in the browser. Stores large amounts of structured data (objects, files, blobs), with indexes and queries.

**Mental model:** localStorage is a sticky note; IndexedDB is a filing cabinet with folders and an index.

```js
const req = indexedDB.open("myDB", 1);
req.onupgradeneeded = () => {
  req.result.createObjectStore("users", { keyPath: "id" });
};
req.onsuccess = () => {
  const db = req.result;
  const tx = db.transaction("users", "readwrite");
  tx.objectStore("users").put({ id: 1, name: "Saksham" });
};
```

**Use cases:** offline-first apps, caching large API data, PWAs. In practice people use wrappers like **idb** or **Dexie**, since the raw API is callback-heavy.

⚠️ **Gotcha:** It's async and event/promise-based, and available in workers. Storage is much larger (hundreds of MB+, subject to browser quota).

**Interview line:** *"IndexedDB is an async, transactional, in-browser NoSQL store for large structured data. I'd use it for offline support or big caches, usually through a wrapper like idb."*

## 4.5 Storage comparison (memorize this table)

|                    | localStorage  | sessionStorage | Cookies              | IndexedDB           |
| ------------------ | ------------- | -------------- | -------------------- | ------------------- |
| Capacity           | ~5MB          | ~5MB           | ~4KB                 | Large (quota-based) |
| Lifetime           | Until cleared | Tab session    | Set by expiry        | Until cleared       |
| Sent to server     | ❌            | ❌             | ✅ every request     | ❌                  |
| Sync / Async       | Sync          | Sync           | Sync                 | **Async**     |
| Accessible from JS | ✅            | ✅             | ✅ (unless HttpOnly) | ✅                  |
| Data type          | Strings       | Strings        | Strings              | Almost anything     |

# Part 5: Networking

## 5.1 HTTP

**What it is:** **HyperText Transfer Protocol.** The request/response protocol of the web. The client sends a request; the server sends back a response. It's **stateless**, so each request is independent (state is added via cookies/tokens).

**Mental model:** Ordering at a counter. You place an order (request), you get your food (response), and the cashier doesn't remember you next time unless you show a loyalty card (cookie/token).

```http
GET /api/users/1 HTTP/1.1
Host: example.com
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{"id":1,"name":"Saksham"}
```

**Versions in one glance:**

- **HTTP/1.1**: one request per connection at a time (head-of-line blocking), so browsers open ~6 parallel connections.
- **HTTP/2**: **multiplexing** (many requests over one connection), header compression.
- **HTTP/3**: runs over **QUIC (UDP)**, faster connection setup, fixes transport-level head-of-line blocking.
- **HTTPS** = HTTP over TLS (encrypted).

**Interview line:** *"HTTP is a stateless request-response protocol. HTTP/2 adds multiplexing over one connection, and HTTP/3 moves to QUIC for faster, more resilient connections."*

## 5.2 HTTP methods

| Method      | Purpose                             | Safe? | Idempotent?            | Has body? |
| ----------- | ----------------------------------- | ----- | ---------------------- | --------- |
| `GET`     | Read a resource                     | ✅    | ✅                     | No        |
| `POST`    | Create / trigger action             | ❌    | ❌                     | Yes       |
| `PUT`     | **Replace** a resource fully  | ❌    | ✅                     | Yes       |
| `PATCH`   | **Partially** update          | ❌    | Usually not guaranteed | Yes       |
| `DELETE`  | Remove                              | ❌    | ✅                     | Optional  |
| `HEAD`    | Like GET, headers only              | ✅    | ✅                     | No        |
| `OPTIONS` | Ask what's allowed (CORS preflight) | ✅    | ✅                     | No        |

- **Safe** = doesn't change server state.
- **Idempotent** = calling it N times has the same effect as calling it once.

**Why idempotency matters:** It's what makes **retries safe**. Retrying a failed `PUT` is fine; retrying a `POST` might create duplicates.

```js
await fetch("/api/users/1", {
  method: "PATCH",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "New Name" }),
});
```

⚠️ **Gotcha:** `PUT` vs `PATCH` is a classic question. PUT replaces the *whole* resource; PATCH changes only the fields you send.

**Interview line:** *"GET reads, POST creates, PUT replaces, PATCH partially updates, DELETE removes. Safe means no side effects, idempotent means repeat calls have the same result, which matters for retries."*

## 5.3 Status codes

| Range         | Meaning       | Must-know codes                                                                                                                                     |
| ------------- | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1xx** | Informational | `101 Switching Protocols` (WebSocket upgrade)                                                                                                     |
| **2xx** | Success       | `200 OK`, `201 Created`, `204 No Content`                                                                                                     |
| **3xx** | Redirect      | `301 Moved Permanently`, `302 Found`, `304 Not Modified`                                                                                      |
| **4xx** | Client error  | `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict`, `422 Unprocessable`, `429 Too Many Requests` |
| **5xx** | Server error  | `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`                                            |

⚠️ **Gotchas (very commonly asked):**

- **401 vs 403**: 401 = "who are you?" (not authenticated). 403 = "I know who you are, but you're not allowed" (not authorized).
- **`fetch` does NOT reject on 4xx/5xx!** It only rejects on network failure. Always check `res.ok`.
- **301 vs 302**: permanent (cached, SEO-transfer) vs temporary.

```js
const res = await fetch("/api/data");
if (!res.ok) throw new Error(`HTTP ${res.status}`);  // must do this yourself
const data = await res.json();
```

**Interview line:** *"2xx is success, 3xx redirects, 4xx is the client's fault, 5xx is the server's. 401 means unauthenticated, 403 means forbidden, and fetch only rejects on network errors, so I check res.ok."*

## 5.4 Headers

**What it is:** Metadata key-value pairs on requests and responses that describe the body, the client, caching, auth, and more.

**Mental model:** The label and shipping info on a parcel, separate from what's inside the box.

| Category              | Examples                                                                                      |
| --------------------- | --------------------------------------------------------------------------------------------- |
| **Content**     | `Content-Type`, `Content-Length`, `Content-Encoding`                                    |
| **Auth**        | `Authorization: Bearer <token>`, `Cookie`, `Set-Cookie`                                 |
| **Caching**     | `Cache-Control`, `ETag`, `If-None-Match`, `Last-Modified`, `Expires`                |
| **CORS**        | `Origin`, `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`                 |
| **Negotiation** | `Accept`, `Accept-Language`, `Accept-Encoding`                                          |
| **Security**    | `Content-Security-Policy`, `Strict-Transport-Security` (HSTS), `X-Content-Type-Options` |

⚠️ **Gotcha:** Sending `Content-Type: application/json` on a cross-origin request makes it "non-simple" and triggers a **preflight** (see CORS).

**Interview line:** *"Headers carry metadata such as content type, auth credentials, caching rules, and CORS permissions. They separate 'how to handle this' from the actual payload."*

## 5.5 REST

**What it is:** **Representational State Transfer**, an architectural *style* for APIs where you model things as **resources** (nouns) identified by URLs, and use HTTP methods as the verbs.

**Mental model:** A library. Each book (resource) has a fixed shelf address (URL), and you use standard actions (borrow, return, add) instead of inventing new ones per book.

**Principles:**

- **Resource-based URLs**: `/users/42/orders` (nouns, not `/getUserOrders`)
- **Standard HTTP methods** and status codes
- **Stateless**: each request contains everything needed
- **Uniform interface**, and often JSON as the representation
- Cacheable, layered

```
GET    /users          → list users
GET    /users/42       → get one
POST   /users          → create
PUT    /users/42       → replace
PATCH  /users/42       → partial update
DELETE /users/42       → delete
```

⚠️ **Gotcha:** REST ≠ "any JSON API over HTTP". Also know the trade-off vs GraphQL: REST can **over-fetch/under-fetch** and need multiple round trips, while GraphQL lets the client ask for exactly what it needs.

**Interview line:** *"REST models data as resources at URLs and uses standard HTTP verbs and status codes, statelessly. It's simple and cacheable, but can over-fetch compared to something like GraphQL."*

## 5.6 CORS

**What it is:** **Cross-Origin Resource Sharing.** A browser mechanism that lets a server say which **other origins** may read its responses. It relaxes the **Same-Origin Policy**.

**Origin** = protocol + domain + port. `https://a.com` ≠ `http://a.com` ≠ `https://a.com:8080` ≠ `https://api.a.com`.

**Mental model:** A club with a guest list. The browser is the bouncer who checks the server's list ("Access-Control-Allow-Origin") before letting your JS see what came back.

```http
# Request from https://app.com
Origin: https://app.com

# Server response
Access-Control-Allow-Origin: https://app.com
Access-Control-Allow-Credentials: true
```

**Why it exists:** Without it, any malicious site could use *your* logged-in cookies to read data from your bank's API.

⚠️ **Gotchas (interviewers love these):**

- CORS is enforced by the **browser**, not the server. `curl`/Postman ignore it. The request often *reaches* the server; the browser just blocks your JS from reading the response.
- It's a **server-side fix**. You can't fix CORS from frontend code (only a dev proxy helps during development).
- With credentials (`credentials: "include"`), the server **cannot** use `*`. It must name the exact origin and send `Allow-Credentials: true`.

**Interview line:** *"CORS is a browser-enforced mechanism where the server whitelists which origins can read its responses, relaxing the same-origin policy. The fix lives on the server, via Access-Control-Allow-Origin headers."*

## 5.7 Preflight

**What it is:** An automatic **`OPTIONS` request** the browser sends *before* the real request, to ask the server "will you accept this cross-origin request?"

**When it triggers ("non-simple" requests):**

- Methods other than `GET`/`HEAD`/`POST` (e.g., `PUT`, `DELETE`, `PATCH`)
- Custom headers (e.g., `Authorization`)
- `Content-Type` other than `text/plain`, `application/x-www-form-urlencoded`, `multipart/form-data` (so **`application/json` triggers it**)

**Mental model:** Calling ahead to ask "are you open, and can I bring my dog?" before driving over.

```http
OPTIONS /api/data
Origin: https://app.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: authorization, content-type

← 204 No Content
Access-Control-Allow-Origin: https://app.com
Access-Control-Allow-Methods: GET, PUT, POST
Access-Control-Allow-Headers: authorization, content-type
Access-Control-Max-Age: 86400   ← cache the preflight result for a day
```

⚠️ **Gotcha:** Preflights add a **round trip**. `Access-Control-Max-Age` caches the result. A common bug is the server not handling `OPTIONS` at all, so the real request never fires.

**Interview line:** *"Preflight is an automatic OPTIONS request the browser sends before non-simple cross-origin requests, for example JSON bodies, custom headers or PUT/DELETE, to check the server allows them. Max-Age lets the result be cached."*

## 5.8 Cookies (in networking context)

Covered in [Part 4](#4-3-cookies), but the networking angle:

- The browser attaches cookies **automatically** to matching requests. That's convenient, and it's exactly why **CSRF** exists (a malicious site triggers a request and your cookie rides along).
- Cross-origin requests **don't send cookies by default**. You need `credentials: "include"` on the client and `Allow-Credentials: true` on the server.
- `SameSite` is the main defense against CSRF.

```js
fetch("https://api.example.com/me", { credentials: "include" });
```

**Interview line:** *"Cookies are auto-attached to requests, so I protect them with HttpOnly, Secure and SameSite, and cross-origin calls need credentials: include plus matching server CORS headers."*

## 5.9 Authentication

**What it is:** Proving **who you are** (authentication) vs. proving **what you can do** (authorization).

**Common approaches:**

| Approach                   | How it works                                                             | Trade-off                                                          |
| -------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| **Session + cookie** | Server stores session, gives browser a session ID cookie                 | Server-side state, easy to revoke, simple and secure with HttpOnly |
| **Token (JWT)**      | Server issues a signed token, client sends it in`Authorization` header | Stateless, scales well, harder to revoke                           |
| **OAuth 2.0 / OIDC** | Delegated login ("Sign in with Google") using access tokens              | Great UX, more moving parts                                        |

**Mental model:** Session = a coat-check ticket (server holds your coat). JWT = a signed passport (you carry all the info, and the border checks the signature).

**Where to store tokens on the client (common debate):**

- `localStorage`: easy but readable by any XSS script.
- **HttpOnly cookie**: JS can't read it, so it's safer against XSS, but you need CSRF protection (SameSite).
- Common secure pattern: **short-lived access token + refresh token in an HttpOnly cookie**.

⚠️ **Gotcha:** "Authentication vs authorization" and "401 vs 403" are frequently paired questions.

**Interview line:** *"Authentication verifies identity, authorization checks permissions. I can use server sessions with cookies or stateless tokens like JWT, and I prefer HttpOnly cookies for storage to reduce XSS exposure."*

## 5.10 JWT basics

**What it is:** **JSON Web Token**, a compact, **signed** token with three Base64URL parts: `header.payload.signature`.

```
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxMjMiLCJleHAiOjE3MDAwMDAwMDB9 . SflKxwRJSMeKKF2QT4f...
   header (alg/type)        payload (claims)                            signature
```

- **Header**: algorithm + type.
- **Payload**: claims like `sub` (user id), `exp` (expiry), `iat` (issued at), roles.
- **Signature**: signs header+payload with a secret/private key, so the server can detect tampering.

**Mental model:** A tamper-evident sealed envelope. Anyone can *read* the letter, but no one can change it without breaking the seal.

```js
// Client sends it on each request
fetch("/api/profile", {
  headers: { Authorization: `Bearer ${accessToken}` },
});

// Decode payload (NOT verify) on the frontend
const payload = JSON.parse(atob(token.split(".")[1]));
```

⚠️ **Gotchas:**

- **JWT is encoded, NOT encrypted.** Never put secrets in the payload.
- Only the **server** can *verify* the signature. The frontend just decodes it (e.g., to read `exp`).
- **Hard to revoke** before expiry (it's stateless), so keep access tokens short-lived and use refresh tokens.
- Always check `exp`, and don't trust the `alg: none` header (server should enforce the algorithm).

**Interview line:** *"A JWT is a signed token with header, payload and signature. It's encoded, not encrypted, so no secrets in it. The server verifies the signature statelessly, and I keep access tokens short-lived with a refresh flow."*

## 5.11 HTTP caching

**What it is:** Reusing previously fetched responses (in the browser or CDN) instead of hitting the server again. Two ideas: **freshness** (can I reuse it without asking?) and **validation** (is my copy still good?).

**Mental model:** Milk in your fridge. If it's within the date (fresh), just use it. If it's past the date, check with the shop ("still good?") before throwing it away or buying new.

**1. Freshness: `Cache-Control`**

```http
Cache-Control: max-age=31536000, immutable   # cache 1 year, never revalidate
Cache-Control: no-cache                      # can store, but MUST revalidate first
Cache-Control: no-store                      # never store (sensitive data)
Cache-Control: private                       # browser only, not shared CDNs
Cache-Control: public                        # CDNs may cache too
```

**2. Validation: `ETag` / `Last-Modified`**

```http
# First response
ETag: "abc123"

# Later request (browser asks: has it changed?)
If-None-Match: "abc123"

# Server: unchanged → tiny response, saves bandwidth
304 Not Modified
```

**Best-practice strategy:**

- **Hashed static assets** (`app.a1b2c3.js`): `max-age=1y, immutable`. The filename changes on every build, so it's a safe cache-bust.
- **HTML**: `no-cache` (always revalidate) so users get new asset links.
- **API data**: short `max-age` or `no-cache` + ETag.

⚠️ **Gotchas:**

- **`no-cache` ≠ "don't cache"**. It means "cache, but revalidate." `no-store` is the real "don't cache."
- A `304` still costs a round trip, but skips the body.
- `stale-while-revalidate` serves stale content instantly while refreshing in the background. Good for perceived speed.

**Interview line:** *"HTTP caching uses Cache-Control for freshness and ETag/Last-Modified for revalidation with 304s. I give hashed assets a long max-age, keep HTML on no-cache, and remember no-cache still stores while no-store doesn't."*

# Part 6: Real-time

**The core question:** *How does the server tell the client something without the client asking every time?* Four answers, from simplest to most powerful.

## 6.1 Polling

**What it is:** The client **repeatedly asks** the server for updates on a timer.

- **Short polling**: request every N seconds; the server replies immediately (even if nothing changed).
- **Long polling**: the server **holds the request open** until there's new data (or a timeout), then the client immediately asks again.

**Mental model:** Short polling = kids in the back seat asking "are we there yet?" every 30 seconds. Long polling = asking once and the driver only answers when you've actually arrived.

```js
// Short polling
setInterval(async () => {
  const res = await fetch("/api/status");
  render(await res.json());
}, 5000);

// Long polling
async function longPoll() {
  try {
    const res = await fetch("/api/updates?since=" + lastId);
    handle(await res.json());
  } finally {
    longPoll();   // immediately reconnect
  }
}
```

**Trade-offs:** Simple, works everywhere, and plain HTTP. But **wasteful** (empty responses), delayed updates (short polling), and heavy on server connections (long polling).

**Interview line:** *"Polling means the client repeatedly asks for updates. Short polling is simple but wasteful, and long polling holds the request open until data arrives, cutting latency at the cost of held connections."*

## 6.2 SSE (Server-Sent Events)

**What it is:** A **one-way** (server → client) persistent HTTP connection where the server **streams events** as they happen. Uses the built-in `EventSource` API.

**Mental model:** A radio broadcast. You tune in, and the station keeps sending, but you can't talk back on the same channel.

```js
const es = new EventSource("/api/stream");

es.onmessage = (e) => console.log("update:", e.data);
es.addEventListener("price", (e) => updatePrice(JSON.parse(e.data)));
es.onerror = () => console.log("connection issue, auto-reconnecting...");
// es.close();
```

```
# Server sends text/event-stream
HTTP/1.1 200 OK
Content-Type: text/event-stream

event: price
data: {"symbol":"AAPL","value":190.5}

```

**Strengths:**

- **Auto-reconnect** built in, with `Last-Event-ID` for resuming.
- Plain HTTP, works with proxies/HTTP2, simple to implement.
- Text-based.

**Limits:** One-way only (send data to the server via normal `fetch`). Text only (no binary). HTTP/1.1 has a ~6 connections per domain limit across tabs (HTTP/2 fixes this).

**Use cases:** live feeds, notifications, dashboards, streaming logs, **AI token streaming**.

**Interview line:** *"SSE is a one-way server-to-client stream over plain HTTP with built-in reconnection through EventSource. It's ideal for notifications, live feeds, and streaming responses when the client doesn't need to send data back on the same channel."*

## 6.3 WebSockets

**What it is:** A **full-duplex, persistent, two-way** connection between client and server over a single TCP connection. It starts as an HTTP request and **upgrades** to the WebSocket protocol (`ws://` / `wss://`).

**Mental model:** A phone call. Both sides can talk any time, and the line stays open. (HTTP is more like sending letters.)

```js
const ws = new WebSocket("wss://example.com/chat");

ws.onopen    = () => ws.send(JSON.stringify({ type: "join", room: "general" }));
ws.onmessage = (e) => console.log("got:", JSON.parse(e.data));
ws.onerror   = (err) => console.error("error", err);
ws.onclose   = (e) => console.log("closed", e.code, e.reason);
```

**Strengths:** Very low latency, low overhead per message (tiny frames, no HTTP headers each time), supports **text and binary**, both directions.

**Limits:**

- No auto-reconnect. **You build it** (with backoff).
- Stateful connections are harder to scale (sticky sessions / pub-sub like Redis).
- Doesn't get HTTP caching, and some proxies/firewalls interfere.
- Need heartbeats to detect dead connections.

**Use cases:** chat, multiplayer games, collaborative editing, live trading, anything needing frequent two-way messages.

**Interview line:** *"WebSockets give a persistent, full-duplex connection after an HTTP upgrade handshake. They're great for low-latency two-way communication like chat, but I have to handle reconnection, heartbeats, and scaling myself."*

## 6.4 WebSocket lifecycle

**What it is:** The stages a connection goes through, both as a protocol and as `readyState` values.

```
1. HTTP Upgrade handshake
   Client → GET /chat, Upgrade: websocket, Sec-WebSocket-Key: ...
   Server → 101 Switching Protocols

2. OPEN      → bidirectional messages flow (frames)
3. CLOSING   → one side sends a close frame
4. CLOSED    → connection terminated
```

| `readyState` | Constant       | Meaning                  |
| -------------- | -------------- | ------------------------ |
| `0`          | `CONNECTING` | Handshake in progress    |
| `1`          | `OPEN`       | Ready to send/receive    |
| `2`          | `CLOSING`    | Close handshake started  |
| `3`          | `CLOSED`     | Closed or failed to open |

**Events:** `onopen` → `onmessage` (many) → `onerror` → `onclose`.

**Production-grade pattern: reconnect with exponential backoff + heartbeat**

```js
function connect(retries = 0) {
  const ws = new WebSocket("wss://example.com/ws");
  let heartbeat;

  ws.onopen = () => {
    retries = 0;
    heartbeat = setInterval(() => {
      if (ws.readyState === WebSocket.OPEN) ws.send('{"type":"ping"}');
    }, 25000);
  };

  ws.onclose = () => {
    clearInterval(heartbeat);
    const delay = Math.min(1000 * 2 ** retries, 30000);   // 1s, 2s, 4s ... cap 30s
    setTimeout(() => connect(retries + 1), delay + Math.random() * 500); // jitter
  };
}
```

⚠️ **Gotchas:**

- Always check `readyState === OPEN` before `send()`, or it throws / drops.
- `101` is the status that confirms the upgrade.
- **Backoff + jitter** prevents a "thundering herd" when the server comes back and thousands of clients reconnect at once.
- Close codes: `1000` normal, `1001` going away, `1006` abnormal (no close frame, e.g., network dropped).
- Clean up on unmount (in React, close the socket in the `useEffect` cleanup).

**Interview line:** *"A WebSocket starts with an HTTP upgrade that returns 101, moves through CONNECTING, OPEN, CLOSING and CLOSED, and I handle reconnection with exponential backoff and jitter plus heartbeats to detect dead connections."*

## 6.5 Real-time comparison (quick decision table)

|                | Short polling             | Long polling            | SSE                                | WebSocket                  |
| -------------- | ------------------------- | ----------------------- | ---------------------------------- | -------------------------- |
| Direction      | Client → server          | Client → server (held) | Server → client                   | **Both**             |
| Connection     | New each time             | Re-opened each time     | One persistent                     | One persistent             |
| Latency        | High                      | Medium                  | Low                                | **Lowest**           |
| Auto-reconnect | N/A                       | Manual                  | ✅ Built-in                        | ❌ Manual                  |
| Binary data    | ✅                        | ✅                      | ❌                                 | ✅                         |
| Complexity     | Lowest                    | Low                     | Low                                | Highest                    |
| Best for       | Simple, infrequent checks | Fallback                | Feeds, notifications, AI streaming | Chat, games, collaboration |

**How to choose (say this in interviews):**

- Need **two-way, frequent** messages → **WebSocket**.
- Only **server pushes** updates → **SSE** (simpler than WS).
- Infrequent or constrained environment → **polling**.
