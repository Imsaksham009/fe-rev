## Part 1: Type Checking

### 1. `typeof` vs `instanceof` vs `Array.isArray` vs `Object.prototype.toString.call`

**Why there are four ways:** none of the simple ones alone is fully reliable — each has a specific blind spot.

**`typeof`** — fast, but very coarse:

```js
typeof 42;          // "number"
typeof "hi";         // "string"
typeof true;         // "boolean"
typeof undefined;    // "undefined"
typeof Symbol();     // "symbol"
typeof 10n;          // "bigint"
typeof function(){}; // "function"

typeof [];       // "object" — arrays are NOT distinguished!
typeof {};       // "object"
typeof null;     // "object" — famous historical bug (JS Core file)
typeof new Date(); // "object"
```

**Use `typeof` for:** primitives and checking if something is a function. **Don't use it for:** telling objects, arrays, null, and dates apart from each other.

**`instanceof`** — checks whether `constructor.prototype` appears anywhere in the value's prototype chain:

```js
[] instanceof Array;   // true
[] instanceof Object;  // true — arrays are also objects (Array.prototype's own prototype is Object.prototype)
{} instanceof Array;   // false
```

> ⚠️ Gotcha: `instanceof` breaks across **realms** (different iframes, or different Node `vm` contexts) — each has its **own** `Array` constructor, so an array from one iframe is `instanceof` its own iframe's `Array`, but not the other's. Rare in interviews, but a great "I know the edge cases" answer.

**`Array.isArray(x)`** — purpose-built, and correctly handles the realm problem above. **Always use this over `instanceof Array`** for checking arrays specifically.

**`Object.prototype.toString.call(x)`** — the most reliable, universal type check. Returns a `"[object Type]"` string and correctly distinguishes everything:

```js
Object.prototype.toString.call([]);        // "[object Array]"
Object.prototype.toString.call({});        // "[object Object]"
Object.prototype.toString.call(null);      // "[object Null]"
Object.prototype.toString.call(undefined); // "[object Undefined]"
Object.prototype.toString.call(new Date()); // "[object Date]"
Object.prototype.toString.call(/regex/);   // "[object RegExp]"
```

**Why `.call()` is needed:** `toString` normally runs on the object you call it on — `.call(x)` forces it to run **as if `this` were `x`**, borrowing the base `Object.prototype` version instead of an overridden one (arrays have their own `.toString()` that just joins elements).

**Interview line:** "`typeof` is fine for primitives and functions but can't tell objects/arrays/null apart; `Array.isArray` is the correct array check; and `Object.prototype.toString.call(x)` is the one method that reliably identifies everything, including `null` and `Date`, because it's borrowing the base implementation instead of any overridden one."

### 2. Quick Reference Table

| Check                | `[]`               | `{}`                | `null`            | `function(){}`        | `new Date()`      |
| -------------------- | -------------------- | --------------------- | ------------------- | ----------------------- | ------------------- |
| `typeof`           | `"object"`         | `"object"`          | `"object"`        | `"function"`          | `"object"`        |
| `instanceof Array` | `true`             | `false`             | throws*             | `false`               | `false`           |
| `Array.isArray`    | `true`             | `false`             | `false`           | `false`               | `false`           |
| `toString.call`    | `"[object Array]"` | `"[object Object]"` | `"[object Null]"` | `"[object Function]"` | `"[object Date]"` |

*`null instanceof Array` doesn't throw — it returns `false`. (`instanceof` only throws if the right-hand side isn't callable/has no `.prototype`.)

## Part 2: Storage — localStorage, sessionStorage, Cookies

### 3. The Three, Side by Side

|                                    | `localStorage`                                                           | `sessionStorage`                        | Cookies                                                           |
| ---------------------------------- | -------------------------------------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------- |
| **Capacity**                 | ~5–10MB                                                                   | ~5–10MB                                  | ~4KB                                                              |
| **Persistence**              | Until explicitly cleared                                                   | Until the**tab** closes             | Configurable expiry (`Max-Age`/`Expires`)                     |
| **Scope**                    | Per-origin, shared across all tabs                                         | Per-origin**and** per-tab           | Per-domain (+ path), can include subdomains                       |
| **Sent with HTTP requests?** | No — JS-only                                                              | No — JS-only                             | **Yes** — automatically attached to every matching request |
| **Accessible via JS?**       | Yes                                                                        | Yes                                       | Yes,**unless** `HttpOnly` flag is set                     |
| **Typical use**              | User preferences, theme, cached data, tokens (with tradeoffs — see below) | Per-tab temporary state (multi-step form) | Auth/session tokens, server-side session ID                       |

**Why "sent with every request" matters:** it's a hidden cost — every cookie for a domain rides along with every request to it (images, API calls, everything), adding overhead. It's also the mechanism behind **CSRF** attacks, which is why cookies used for auth need `SameSite` and `Secure` flags.

**Why `HttpOnly` matters for security:** an `HttpOnly` cookie **cannot be read by JavaScript at all** — this is the standard defense against **XSS** attacks stealing an auth token, since even injected malicious JS can't access it. `localStorage` has no equivalent protection — anything with script execution on your page can read it.

```js
localStorage.setItem("theme", "dark");
localStorage.getItem("theme");   // "dark"
localStorage.removeItem("theme");
localStorage.clear();            // wipes everything for this origin

sessionStorage.setItem("draftId", "123"); // gone when the tab closes

document.cookie = "token=abc123; Max-Age=3600; Secure; SameSite=Strict";
// HttpOnly cookies can ONLY be set by the server (Set-Cookie response header), never by document.cookie
```

**Interview line — the one they're really testing:** "For auth tokens, I'd lean towards an `HttpOnly` cookie over `localStorage`, because `localStorage` is readable by any script on the page — including an injected one from an XSS attack — while `HttpOnly` cookies aren't accessible to JavaScript at all."

---

### 4. Storage Events (bonus — used for cross-tab sync)

**What it is:** The `storage` event fires on **other tabs** (not the one that made the change) when `localStorage` changes — useful for syncing state across open tabs (e.g., logging out everywhere when you log out in one tab).

```js
window.addEventListener("storage", (e) => {
  console.log(e.key, e.oldValue, e.newValue); // fires in OTHER tabs, not the one that wrote
});
```

## Part 3: Error Handling Patterns

### 5. Custom Error Classes

**Why bother:** a plain `throw new Error("...")` loses information — you can't tell *what kind* of error it was without parsing the message string. Custom error classes let you `instanceof`-check and attach structured data.

```js
class ValidationError extends Error {
  constructor(message, field) {
    super(message);              // sets this.message
    this.name = "ValidationError"; // shows up in stack traces / console.error
    this.field = field;           // extra structured data
  }
}

try {
  throw new ValidationError("Email is invalid", "email");
} catch (e) {
  if (e instanceof ValidationError) {
    console.log(`${e.field}: ${e.message}`); // "email: Email is invalid"
  } else {
    throw e; // re-throw anything we didn't expect
  }
}
```

**Why `extends Error` and calling `super(message)`:** this keeps `e.message`, `e.stack`, and `e instanceof Error` all working correctly — you're building on top of the real error mechanism, not replacing it.

---

### 6. `Error.cause` (ES2022)

**What it is:** Lets you chain a new, more specific error to the original low-level one, without losing the original — useful when a high-level operation fails because a low-level one did, and you want both messages available.

```js
try {
  JSON.parse("{ bad json");
} catch (originalError) {
  throw new Error("Failed to load config", { cause: originalError });
}

// Later, whoever catches it:
try {
  // ...
} catch (e) {
  console.log(e.message);       // "Failed to load config"
  console.log(e.cause.message); // the original JSON parse error
}
```

**Interview line:** "`Error.cause` lets me wrap a lower-level error in a more meaningful, higher-level one without losing the original stack trace and message — useful for debugging where a generic 'failed to fetch' actually came from a specific network timeout."

---

### 7. When to Use Custom Errors vs Plain Errors

**Rule of thumb:** if calling code needs to **behave differently** based on the error type (retry on a `NetworkError`, show a specific field error on a `ValidationError`, redirect on an `AuthError`), use a custom class. If it's a one-off internal failure nobody needs to distinguish, a plain `Error` with a clear message is enough — don't over-engineer it.

## Part 4: Regex Basics

**Mindset for interviews:** you're rarely asked to write a "perfect" production regex (email validation is famously never fully correct with regex alone) — you're asked to show you know the methods and can write something reasonable under time pressure.

### 8. The Methods

| Method                      | Called on | Returns          | Notes                                                                                      |
| --------------------------- | --------- | ---------------- | ------------------------------------------------------------------------------------------ |
| `regex.test(str)`         | RegExp    | `boolean`      | Fastest — use when you just need yes/no                                                   |
| `str.match(regex)`        | String    | Array or`null` | Without`/g`: first match + capture groups. With `/g`: all matches, no groups           |
| `str.matchAll(regex)`     | String    | Iterator         | All matches**with** capture groups — regex **must** have `/g`               |
| `regex.exec(str)`         | RegExp    | Array or`null` | With`/g`, is **stateful** — repeated calls step through matches via `lastIndex` |
| `str.replace(regex, ...)` | String    | New string       | Covered in the Built-in Methods file                                                       |

```js
/\d+/.test("abc123"); // true

"a1b2c3".match(/\d/g); // ["1", "2", "3"] — all matches, flat array, no groups

[..."a1b2c3".matchAll(/[a-z](\d)/g)].map(m => m[1]); // ["1", "2", "3"] — group 1 from each match
```

**Interview line:** "`test` for a quick boolean, `match`/`matchAll` when I need the actual matched text or capture groups — `matchAll` specifically when I need groups from *every* match, since plain `match` with `/g` throws groups away."

---

### 9. Common Patterns Worth Having Memorized

```js
/^\S+@\S+\.\S+$/         // simple email check (good enough for interviews — real validation is far messier)
/^\d+$/                  // only digits
/^[a-zA-Z]+$/             // only letters
/\s+/                    // one or more whitespace characters
/^https?:\/\//            // starts with http:// or https://
/[^a-zA-Z0-9]/g           // anything that's NOT alphanumeric (useful for the palindrome-cleaning problem in the Logic file)
```

**Cheat sheet for symbols:**

| Symbol        | Means                                          |
| ------------- | ---------------------------------------------- |
| `\d`        | digit`[0-9]`                                 |
| `\w`        | word character`[a-zA-Z0-9_]`                 |
| `\s`        | whitespace                                     |
| `+`         | one or more                                    |
| `*`         | zero or more                                   |
| `?`         | zero or one (optional)                         |
| `^` / `$` | start / end of string                          |
| `[^...]`    | NOT any of these characters                    |
| `/g`        | global — find all matches, not just the first |
| `/i`        | case-insensitive                               |

---

### 10. Quick Practical Example — validate & extract in one

```js
function extractHashtags(text) {
  return [...text.matchAll(/#(\w+)/g)].map(match => match[1]);
}
extractHashtags("Loving #JavaScript and #WebDev today!"); // ["JavaScript", "WebDev"]
```

## Part 5: Proxy & Reflect (bonus)

**Where this fits:** less commonly asked than everything above, but shows up at the 2–4 YOE level as a "have you seen this" question, or in system-design-flavored FE rounds ("how would you build a reactive state library").

### 11. Proxy & Reflect

**What it is:** `Proxy` lets you **intercept** fundamental operations on an object — reading a property, writing one, checking `in`, deleting — by wrapping it with a `handler` of **trap** functions. `Reflect` is a companion object with methods that mirror those same operations, used **inside** traps to perform the "default" behavior after your custom logic runs.

**Mental model:** A Proxy is a front desk in front of the real object. Every request (get/set/delete) goes through the front desk first, which can log it, block it, or modify it, before (optionally) forwarding it to the real object behind.

```js
const target = { name: "Saksham", age: 25 };

const handler = {
  get(obj, prop) {
    console.log(`Reading "${prop}"`);
    return Reflect.get(obj, prop); // forward to the real, default behavior
  },
  set(obj, prop, value) {
    if (prop === "age" && typeof value !== "number") {
      throw new TypeError("age must be a number");
    }
    return Reflect.set(obj, prop, value); // forward the actual assignment
  },
};

const person = new Proxy(target, handler);

console.log(person.name);  // logs "Reading name", then "Saksham"
person.age = 26;           // works
person.age = "old";        // throws TypeError — caught by the set trap
```

**Why use `Reflect` instead of just doing `obj[prop] = value` directly in the trap?** For simple cases they're equivalent, but `Reflect` methods are designed to correctly forward `this` and edge cases (like inherited proxies) — using `Reflect` inside traps is the recommended, safer default.

**Real-world use cases:**

- **Validation** — as above, rejecting invalid writes.
- **Reactivity systems** — Vue 3's reactivity is built on `Proxy` (it replaced `Object.defineProperty`, which couldn't detect new property additions or array index changes).
- **Logging/debugging** — trace every read/write to an object during development.
- **Default values** — a `get` trap that returns a fallback instead of `undefined` for missing keys.

**Interview line:** "A Proxy wraps an object and intercepts operations like get/set through trap functions, forwarding the default behavior via `Reflect` — it's how Vue 3 implemented its reactivity system, replacing the older `Object.defineProperty` approach which couldn't catch new properties being added."
