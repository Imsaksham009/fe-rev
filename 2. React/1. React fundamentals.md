## Part 1: React Fundamentals

### 1. JSX

**What it is:** JSX is a syntax extension for JavaScript that lets you write HTML-like markup inside JS files. It's not HTML — it compiles (via Babel) into `React.createElement(...)` calls that produce plain JS objects describing the UI.

**Why it exists:** Before JSX, UI was built with nested, imperative `createElement` calls or string templates — both hard to visualize at a glance. JSX keeps the markup and the logic that drives it in one place, so the two can't silently drift out of sync.

**Mental model:** JSX is sugar. `<div className="a">{name}</div>` really means `React.createElement('div', {className: 'a'}, name)` — written to look like HTML so it's easier for your brain to parse, nothing more.

```jsx
const element = <h1 className="title">Hello, {user.name}</h1>;

// compiles to (roughly):
const element = React.createElement(
  'h1',
  { className: 'title' },
  'Hello, ',
  user.name
);
```

**Interview line:** "JSX is syntactic sugar over `React.createElement` — it lets us describe UI declaratively, and the compiler turns it into plain JS objects that React can work with."

> ⚠️ Gotcha: A JSX expression must return a *single* root element (or a Fragment `<>...</>`). Also, `class` becomes `className` and `for` becomes `htmlFor` — JSX attributes are camelCase JS, not raw HTML.

---

### 2. Components

**What it is:** A component is a reusable, self-contained function (or class) that takes inputs (`props`) and returns JSX describing what should appear on screen. Function components are the standard today.

**Why it exists:** UIs are naturally made of repeating, nested pieces — buttons, cards, forms. Components let you build a piece once and reuse it everywhere, while React manages each instance's own state and lifecycle independently.

**Mental model:** Components are like recipes in a cookbook — each one takes ingredients (props) and produces a dish (JSX). A whole page is just several recipes combined and nested.

```jsx
function Greeting({ name }) {
  return <h1>Hello, {name}!</h1>;
}

function App() {
  return <Greeting name="Saksham" />;
}
```

**Interview line:** "A component is just a function that returns JSX — React calls it, gets back a description of UI, and renders that to the DOM."

> ⚠️ Gotcha: Component names must start with a capital letter. `<greeting />` (lowercase) is treated as an unknown HTML tag, not your component, and fails silently or renders nothing.

---

### 3. Props

**What it is:** Props ("properties") are the inputs passed into a component from its parent — read-only data that configures how that component renders.

**Why it exists:** Components need a way to receive data from outside themselves without reaching into global state. Props make data flow explicit and one-directional (parent → child), which is what makes a React tree predictable to trace and debug.

**Mental model:** Props are function arguments. The component doesn't choose its props any more than a function chooses the arguments it's called with — the caller (parent) decides.

```jsx
function Button({ label, onClick }) {
  return <button onClick={onClick}>{label}</button>;
}

<Button label="Save" onClick={() => console.log('saved')} />;
```

**Interview line:** "Props are read-only inputs a parent passes down to configure a child — a component should never mutate its own props."

> ⚠️ Gotcha: Props are immutable from the child's side. If a value needs to change over time from *within* the component, that value belongs in state, not props.

---

### 4. State

**What it is:** State is data a component owns and manages internally, that can change over time, and whose change causes the component to re-render (typically via `useState` or `useReducer`).

**Why it exists:** Not everything a component needs comes from outside — a component often has to remember things between renders (an input's current value, whether a modal is open). State is React's built-in mechanism for that memory.

**Mental model:** State is a component's own private notebook. Nothing outside the component can write in it directly — and every time the component writes something new, it re-reads the notebook and redraws itself accordingly.

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

**Interview line:** "State is local, mutable-over-time data owned by a component — updating it schedules a re-render so the UI reflects the new value."

> ⚠️ Gotcha: State updates are asynchronous and batched. Reading the state variable immediately after calling its setter still gives you the *old* value — the update only applies on the next render.

---

### 5. Rendering

**What it is:** Rendering is React calling your component function to figure out what the UI *should* look like — producing a tree of React elements (often called the virtual DOM), which React then diffs against the previous tree to decide what actually needs to change in the real DOM.

**Why it exists:** Manually mutating the DOM by hand for every data change is slow and error-prone. React splits the work into "figure out what UI should look like" (render) and "actually touch the DOM" (commit) so it can batch and optimize the real, expensive DOM work.

**Mental model:** Rendering is a chef writing today's menu on paper — calling your function, getting JSX back. It's not the same as actually cooking and serving the food; that's the separate "commit" phase, where real DOM updates happen.

```jsx
function App() {
  console.log('rendering App'); // runs on every render
  return <h1>Hello</h1>;
}
```

**Interview line:** "Rendering means React calls your component to get a description of the UI — it doesn't touch the DOM directly; that happens in a separate commit phase."

> ⚠️ Gotcha: "Render" does not mean "DOM update." A component can render (its function runs) with zero visible DOM change, if the diff finds nothing actually different.

---

### 6. Re-rendering

**What it is:** A re-render happens when a component's function runs again — triggered by its own state changing, its parent re-rendering (by default, every child re-renders too), or a subscribed context value changing.

**Why it exists:** React needs some trigger to know "something might have changed, go recompute the UI." Re-renders are how new data actually makes it onto the screen — without them the UI would be frozen at its first paint.

**Mental model:** A re-render is React re-asking the same question after new information arrives: "given this new state, what should the UI look like now?" Same question, re-answered.

```jsx
function Parent() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount(count + 1)}>+</button>
      <Child /> {/* re-renders too, even though it reads no props from Parent */}
    </>
  );
}
```

**Interview line:** "By default, when a parent re-renders, all its children re-render too, regardless of whether their own props changed — that cascading behavior is exactly what `memo`, `useMemo`, and `useCallback` exist to control."

> ⚠️ Gotcha: A re-render isn't automatically wasted — but unnecessary re-renders cascading across a large subtree are the single most common React performance complaint interviewers probe on.

---

### 7. Conditional Rendering

**What it is:** Choosing what JSX to return based on a condition — using ternaries, `&&`, early returns, or if/else logic before the return statement.

**Why it exists:** UI naturally differs based on state (loading vs. loaded, logged in vs. not). React has no special syntax for this because it doesn't need one — conditional rendering is just ordinary JS control flow applied to a JSX value.

**Mental model:** JSX is just a value, so "conditionally render" really means "conditionally pick which value to return" — the exact same logic as picking between two strings or numbers.

```jsx
function Status({ isLoading, data }) {
  if (isLoading) return <Spinner />;
  return <div>{data ? data.name : 'No data'}</div>;
}

// with &&
{items.length > 0 && <List items={items} />}
```

**Interview line:** "Conditional rendering is plain JavaScript — ternaries, `&&`, or early returns — there's no dedicated React syntax for it."

> ⚠️ Gotcha: `{count && <Badge />}` renders a literal `0` on screen when `count` is `0`, since `0` is falsy but not `false`/`null`/`undefined`. Guard with `count > 0 && ...` or a ternary instead.

---

### 8. Lists

**What it is:** Rendering a collection of items by mapping an array into an array of JSX elements, typically with `.map()`.

**Why it exists:** UIs constantly need to show N of something — a list of todos, search results, a table of rows. Mapping data straight to JSX is React's answer to "repeat this template once per item," using JS you already know instead of a templating DSL.

**Mental model:** `.map()` over data works identically whether you're transforming numbers or transforming data into UI — React just needs the final result to be an array of elements.

```jsx
function TodoList({ todos }) {
  return (
    <ul>
      {todos.map(todo => (
        <li key={todo.id}>{todo.text}</li>
      ))}
    </ul>
  );
}
```

**Interview line:** "Lists in React are just `.map()` producing an array of elements — React additionally needs a stable `key` on each one to track identity across renders."

> ⚠️ Gotcha: Omitting `key` doesn't crash the app, but React logs a warning and falls back to less efficient — and sometimes visibly buggy — reconciliation.

---

### 9. Keys

**What it is:** A `key` is a special string prop React uses to identify which items in a list changed, were added, or were removed between renders. It's read internally by React and never passed down to your component as a normal prop.

**Why it exists:** When a list re-renders, React needs to match "old" elements to "new" ones to know what to update, move, or destroy. Without a stable identity per item, React falls back to comparing by position — which silently breaks the moment items are reordered, inserted, or removed from the middle.

**Mental model:** Keys are name tags at a conference. Without them, if two people swap seats, the organizer (React) has to assume everyone in those seats changed roles entirely. With name tags, it instantly knows who actually moved where.

```jsx
{todos.map(todo => (
  <TodoItem key={todo.id} todo={todo} /> // stable, unique id — good
))}

{todos.map((todo, index) => (
  <TodoItem key={index} todo={todo} /> // index as key — risky if order can change
))}
```

**Interview line:** "Keys give React a stable identity for list items across renders, so it can correctly reuse, reorder, or discard DOM nodes and component state instead of guessing by position."

> ⚠️ Gotcha: Using the array `index` as a key is fine for static lists that never reorder — but once items can be added, removed, or reordered, it causes state to attach to the wrong row (classic bug: an input's typed value appearing on the wrong item after a row above it is deleted).

### 10. Component Composition

**What it is:** Building complex UIs by combining smaller components together — including passing components in via `children` or as props — instead of one component trying to handle every layout variant internally through config flags.

**Why it exists:** It keeps individual components small and focused, and avoids a component's prop API ballooning into a dozen booleans (`showHeader`, `showFooter`, `compact`, ...) trying to cover every possible use case.

**Mental model:** Composition is Lego, not custom-molded plastic. You don't build one giant bespoke brick for every shape you'll ever need — you combine a handful of small, standard bricks in different arrangements.

```jsx
function Card({ children }) {
  return <div className="card">{children}</div>;
}

function App() {
  return (
    <Card>
      <h2>Title</h2>
      <p>Some content</p>
    </Card>
  );
}
```

**Interview line:** "Composition means building UI by nesting and combining components — often via `children` — instead of a single component branching internally on a growing list of props."

> ⚠️ Gotcha: Reaching for composition (`children`, slots) instead of bolting on another boolean prop is usually the answer that reads as "more senior" in a design discussion — it's a good instinct to name explicitly in an interview.

---

### 11. Props Drilling

**What it is:** Passing a prop down through several layers of components that don't use it themselves, purely to get it to a deeply nested child that does.

**Why it exists (why it's a problem):** It's not a feature you reach for — it's a pain point that emerges naturally as a component tree grows, and it's precisely the problem Context (and later, state libraries) were built to solve.

**Mental model:** Passing a sealed note by hand through five people in a chain, when only the fifth person actually needs to read it — everyone in between has to physically handle it for no reason of their own.

```jsx
function App() {
  const user = { name: 'Saksham' };
  return <Layout user={user} />;
}
function Layout({ user }) {
  return <Sidebar user={user} />; // doesn't use `user`, just forwards it
}
function Sidebar({ user }) {
  return <Profile user={user} />; // finally used here
}
```

**Interview line:** "Props drilling is passing data through intermediate components that don't need it — a maintainability smell that Context or a state-management library resolves."

> ⚠️ Gotcha: Don't jump straight to Context (or Redux) for one or two levels of drilling — that's often over-engineering. Drilling becomes a genuine problem around three-plus levels deep, or when many unrelated components need the same piece of data.

---

### 12. Lifting State Up

**What it is:** Moving state from a child component up to the nearest common ancestor of every component that needs to read or update it, then passing it back down as props.

**Why it exists:** Sibling components can't talk to each other directly — React's data flow is strictly one-directional (parent → child). If two siblings need to share or stay in sync on some state, that state has to live in a shared parent above both of them.

**Mental model:** If two roommates both need control of the thermostat, you don't give each of them a separate one — you put a single thermostat in the shared hallway (the parent) that both rooms can see and adjust.

```jsx
function Parent() {
  const [value, setValue] = useState('');
  return (
    <>
      <Input value={value} onChange={setValue} />
      <Preview value={value} />
    </>
  );
}
```

**Interview line:** "Lifting state up means moving shared state to the closest common parent, so sibling components stay in sync through shared props instead of each holding its own disconnected copy."

> ⚠️ Gotcha: Lifting state further up than necessary "just in case" causes unrelated parts of the tree to re-render for no reason. State should live as close as possible to where it's actually used, and only move up when sharing is genuinely required.

---

### 13. Controlled vs Uncontrolled Components

**What it is:** In a **controlled** component, a form input's value is driven entirely by React state (`value` + `onChange`) — React is the single source of truth. In an **uncontrolled** component, the DOM itself holds the current value, and you read it on demand via a `ref`.

**Why it exists:** Native form elements normally manage their own internal state — that's just how plain HTML works. React offers both styles: controlled for when you need to validate, transform, or react to every keystroke; uncontrolled for simpler cases where you only need the value once, at submit time.

**Mental model:** Controlled is a puppet — every position is set explicitly by the puppeteer (React state); nothing moves on its own. Uncontrolled is a whiteboard — it just holds whatever's written on it, and you walk over and read it whenever you need to.

```jsx
// Controlled
function ControlledInput() {
  const [value, setValue] = useState('');
  return <input value={value} onChange={e => setValue(e.target.value)} />;
}

// Uncontrolled
function UncontrolledInput() {
  const inputRef = useRef(null);
  const handleSubmit = () => console.log(inputRef.current.value);
  return <input ref={inputRef} defaultValue="" />;
}
```

**Interview line:** "Controlled components keep the input's value in React state as the single source of truth; uncontrolled components let the DOM hold the value and you pull it via a ref when needed — most production forms default to controlled inputs for validation and instant feedback."

> ⚠️ Gotcha: Switching an input between controlled and uncontrolled mid-life — e.g., `value` going from a string to `undefined` — triggers a React warning. Pick one mode and stay in it, using `value={x ?? ''}` to avoid an accidental `undefined`.

## Part 2: Hooks

For each hook below: **What** it is → **Why** it exists → **Mental model** → **How** to use it → **When** to reach for it → **When NOT** to → **Common mistakes**.

### 14. `useState`

**What:** A hook that lets a function component hold and update local state across renders. Returns a `[value, setter]` pair.

**Why:** Function components, unlike class components, have no `this.state` — before hooks, only classes could hold state at all. `useState` gives function components that same persistent memory, tied to the component instance, surviving between renders (a plain local variable would just reset every time the function runs).

**Mental model:** React keeps a labeled box for this component instance, living outside the function itself. Each render, your function asks React "what's in the box right now?" — it never recreates the box from scratch.

**How:**

```jsx
function Counter() {
  const [count, setCount] = useState(0); // 0 = initial value, used only on first render

  const increment = () => setCount(count + 1);
  // safer under rapid updates — uses the latest value, not a stale closure:
  const incrementSafe = () => setCount(prev => prev + 1);

  return <button onClick={increment}>{count}</button>;
}
```

Calling the setter *schedules* a re-render with the new value — it doesn't mutate the existing variable in place.

**When to use:** Simple, independent pieces of state — a toggle, an input value, a counter, a list where updates don't depend on complex prior logic.

**When NOT to use:** When the next state depends on several related sub-values changing together, or the update logic itself is non-trivial (multiple `setX` calls in one handler that must stay in sync) — that's the signal to reach for `useReducer` instead.

**Common mistakes:**

- ⚠️ Reading `count` immediately after calling `setCount(count + 1)`, expecting the updated value — state updates are async, and the old `count` stays in scope until the next render.
- ⚠️ Calling `setCount(count + 1)` several times in the same handler, expecting them to add up — `count` doesn't change *between* those calls, so all of them use the same stale value. Use the functional updater `setCount(prev => prev + 1)` instead.
- ⚠️ Passing an object or array to `useState` and mutating it directly (`state.items.push(...)`) — React compares by reference, so this silently fails to trigger a re-render. Always create a new object/array.

**Interview line:** "`useState` gives a function component its own persistent memory across renders — calling the setter schedules a re-render with the new value, and for updates that depend on the previous state, the functional form avoids stale-closure bugs."

---

### 15. `useEffect`

**What:** A hook for running "side effects" — code that reaches outside the render itself (data fetching, subscriptions, timers, manually touching the DOM) — after React has committed changes to the DOM.

**Why:** Rendering is supposed to be a pure calculation of "what does the UI look like given this data" — side effects don't belong inside that calculation. `useEffect` is React's dedicated place to run that impure code, and to clean it back up.

**Mental model:** Render is designing a blueprint. `useEffect` is what happens *after* the building is actually constructed — only once the walls (DOM) exist can you go plug in the wiring (the effect).

**How:**

```jsx
useEffect(() => {
  const id = setInterval(() => console.log('tick'), 1000);
  return () => clearInterval(id); // cleanup — runs before the next effect, and on unmount
}, []); // dependency array — [] = run once, after mount

useEffect(() => {
  fetchUser(userId).then(setUser);
}, [userId]); // re-runs whenever userId changes
```

Three variants by dependency array: no array at all (runs after *every* render), `[]` (runs once, after mount), `[deps]` (runs on mount, then again whenever a listed value changes).

**When to use:** Data fetching, subscriptions (WebSocket connections, event listeners), manually syncing with something outside React (browser APIs like `document.title`), timers/intervals.

**When NOT to use:** For deriving one piece of state from another — e.g. `total = price * quantity` — compute it directly during render; don't `useEffect` + `setState` to "sync" it, which adds an extra render and a race-condition risk. Also not for a user event's direct consequence — a click that should trigger a fetch should call that function straight from the event handler, not indirectly via a state change that an effect happens to be watching.

**Common mistakes:**

- ⚠️ Missing dependencies in the array — using a variable inside the effect that isn't listed means the effect closes over a *stale* value from an earlier render (the classic "why isn't my effect seeing the new state" bug). Let the linter's exhaustive-deps rule guide the list rather than silencing it.
- ⚠️ Forgetting cleanup — subscriptions, timers, or listeners started in an effect without a matching `return () => {...}` keep running (and referencing stale state/props) after the component unmounts or before the next effect run.
- ⚠️ Putting an object or array literal in the dependency array — `{}` / `[]` are a brand-new reference on every render, so the effect ends up re-running every single time regardless of whether the actual values inside changed.
- ⚠️ Fetching without a cancellation guard — if `userId` changes quickly, an older, slower request can resolve *after* a newer one and overwrite fresher data (a race condition), unless you check "is this still the latest request" or use `AbortController`.

**Interview line:** "`useEffect` runs side effects after the DOM commits, re-running whenever its dependencies change — it's for syncing with something outside React, not for deriving values that render can just compute directly."

### 16. `useRef`

**What:** A hook that returns a mutable object shaped `{ current: value }` that persists across renders — but changing `.current` does **not** trigger a re-render.

**Why:** Sometimes a component needs to remember a value between renders without that value affecting what's on screen, or needs a direct handle on a DOM node. `useState` would cause an extra, unnecessary re-render for values the UI doesn't actually depend on; `useRef` sidesteps that entirely.

**Mental model:** A ref is a sticky note taped inside the component that React never looks at when deciding whether to redraw the screen — you can read and write it freely, and visually, nothing happens.

**How:**

```jsx
function TextInputFocus() {
  const inputRef = useRef(null);
  useEffect(() => { inputRef.current.focus(); }, []); // direct DOM access
  return <input ref={inputRef} />;
}

function Timer() {
  const countRef = useRef(0); // mutable value, not meant for display
  const handleClick = () => { countRef.current += 1; console.log(countRef.current); };
  return <button onClick={handleClick}>Log count</button>;
}
```

**When to use:** Referencing a DOM element directly (focus, scroll position, measuring size), storing a mutable value that must survive re-renders but shouldn't cause one (an interval ID, a "did this already run" flag, a previous-value cache), keeping something stable across renders without retriggering an effect that depends on it.

**When NOT to use:** For any value the UI needs to actually display, or that should cause a re-render when it changes — that belongs in `useState`. Using a ref for that kind of data means the screen silently goes stale.

**Common mistakes:**

- ⚠️ Expecting the UI to update when `.current` changes — it won't. React has no idea the ref changed, since it isn't part of the render output. If it needs to show on screen, it needs to be state.
- ⚠️ Reading `ref.current` *during render* to make a rendering decision — a ref isn't guaranteed to be attached to its DOM node on the very first render, and using it inside the render body (rather than an effect or event handler) is an anti-pattern React explicitly warns against.

**Interview line:** "`useRef` gives you a persistent mutable box that survives re-renders without causing one — used for DOM references and for values you need to keep around that shouldn't affect what's rendered."

---

### 17. `useMemo`

**What:** A hook that memoizes (caches) the *result of a computation* across renders, only recomputing it when one of its listed dependencies actually changes.

**Why:** Some calculations are expensive — sorting or filtering a large array, heavy math — and redoing that work on every render, even when the inputs didn't change, wastes time. `useMemo` skips the recomputation whenever nothing relevant changed.

**Mental model:** A cached search result. Ask the exact same question twice and a good search engine doesn't redo the whole search from scratch — it serves the cached answer, and only redoes the work once the question itself actually changes.

**How:**

```jsx
function ProductList({ products, query }) {
  const filtered = useMemo(
    () => products.filter(p => p.name.includes(query)),
    [products, query] // only recompute when products or query change
  );
  return <List items={filtered} />;
}
```

**When to use:** Genuinely expensive computations that would otherwise re-run on every render for no reason; stabilizing an object/array reference passed as a prop to a `memo`-wrapped child, so that memoization doesn't break.

**When NOT to use:** For cheap calculations (`a + b`, a simple string template) — the memoization bookkeeping itself has a cost, and for trivial work that cost isn't worth paying. It's also not a substitute for `useState` — it's for values *derived* from other state, not state you store directly.

**Common mistakes:**

- ⚠️ Reaching for `useMemo` everywhere "just in case" — over-memoizing cheap operations adds complexity and can end up net-slower. Profile before optimizing, rather than guessing.
- ⚠️ Missing or incorrect dependencies — the same failure mode as `useEffect`: leaving out a value the calculation actually reads gives you a stale, incorrectly cached result.
- ⚠️ Treating `useMemo` as a guarantee — React is explicitly allowed to discard a cached value and recompute anyway (e.g., to free memory). It's a performance hint, not a correctness contract, so never rely on it to *prevent* a computation from running for correctness reasons.

**Interview line:** "`useMemo` caches an expensive computed value between renders, only redoing the work when its dependencies change — it's a performance tool for derived data, not something you reach for by default."

---

### 18. `useCallback`

**What:** A hook that memoizes a *function reference* itself across renders, only creating a new function when its dependencies change. Functionally, `useCallback(fn, deps)` is equivalent to `useMemo(() => fn, deps)`.

**Why:** In JS, a function defined inside a component is a brand-new value on every render — even when its logic is identical to last time. When that function is passed as a prop to a child wrapped in `React.memo`, the new reference makes the child re-render anyway, quietly defeating the memoization. `useCallback` keeps the same function reference across renders when nothing relevant has changed.

**Mental model:** Without `useCallback`, you hand your child a freshly photocopied page every render — even if the words are identical, the child (doing a reference check) sees "different paper" and redoes its work. `useCallback` hands over the *same physical page* when nothing changed.

**How:**

```jsx
function Parent() {
  const [count, setCount] = useState(0);
  const handleClick = useCallback(() => {
    console.log('clicked');
  }, []); // same function reference on every render

  return <MemoChild onClick={handleClick} />; // won't re-render just because Parent did
}

const MemoChild = React.memo(function MemoChild({ onClick }) {
  console.log('MemoChild rendered');
  return <button onClick={onClick}>Click</button>;
});
```

**When to use:** Passing a callback as a prop to a `React.memo`-wrapped child, so the memoization actually holds; when the function is itself a dependency of another hook (like `useEffect`) and a stable reference is needed to stop that effect from re-running every render.

**When NOT to use:** For every function in a component "just in case" — if the function isn't passed to a memoized child or used as another hook's dependency, memoizing it buys nothing and just adds overhead.

**Common mistakes:**

- ⚠️ Using `useCallback` without wrapping the child in `React.memo` — the stabilized function reference is pointless if the child re-renders on every parent render regardless.
- ⚠️ Forgetting the function still closes over whatever values existed at the render where it was created — an empty dependency array locks in `count`, `props`, etc. from that first render (a stale closure), unless those values are added to `deps` or a functional updater is used instead.

**Interview line:** "`useCallback` memoizes a function's identity across renders — it only matters when that stable identity is actually needed downstream, like a prop to a `memo`-wrapped child or a dependency of another hook."

---

### 19. `useReducer`

**What:** A hook for managing state through a reducer function shaped `(state, action) => newState`, similar to Redux — you `dispatch` actions instead of calling a setter directly.

**Why:** When state updates involve several related sub-values, or the "what's the next state" logic is non-trivial — depends on the action type, needs multiple `setX` calls that must stay in sync — spreading that logic across many `useState` calls and handlers gets hard to follow and easy to get inconsistent. A reducer centralizes all the transition logic in one testable place.

**Mental model:** `useState` is directly editing a value with a pen. `useReducer` is submitting a request form ("action") to a clerk (the reducer) who follows a fixed rulebook to decide the new state — you never edit the value yourself, you only ever describe *what happened*.

**How:**

```jsx
function reducer(state, action) {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'decrement': return { count: state.count - 1 };
    case 'reset': return { count: 0 };
    default: throw new Error('Unknown action');
  }
}

function Counter() {
  const [state, dispatch] = useReducer(reducer, { count: 0 });
  return (
    <>
      <button onClick={() => dispatch({ type: 'increment' })}>+</button>
      <button onClick={() => dispatch({ type: 'decrement' })}>-</button>
      <span>{state.count}</span>
    </>
  );
}
```

**When to use:** Complex state with multiple sub-values that update together; state transitions that depend on the *type* of action rather than a simple new value; cases where the update logic benefits from being unit-tested in isolation (a reducer is a pure function — easy to test without rendering anything).

**When NOT to use:** For simple, independent state — a toggle, a single input value — `useState` is more direct and doesn't need the action/reducer ceremony.

**Common mistakes:**

- ⚠️ Mutating `state` inside the reducer instead of returning a new object — like all React state, the reducer must return a new object/array; mutating and returning the same reference means React won't detect any change.
- ⚠️ Putting side effects (API calls, logging) inside the reducer itself — reducers must stay pure functions; side effects belong in `useEffect`, triggered off the resulting state, never inside the reducer.

**Interview line:** "`useReducer` centralizes state-transition logic in a pure reducer you dispatch actions to — it shines once updates get complex or several pieces of state need to change together in a coordinated way."

### 20. Custom Hooks

**What:** A custom hook is just a regular JS function whose name starts with `use` and that calls other hooks inside it — a way to extract and reuse *stateful* logic between components.

**Why:** Before hooks, sharing stateful logic (not just UI) between components meant awkward patterns like higher-order components or render props, both of which wrapped the component tree in extra layers ("wrapper hell"). Custom hooks let you extract logic into a plain function with zero extra component nesting.

**Mental model:** If a regular function extracts *reusable logic*, a custom hook extracts *reusable stateful logic* — the same idea, just with the ability to plug into React's state and lifecycle.

**How:**

```jsx
function useWindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    const handleResize = () => setWidth(window.innerWidth);
    window.addEventListener('resize', handleResize);
    return () => window.removeEventListener('resize', handleResize);
  }, []);

  return width;
}

function Sidebar() {
  const width = useWindowWidth(); // reused in any component that needs it
  return <div>{width < 768 ? 'Mobile view' : 'Desktop view'}</div>;
}
```

**When to use:** Any time the same stateful logic — a fetch pattern, a subscription, form-handling logic, debouncing — shows up in more than one component, or even in a single component, if extracting it makes that component's own logic easier to read.

**When NOT to use:** For logic that has no state or effects and is purely a calculation — that's a plain utility function, not a hook, and doesn't need the `use` prefix or the Rules of Hooks constraints.

**Common mistakes:**

- ⚠️ Calling a custom hook conditionally or inside a loop — like any hook, it must be called unconditionally at the top level of the component, on every render, in the same order (the "Rules of Hooks").
- ⚠️ Assuming a custom hook shares state *between* components — it doesn't. Each component using a custom hook gets its own independent state; a custom hook shares the *logic* for producing state, not the state itself (that's what Context is for).

**Interview line:** "A custom hook is a plain function starting with `use` that composes React's built-in hooks — it's how you extract and reuse stateful logic across components without adding any extra component wrapping."
