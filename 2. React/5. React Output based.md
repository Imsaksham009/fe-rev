## The Big Picture First (read this once, it ties everything together)

React output questions aren't tricky because React is random — they're tricky because people forget **when** things happen. You only need two ideas.

### Idea 1: Every render is a snapshot

Inside one render, `count` is a **constant** — like a photograph. Every handler, effect, and timeout created *during that render* remembers that render's values forever (these are closures — same idea as in the JS Core file). Calling `setCount` does **not** change the variable you're holding; it *queues* an update that will produce the *next* snapshot.

### Idea 2: React does things in a fixed order

| Step                                        | What happens                                                                  | Logs from here appear…   |
| ------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------- |
| 1.**Render phase**                    | Component bodies run,**parent before child**                            | first                     |
| 2.**Commit**                          | DOM updated, refs attached                                                    | —                        |
| 3.**Layout effects**                  | Previous layout cleanups, then layout effects (**child before parent**) | before the browser paints |
| 4.**Paint**                           | Browser draws the screen                                                      | —                        |
| 5.**Passive effects** (`useEffect`) | *All* previous cleanups first, then effects (**child before parent**) | after paint               |

### The 4-step trace (use it on every question)

1. **Write down the snapshot** — the values of props and state in *this* render.
2. **Run the handler/effect using only that snapshot.** Note every `setState` as *queued*, not applied.
3. **Batch and process the queue in order** → that produces the *next* snapshot, and one re-render.
4. **Order the logs** using the phase table above.

### The update-queue rule

When React processes queued updates in order: a **value** (`setX(5)`) *replaces* the pending state; a **function** (`setX(c => c + 1)`) *receives* the pending state and returns the next one.

### What StrictMode double-runs (development only)

| Double-invoked in dev                                             | Why                   |
| ----------------------------------------------------------------- | --------------------- |
| Component function bodies                                         | Catch impure renders  |
| State updater functions & reducers                                | Catch impure updaters |
| `useState` / `useMemo` / `useReducer` initializer functions | Same                  |
| Effects: setup → cleanup → setup again on mount                 | Catch missing cleanup |

None of this happens in production.

**How to answer out loud in an interview:** Don't just say the output. Say: *"Each render is a snapshot, so…"* then narrate the trace. Naming the rule is what earns the points.

## Part 1: State Snapshots & Batching

### 1. Three increments

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
    console.log(count);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

Click once. What's logged, and what does the button show?

<details>
<summary>Answer</summary>

**Logs `0`. The button shows `1`.**

Trace: the snapshot is `count = 0`. Each line is really `setCount(0 + 1)` — three updates that all say "replace with 1". Batched, the result is `1`. And `console.log(count)` reads the snapshot, which is still `0`.

**Rule:** State is a snapshot; the setter queues an update, it doesn't change the variable.

</details>

---

### 2. Functional updaters

```jsx
function handleClick() {
  setCount(c => c + 1);
  setCount(c => c + 1);
  setCount(c => c + 1);
  console.log(count);
}
```

Same component, starting from `0`. Click once. Logs and button?

<details>
<summary>Answer</summary>

**Logs `0`. The button shows `3`.**

Trace: each updater receives the *pending* state from the previous one: `0 → 1 → 2 → 3`. The log still reads the old snapshot.

**Rule:** Use the functional form when the next state depends on the previous one.

</details>

---

### 3. The update queue

```jsx
function handleClick() {
  setCount(count + 5);
  setCount(c => c + 1);
  setCount(42);
}
```

Starting from `0`. What does the button show after one click?

<details>
<summary>Answer</summary>

**`42`.**

Trace through the queue, in order:

1. `count + 5` → a *value* → replace with `5`
2. `c => c + 1` → a *function* → receives `5` → `6`
3. `42` → a *value* → replace with `42`

Final: `42`.

**Rule:** Values replace, functions transform — processed strictly in order.

</details>

---

### 4. The stale timeout

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    setTimeout(() => console.log('timeout:', count), 1000);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

(a) Click once and wait. (b) Reload, then click **three times slowly** (letting each re-render finish before the next click). What's logged?

<details>
<summary>Answer</summary>

**(a) `timeout: 0`** — even though the screen already shows `1`.
**(b) `timeout: 0`, `timeout: 1`, `timeout: 2`.**

Trace: the timeout callback was created during the render where `count` was `0`, so it closes over `0` forever. On the second click, the handler comes from the *next* snapshot (`count = 1`), so its timeout logs `1`, and so on.

**Rule:** Closures capture the snapshot they were created in. This is the origin of the classic "stale closure" bug.

</details>

### 5. Batching outside events (React 17 vs 18)

```jsx
function App() {
  const [a, setA] = useState(0);
  const [b, setB] = useState(0);
  console.log('render');

  function handleClick() {
    setTimeout(() => {
      setA(a + 1);
      setB(b + 1);
    }, 0);
  }

  return <button onClick={handleClick}>go</button>;
}
```

After the initial mount, you click once. How many **new** `render` logs appear in (a) React 18 with `createRoot`, and (b) React 17 (or the legacy root)?

<details>
<summary>Answer</summary>

**(a) One. (b) Two.**

React 18's automatic batching groups updates from *anywhere* — timeouts, promises, native handlers — into one render. React 17 only batched inside React event handlers, so two `setState` calls in a `setTimeout` caused two separate renders.

**Rule:** React 18 batches automatically everywhere with `createRoot`. (`flushSync` is the opt-out.)

</details>

### 6. Mutating state

```jsx
function Profile() {
  const [user, setUser] = useState({ name: 'Ana' });

  function rename() {
    user.name = 'Bo';
    setUser(user);
  }

  return (
    <>
      <p>{user.name}</p>
      <button onClick={rename}>Rename</button>
    </>
  );
}
```

Click "Rename". What does the paragraph show?

<details>
<summary>Answer</summary>

**Still `Ana`.**

Trace: `setUser(user)` passes the *same object reference*. React compares with `Object.is`, sees "no change," and bails out — no update on screen. The object *was* mutated, though: if anything else re-renders this component later, it would suddenly show `Bo`, which makes the bug even harder to track down.

**Fix:** `setUser({ ...user, name: 'Bo' })` — always create a new object.

**Rule:** React detects changes by reference, so never mutate state.

</details>

### 7. Lazy initial state

```jsx
function expensive() {
  console.log('expensive called');
  return 100;
}

function App() {
  const [a] = useState(expensive());
  const [b] = useState(() => expensive());
  const [n, setN] = useState(0);

  return <button onClick={() => setN(n + 1)}>{n}</button>;
}
```

(No StrictMode.) How many times is `expensive called` logged (a) on mount, and (b) after each click?

<details>
<summary>Answer</summary>

**(a) Twice on mount. (b) Once per click.**

Trace: `useState(expensive())` *calls* `expensive()` during every render — React just ignores the result after the first. `useState(() => expensive())` passes a function, which React calls **only on the first render**. So: mount = 2 logs (one from each), and each re-render adds 1 (only `a`'s line).

**Rule:** For expensive initial values, pass a function (lazy initializer).

</details>

## Part 2: Effects

### 8. Mount order

```jsx
function Child() {
  console.log('Child render');
  useEffect(() => {
    console.log('Child effect');
    return () => console.log('Child cleanup');
  }, []);
  return <p>child</p>;
}

function Parent() {
  console.log('Parent render');
  useEffect(() => {
    console.log('Parent effect');
    return () => console.log('Parent cleanup');
  }, []);
  return <Child />;
}
```

Mount `<Parent />` (no StrictMode). Output?

<details>
<summary>Answer</summary>

```
Parent render
Child render
Child effect
Parent effect
```

Render goes **top-down** (parent first, since the parent's render is what produces the child). Effects go **bottom-up** — children's effects run before their parent's, so a parent's effect can rely on its children being fully set up.

**Rule:** Render: parent → child. Effects: child → parent.

</details>

---

### 9. Cleanup timing

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    console.log('effect', count);
    return () => console.log('cleanup', count);
  }, [count]);

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

Mount, then click twice. Output?

<details>
<summary>Answer</summary>

```
effect 0        ← mount
cleanup 0       ← click 1
effect 1
cleanup 1       ← click 2
effect 2
```

The cleanup logs the **old** value — it's a closure from the *previous* render. When `count` changes, React first runs the previous effect's cleanup (with its own snapshot, `0`), then runs the new effect (with `1`).

**Rule:** Cleanup runs before the next effect, and sees the values from the render that created it.

</details>

### 10. StrictMode double-run

```jsx
// index.jsx
<StrictMode><App /></StrictMode>

function App() {
  console.log('render');
  useEffect(() => {
    console.log('effect');
    return () => console.log('cleanup');
  }, []);
  return <p>hi</p>;
}
```

Output on mount in **development**? And in production?

<details>
<summary>Answer</summary>

**Development:**

```
render
render        ← StrictMode's second render (may appear dimmed in the console)
effect
cleanup       ← StrictMode simulates unmount…
effect        ← …then remount
```

**Production:** `render`, `effect` — once each.

StrictMode is deliberately stress-testing you: if an effect has no proper cleanup (a subscription, a timer), the extra cycle exposes it immediately as a duplicate.

**Rule:** The double effect run is a feature, not a bug. If it breaks your app, you're missing a cleanup.

</details>

### 11. The interval that gets stuck

```jsx
function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => setCount(count + 1), 1000);
    return () => clearInterval(id);
  }, []);

  return <p>{count}</p>;
}
```

What does the screen show over time?

<details>
<summary>Answer</summary>

**It shows `0`, then `1`, then stays at `1` forever.**

Trace: the effect runs once (empty deps), so the interval's callback closes over the very first snapshot, `count = 0`. Every tick calls `setCount(0 + 1)`. After the first tick the state is `1`; every later tick sets `1` again — same value, so React bails out.

**Fixes:** `setCount(c => c + 1)` (best — no dependency needed), or list `count` in the deps (works, but recreates the interval every tick).

**Rule:** An effect with `[]` deps sees only its first snapshot. Use functional updates to avoid stale state.

</details>

---

### 12. The effect loop

```jsx
function App() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    setCount(count + 1);
  });

  return <p>{count}</p>;
}
```

What happens?

<details>
<summary>Answer</summary>

**An infinite render loop** (React warns "Maximum update depth exceeded" in dev).

Trace: no dependency array → the effect runs after *every* render → it sets state → that causes a render → which runs the effect again → forever.

**Fix:** add a dependency array, and only set state when there's a real reason to.

**Rule:** No deps = runs after every render. Setting state unconditionally inside such an effect always loops.

</details>

---

### 13. Object in the dependency array

```jsx
function App() {
  const [n, setN] = useState(0);
  const options = { theme: 'dark' };

  useEffect(() => {
    console.log('effect ran');
  }, [options]);

  return <button onClick={() => setN(n + 1)}>{n}</button>;
}
```

Mount, then click three times. How many times is `effect ran` logged?

<details>
<summary>Answer</summary>

**Four times** — once on mount, and once per click.

Trace: `options` is a brand-new object on every render. React compares dependencies with `Object.is`, so `{...} !== {...}` and the effect re-runs every time, despite the contents being identical.

**Fixes:** move `options` outside the component, wrap it in `useMemo`, or depend on the primitive values inside it (`[theme]`).

**Rule:** Objects, arrays, and functions are new references every render.

</details>

### 14. `useLayoutEffect` vs `useEffect`

```jsx
function App() {
  console.log('render start');
  useEffect(() => { console.log('useEffect'); });
  useLayoutEffect(() => { console.log('useLayoutEffect'); });
  console.log('render end');
  return <p>hi</p>;
}
```

Output on mount?

<details>
<summary>Answer</summary>

```
render start
render end
useLayoutEffect
useEffect
```

The whole component body runs first (render phase). Then, after the commit, layout effects run **synchronously before the browser paints**; passive effects (`useEffect`) run **after paint**. The order they're *written* in doesn't matter.

**Rule:** `useLayoutEffect` runs before paint (use it to measure or adjust the DOM without flicker); `useEffect` runs after.

</details>

## Part 3: Rendering, Keys & Identity

### 15. Render order (and `memo`)

```jsx
function App() {
  const [n, setN] = useState(0);
  console.log('App');
  return (
    <>
      <button onClick={() => setN(n + 1)}>{n}</button>
      <A />
    </>
  );
}
function A() { console.log('A'); return <B />; }
function B() { console.log('B'); return null; }
```

(a) Output on click? (b) Now `A` is wrapped: `const A = React.memo(function A() {...})`. Output on click?

<details>
<summary>Answer</summary>

**(a) `App`, `A`, `B`** — top-down. A re-render cascades to all children by default, even though `A` has no props.

**(b) Only `App`.** `A` takes no props, so `memo` finds them equal and skips it — and since `B` is only reachable *through* `A`, it's skipped too.

**Rule:** Parent re-renders cascade downward; `memo` cuts the cascade if props are unchanged.

</details>

### 16. `key` resets state

```jsx
function App() {
  const [id, setId] = useState(1);
  return (
    <>
      <button onClick={() => setId(id + 1)}>Next user</button>
      <Profile key={id} id={id} />
    </>
  );
}

function Profile({ id }) {
  const [text, setText] = useState('');
  return (
    <input value={text} onChange={e => setText(e.target.value)} placeholder={`note for user ${id}`} />
  );
}
```

Type something in the input, then click "Next user". What happens to the text? And without `key={id}`?

<details>
<summary>Answer</summary>

**With the key: the input clears.** When `key` changes, React treats it as a *different component* — it unmounts the old `Profile` and mounts a fresh one with fresh state.
**Without the key: the text stays** (only the placeholder changes), because it's the same component in the same position, so its state is preserved.

**Rule:** Changing `key` is the standard way to deliberately reset a component's state.

</details>

### 17. A component defined inside a component

```jsx
function Parent() {
  const [n, setN] = useState(0);

  function Child() {
    const [text, setText] = useState('');
    return <input value={text} onChange={e => setText(e.target.value)} />;
  }

  return (
    <>
      <button onClick={() => setN(n + 1)}>Clicked {n}</button>
      <Child />
    </>
  );
}
```

Type "hello" in the input. Then click the button. What happens?

<details>
<summary>Answer</summary>

**The input is cleared** (and loses focus).

Trace: typing only re-renders `Child` (its own state), so it works fine. But clicking the button re-renders `Parent`, which creates a **brand-new `Child` function** — a new component *type*. React sees a different type at that position, unmounts the old one, and mounts a fresh one, wiping its state.

**Fix:** define `Child` outside `Parent` and pass data through props.

**Rule:** Never define components inside other components — a new function identity means a new component type.

</details>

### 18. Index keys

```jsx
function Row({ label }) {
  const [done, setDone] = useState(false);
  return (
    <li>
      <input type="checkbox" checked={done} onChange={() => setDone(!done)} />
      {label}
    </li>
  );
}

function App() {
  const [items, setItems] = useState(['A', 'B', 'C']);
  return (
    <>
      <button onClick={() => setItems(items.slice(1))}>Delete first</button>
      <ul>
        {items.map((item, index) => <Row key={index} label={item} />)}
      </ul>
    </>
  );
}
```

Tick the checkbox next to **A**, then click "Delete first". Which row is checked?

<details>
<summary>Answer</summary>

**`B` is checked** — even though you ticked `A`.

Trace: state lives with the *component instance*, and React matches instances by key. With `key={index}`, the instance at key `0` (which had `done = true`) survives and simply receives the new label `B`. The instance for key `2` is what gets removed.

**Fix:** `key={item}` (or a stable id) — then `A`'s instance is the one removed, along with its state.

**Rule:** Index keys tie state to *position*, not identity. Only safe for static lists.

</details>

### 19. `&&` with zero

```jsx
function Cart({ items }) {
  return <div>{items.length && <List items={items} />}</div>;
}

<Cart items={[]} />
```

What renders?

<details>
<summary>Answer</summary>

**A literal `0`.**

Trace: `0 && anything` short-circuits to `0`, and React *does* render the number `0` (unlike `false`, `null`, `undefined`, which render nothing).

**Fix:** `items.length > 0 && ...`, or use a ternary.

**Rule:** `&&` returns the left side if it's falsy — and `0` is falsy but visible.

</details>

### 20. Same position, same type

```jsx
function App() {
  const [isFancy, setIsFancy] = useState(false);
  return (
    <div>
      {isFancy ? <Counter fancy /> : <Counter />}
      <label>
        <input type="checkbox" checked={isFancy} onChange={e => setIsFancy(e.target.checked)} />
        Fancy style
      </label>
    </div>
  );
}
```

`Counter` has its own `count` state. Click the counter a few times, then toggle the checkbox. Does the count reset? Now rewrite it as:

```jsx
{isFancy && <Counter fancy />}
{!isFancy && <Counter />}
```

Does the count reset now?

<details>
<summary>Answer</summary>

**First version: the count is preserved.** Both branches render a `<Counter />` at the *same position* with the *same type*, so React sees one component receiving new props and keeps its state.
**Second version: the count resets.** These are two *different slots* in the children list (one is always `false`), so toggling unmounts one `Counter` and mounts the other.

**Rule:** State is tied to a component's **type and position** in the tree — not to where it appears in your JSX text.

</details>

## Part 4: Handlers, Refs & Hook Rules

### 21. Calling instead of passing

```jsx
function App() {
  const [count, setCount] = useState(0);
  return <button onClick={setCount(count + 1)}>{count}</button>;
}
```

What happens?

<details>
<summary>Answer</summary>

**Error: "Too many re-renders. React limits the number of renders to prevent an infinite loop."**

Trace: `setCount(count + 1)` is *called during render* (it's not wrapped in a function), which sets state, which triggers a render, which calls it again…

**Fix:** `onClick={() => setCount(count + 1)}`.

**Rule:** Pass a function to `onClick`; don't call one. (`onClick={handle()}` runs immediately at render time; `onClick={handle}` runs on click.)

</details>

---

### 22. Refs don't re-render

```jsx
function Clicker() {
  const clicks = useRef(0);

  return (
    <>
      <button onClick={() => { clicks.current += 1; console.log(clicks.current); }}>
        Click
      </button>
      <p>Clicks: {clicks.current}</p>
    </>
  );
}
```

Click the button three times. What's in the console, and what does the screen show?

<details>
<summary>Answer</summary>

**Console: `1`, `2`, `3`. Screen: `Clicks: 0`.**

Trace: changing `ref.current` doesn't trigger a render, so React never re-runs the JSX. The value *is* updated — if something else re-renders the component later, the screen will suddenly jump to `3`.

**Fix:** if the value should appear on screen, it belongs in `useState`.

**Rule:** Refs are for values that *don't* affect rendering.

</details>

### 23. `useCallback` with empty deps

```jsx
function App() {
  const [count, setCount] = useState(0);
  const log = useCallback(() => console.log(count), []);

  return (
    <>
      <button onClick={() => setCount(count + 1)}>+</button>
      <button onClick={log}>Log</button>
    </>
  );
}
```

Click "+" three times, then "Log". What's logged?

<details>
<summary>Answer</summary>

**`0`.**

Trace: with `[]` deps, `useCallback` returns the function from the *first* render forever — and that function closes over the first snapshot, `count = 0`.

**Fix:** add `count` to the deps, or read the latest value from a ref.

**Rule:** Memoized functions are stale-closure factories if their deps are wrong.

</details>

### 24. A conditional hook

```jsx
function Profile({ isLoggedIn }) {
  if (isLoggedIn) {
    const [name, setName] = useState('Ana');
  }
  const [theme, setTheme] = useState('dark');
  return <p>{theme}</p>;
}
```

It renders fine with `isLoggedIn={true}`. What happens when the prop flips to `false`?

<details>
<summary>Answer</summary>

**React throws an error** ("Rendered fewer hooks than expected…"; flipping the other way gives "Rendered more hooks than during the previous render").

Why: React doesn't track hooks by name — it tracks them by **call order**, like a numbered list. Skipping one shifts every later hook into the wrong slot, so `theme` would read `name`'s state.

**Rule:** Only call hooks at the top level, unconditionally, in the same order every render. (Put the condition *inside* the hook, not around it.)

</details>

### 25. StrictMode and updater functions

```jsx
<StrictMode><App /></StrictMode>

function App() {
  const [n, setN] = useState(0);
  return (
    <button onClick={() => setN(c => { console.log('updater'); return c + 1; })}>
      {n}
    </button>
  );
}
```

Click once in **development**. How many times is `updater` logged, and what does the button show?

<details>
<summary>Answer</summary>

**`updater` is logged twice. The button shows `1` (not 2).**

StrictMode calls updater functions twice to catch impure ones; it uses one result and discards the other. In production it runs once.

**Rule:** Updater functions and reducers must be **pure** — no logging, no side effects, no mutation.

</details>

### 26. Copying a prop into state

```jsx
function Child({ name }) {
  const [text, setText] = useState(name);
  return <p>{text}</p>;
}

function Parent() {
  const [name, setName] = useState('Ana');
  return (
    <>
      <button onClick={() => setName('Bo')}>Rename</button>
      <Child name={name} />
    </>
  );
}
```

Click "Rename". What does the paragraph show?

<details>
<summary>Answer</summary>

**Still `Ana`.**

Trace: `useState(name)` uses the prop **only as the initial value**. `Child` re-renders with `name = 'Bo'`, but React ignores the initializer after the first render and keeps the state it already has.

**Fix:** use the prop directly (`<p>{name}</p>`), or reset the component with `key={name}`.

**Rule:** Don't copy props into state unless you truly want a one-time starting value.

</details>

## Part 5: Boss Level & Quick-Fire Gotchas

### 27. Boss level

```jsx
function App() {
  const [n, setN] = useState(0);
  console.log('render', n);

  useLayoutEffect(() => {
    console.log('layout', n);
  });

  useEffect(() => {
    console.log('effect', n);
    if (n === 0) setN(1);
  }, [n]);

  return <p>{n}</p>;
}
```

(No StrictMode.) Output on mount?

<details>
<summary>Answer</summary>

```
render 0
layout 0
effect 0
render 1
layout 1
effect 1
```

Full trace:

1. **Render** with `n = 0` → logs `render 0`.
2. **Commit**, then the layout effect (no deps, so it runs on every commit) → `layout 0`.
3. **After paint**, the passive effect runs → `effect 0`, and it calls `setN(1)`.
4. That update triggers a **new render** with `n = 1` → `render 1`.
5. Commit → `layout 1`. Then the passive effect runs again because its dep changed `0 → 1` → `effect 1`. This time `n` isn't `0`, so no more state updates — the chain ends.

**Rule:** Every state update restarts the cycle: render → layout effects → paint → passive effects.

### 28. Quick-fire gotchas

Short, high-frequency traps. For each one, be able to say the cause and the fix in one breath.

| Gotcha                                                                  | What goes wrong                                                            | Fix                                                            |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `setState` then read the variable                                     | You still see the old value (snapshot)                                     | Use the next render, or compute the new value first            |
| Multiple`setCount(count + 1)`                                         | Only increments once                                                       | `setCount(c => c + 1)`                                       |
| Missing effect dependency                                               | Stale closure — effect sees old values                                    | Add the dep (trust the lint rule)                              |
| No effect cleanup                                                       | Leaked timers/listeners; duplicates in StrictMode                          | Return a cleanup function                                      |
| Fetch in effect, changing param                                         | Slow old request overwrites the newer one (race)                           | Cancel with`AbortController` or an `ignore` flag           |
| Object/array/function in deps                                           | Effect re-runs every render                                                | Hoist,`useMemo`/`useCallback`, or use primitives           |
| `async` function passed to `useEffect`                              | Effect returns a Promise; React warns it's not a cleanup                   | Define an inner`async` function and call it                  |
| Index as`key`                                                         | State attaches to the wrong item on delete/reorder                         | Use a stable unique id                                         |
| Component defined inside a component                                    | Remounts every render, state resets                                        | Define it outside                                              |
| `{count && <X />}`                                                    | Renders`0`                                                               | `count > 0 && …` or a ternary                               |
| `useState(props.x)`                                                   | Later prop changes ignored                                                 | Use the prop, or`key` to reset                               |
| Mutating state or props                                                 | No re-render; hard-to-trace bugs                                           | Create new objects/arrays                                      |
| Hooks in`if`/loops                                                    | "Rendered fewer/more hooks" error                                          | Keep hooks top-level; put conditions inside                    |
| `onClick={fn()}`                                                      | Runs at render, can loop                                                   | `onClick={fn}` or `onClick={() => fn(arg)}`                |
| `ref.current` for display data                                        | UI doesn't update                                                          | Use state                                                      |
| `useEffect` for measuring DOM                                         | Visible flicker (runs after paint)                                         | `useLayoutEffect`                                            |
| Setting state of another component during render                        | Warning: "Cannot update a component while rendering a different component" | Move it to an event handler or effect                          |
| `value` without `onChange` (or `value={undefined}` then a string) | Read-only input / controlled ↔ uncontrolled warning                       | Add`onChange`; default to `''`                             |
| `key` read as a prop                                                  | `props.key` is `undefined`                                             | Pass the id under a different prop name                        |
| StrictMode "runs twice"                                                 | Panic that React is buggy                                                  | It's intentional in dev — fix the impurity/cleanup it exposed |
