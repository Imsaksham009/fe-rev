## The Big Picture First (read this once, it ties everything together)

**The golden rule of performance work: measure first, then fix the cheapest thing first.** Most "optimizations" people do by gut feel don't help, and memoization has its own cost. Interviewers listen for exactly this mindset.

Before touching any code, ask two questions:

1. Is it slow to **load** (big bundle, slow network) or slow to **interact** (typing lags, clicks feel heavy)?
2. Is the cause **too much rendering work** or **too much stuff** (too many DOM nodes, too much JS)?

Then fix in order of cost — cheapest first:

| Tier                 | Fixes                                              | Cost                               |
| -------------------- | -------------------------------------------------- | ---------------------------------- |
| 1. Free (structural) | Colocate state, composition, hoist constants       | None — no extra code paths        |
| 2. Cheap             | `memo` + `useMemo` + `useCallback`           | Some complexity, easy to get wrong |
| 3. Prioritize        | `useTransition` / `useDeferredValue`, debounce | Small                              |
| 4. Structural        | Virtualization, code splitting, pagination         | Moderate                           |

**The running example — a deliberately slow page:**

```jsx
function ProductPage() {
  const [query, setQuery] = useState('');
  const [isCartOpen, setIsCartOpen] = useState(false);   // only the drawer cares
  const [cartCount, setCartCount] = useState(0);

  // 5,000 products — this filter runs on EVERY render
  const filtered = products.filter(p =>
    p.name.toLowerCase().includes(query.toLowerCase())
  );

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <button onClick={() => setIsCartOpen(o => !o)}>Cart ({cartCount})</button>
      {isCartOpen && <CartDrawer />}
      <ProductList products={filtered} onAdd={() => setCartCount(c => c + 1)} />
    </>
  );
}
```

**What's wrong with it — and where each problem gets fixed:**

| Problem                                                               | Fixed in   |
| --------------------------------------------------------------------- | ---------- |
| Toggling the cart drawer re-renders all 5,000 rows for no reason      | #3, #4, #5 |
| The filter recomputes on every render, even unrelated ones            | #6         |
| `onAdd` is a new function every render (kills memoization)          | #7         |
| Every keystroke blocks typing while the list re-renders               | #8, #11    |
| 5,000 rows means 5,000 DOM nodes                                      | #10        |
| `CartDrawer` code ships in the first bundle even if nobody opens it | #9         |

## Part 1: Measure & Diagnose

### 1. Profiling with React DevTools

**What it is:** The **Profiler** tab in React DevTools records what re-rendered during an interaction, how long each component took, and — if you enable "Record why each component rendered" — *why* it rendered. For page-level problems, pair it with Chrome's Performance tab and Lighthouse/Web Vitals.

**Why it exists:** Optimizing without measuring is guessing. The slow part is rarely where you'd assume, and every optimization (like `memo`) adds complexity and its own cost. The profiler tells you what is *actually* slow.

**Mental model:** A doctor running tests before recommending surgery. You wouldn't operate on a hunch.

**Connect it to the example:** Start recording, type one character in the search box, stop. The Profiler shows: `ProductList` took ~80ms (5,000 rows), `CartBadge`-style siblings re-rendered even though nothing changed for them, and toggling the drawer *also* re-rendered `ProductList`. Now you know exactly where to aim — and you can re-record after each fix to prove it helped.

How to read it:

- **Commit chart (top bar)** — each bar is one commit (one DOM update); taller/yellower means slower.
- **Flamegraph** — components in the tree for a commit; **gray = did not render** in that commit, colored = rendered (color and width show time).
- **Ranked chart** — same commit, sorted slowest first. This is usually the fastest way to find the culprit.
- **Highlight updates** (in DevTools settings) — flashes a border around every component that re-renders, live.

**Interview line:** "I always profile first — the React DevTools Profiler shows what re-rendered, how long it took, and why, so I optimize the actual bottleneck instead of guessing."

> ⚠️ Gotcha: Development builds are much slower than production, and `StrictMode` deliberately double-renders components in dev. Treat dev numbers as *relative* (is A slower than B?), not absolute — and confirm important wins on a production build.

### 2. What Makes React Apps Slow

**What it is:** A short list of root causes. Almost every real performance problem is one of these:

**Too much rendering work**

- **Unnecessary re-renders of big subtrees** — state lives too high, or a parent re-render cascades into expensive children (#3–#5).
- **Expensive work during render** — filtering/sorting large arrays or heavy calculations on every render (#6).
- **Unstable references** — new objects, arrays, or functions every render defeating `memo` (#5, #7).
- **Context updates** re-rendering every consumer (covered in the State Management file, #5).

**Too much stuff**

- **Too many DOM nodes** — long lists rendered in full (#10).
- **Large JS bundle** — slow first load (#9, #12).
- **Network problems** — waterfalls, no caching, huge images (#12).

**Why it matters:** Naming the *category* first tells you which tool to use. A laggy input is a rendering-work problem; a slow first paint is a bundle problem — and no amount of `useMemo` fixes a 3MB bundle.

**Mental model:** A traffic jam has different causes — too many cars (DOM nodes), cars taking pointless detours (unnecessary renders), a slow toll booth (expensive calculation), or a very long road (big bundle). You fix each differently.

**Connect it to the example:** `ProductPage` has *all of them at once*: the drawer toggle causes a pointless cascade, the filter is a slow toll booth, the function prop is an unstable reference, 5,000 rows is too many cars, and `CartDrawer` adds weight to the road.

**Interview line:** "Slow React apps usually come down to unnecessary re-renders, expensive render-time work, too many DOM nodes, or a heavy bundle — and diagnosing which one it is decides which fix to use."

> ⚠️ Gotcha: A re-render is not automatically a problem. Re-rendering a cheap component 100 times is fine; re-rendering one expensive component once per keystroke is not. The question is always "is this render *expensive* and *unnecessary*?"

## Part 2: Stop Unnecessary Re-renders

### 3. State Colocation (Push State Down)

**What it is:** Keeping state as close as possible to the component that actually uses it — so when it changes, only a small subtree re-renders.

**Why it exists:** Re-renders cascade *downward* from wherever the state lives. The higher the state, the bigger the blast radius. Moving it down is the cheapest fix there is: no `memo`, no hooks, no dependency arrays.

**Mental model:** A fire door. You don't stop fires from starting — you contain them to one room.

**Connect it to the example:** `isCartOpen` is only used by the cart button and drawer, yet it lives in `ProductPage` — so toggling it re-renders `ProductList` (all 5,000 rows). Move it into a small component that owns it:

```jsx
function CartButton({ count }) {
  const [isOpen, setIsOpen] = useState(false);   // state moved down
  return (
    <>
      <button onClick={() => setIsOpen(o => !o)}>Cart ({count})</button>
      {isOpen && <CartDrawer />}
    </>
  );
}

function ProductPage() {
  // ... no more isCartOpen here
  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <CartButton count={cartCount} />
      <ProductList products={filtered} onAdd={handleAdd} />
    </>
  );
}
```

Toggling the drawer now re-renders only `CartButton` and its children. `ProductList` is untouched.

**Interview line:** "Before reaching for memoization, I check whether state can move down. Re-renders cascade from where state lives, so colocating it shrinks the blast radius for free."

> ⚠️ Gotcha: This only works for state that's genuinely used by a smaller subtree. `query` is needed by both the input *and* the list, so it can't move down — that's where the next techniques come in.

### 4. Children as Props (Composition)

**What it is:** When a component with its own state receives heavy content via `children` (or another prop), that content doesn't re-render when the wrapper's state changes — because the content's element was created by a *parent that didn't re-render*.

**Why it works:** React skips re-rendering an element when it's the *exact same reference* as last time. `children` was created up in the parent; when the wrapper re-renders due to its own state, it re-uses that same `children` element — so React bails out on it.

**Mental model:** A sealed package handed to you. When you re-tie the ribbon on the outside (re-render), the package inside is the same package — nobody reopens it.

```jsx
function Layout({ children }) {
  const [sidebarOpen, setSidebarOpen] = useState(false);
  return (
    <div>
      <button onClick={() => setSidebarOpen(o => !o)}>Menu</button>
      {sidebarOpen && <Sidebar />}
      {children}        {/* same element reference each time → skipped */}
    </div>
  );
}

function App() {
  return (
    <Layout>
      <ProductPage />   {/* created here; App doesn't re-render when sidebarOpen changes */}
    </Layout>
  );
}
```

Toggling `sidebarOpen` re-renders `Layout`, but **not** `ProductPage`.

**Interview line:** "If a stateful wrapper re-renders, content passed in as `children` doesn't — its element was created by a parent that didn't re-render, so React reuses it. It's a memoization-free way to isolate expensive subtrees."

> ⚠️ Gotcha: It only works if the element is created *above* the re-rendering component. Writing `<ProductPage />` inside `Layout`'s own JSX would create a new element every render and defeat it. It also doesn't help if that child reads a context whose value changed.

### 5. `React.memo`

**What it is:** A wrapper that memoizes a component: it skips re-rendering if its props are **shallowly equal** (compared with `Object.is`, prop by prop) to the previous props.

**Why it exists:** By default, when a parent re-renders, *every* child re-renders too, regardless of whether its props changed. `memo` adds a "did my props actually change?" check to stop that cascade.

**Mental model:** A bouncer with a guest list. Each time the parent asks for a re-render, the bouncer compares tonight's props to last time's. Identical? Not getting in.

```jsx
const ProductList = React.memo(function ProductList({ products, onAdd }) {
  console.log('ProductList rendered');
  return (
    <ul>
      {products.map(p => <ProductRow key={p.id} product={p} onAdd={onAdd} />)}
    </ul>
  );
});
```

But here's the catch — **`memo` only works if the props are stable.** In our example, `filtered` is a brand-new array every render and `onAdd` is a brand-new function every render, so the shallow comparison *always* fails and `memo` does nothing. Each unstable prop type has its own fix:

| Prop that breaks`memo`                                      | Why                       | Fix                                           |
| ------------------------------------------------------------- | ------------------------- | --------------------------------------------- |
| Object / array literal (`style={{...}}`, `items={[1,2]}`) | New reference each render | Hoist outside the component, or`useMemo`    |
| Function (`onClick={() => ...}`)                            | New function each render  | `useCallback` (#7)                          |
| Derived array (`.filter()` / `.map()` result)             | New array each render     | `useMemo` (#6)                              |
| JSX`children` (`<Card><span/></Card>`)                    | New element each render   | Hoist the element,`useMemo`, or restructure |

**Interview line:** "`React.memo` skips a re-render when props are shallowly equal — but it's only effective if the props are referentially stable, so it usually needs `useMemo` and `useCallback` alongside it."

> ⚠️ Gotcha #1: `memo` does **not** block re-renders caused by the component's *own state* or a *context* it reads — only re-renders triggered by its parent.
>
> ⚠️ Gotcha #2: Don't wrap everything in `memo`. The prop comparison itself costs something, and for cheap components that cost outweighs the benefit. Use it for components the profiler shows are expensive *and* re-render unnecessarily.
>
> ⚠️ Gotcha #3: A second argument (`memo(Comp, areEqual)`) lets you write a custom comparison, but it's rarely worth it — a buggy comparator causes stale UI that's hard to debug.

### 6. `useMemo` — When It Actually Helps

*(Syntax and basics are in the React file, #17 — this is the decision guide.)*

**What it is:** Caches the result of a calculation between renders, recomputing only when its dependencies change.

**Why it exists:** Some work is genuinely expensive, and repeating it on every render — including renders unrelated to that work — wastes time.

**Mental model:** A cached search result. Same question, same cached answer; only redo the work when the question changes.

**The three legitimate reasons to use it:**

1. **A calculation that's measurably expensive** — large filter/sort/aggregate. (React's docs suggest timing it: if it takes around a millisecond or more, it's a candidate.)
2. **Stabilizing an object/array prop** passed to a `memo`-wrapped child (#5).
3. **Stabilizing a value that's a dependency** of another hook, so an effect doesn't re-run every render.

**Connect it to the example:**

```jsx
const filtered = useMemo(
  () => products.filter(p => p.name.toLowerCase().includes(query.toLowerCase())),
  [products, query]   // recomputes only when the query changes — not on unrelated renders
);
```

This fixes two things at once: the filter no longer re-runs on unrelated renders, and `filtered` is now a *stable array* the memoized `ProductList` can compare successfully.

**Interview line:** "I use `useMemo` for measurably expensive calculations or to stabilize a reference that a memoized child or hook depends on — not by default, because memoization has its own overhead."

> ⚠️ Gotcha: `useMemo` is a performance hint, not a guarantee — React may discard cached values. Never rely on it for correctness. And a missing dependency gives you a stale cached result, just like `useEffect`.

### 7. `useCallback` — When It Actually Helps

*(Basics are in the React file, #18 — this is the decision guide.)*

**What it is:** Memoizes a *function reference* so the same function object is reused across renders unless its dependencies change.

**Why it exists:** A function defined in a component is a new object every render. If it's passed to a `memo`-wrapped child, that new reference makes the child re-render anyway. `useCallback` keeps the reference stable.

**Mental model:** Handing your child the *same physical page* each time instead of a fresh photocopy — so a reference check sees "unchanged."

**Connect it to the example:** `onAdd={() => setCartCount(c => c + 1)}` is a new function every render, which defeats `memo(ProductList)`. Fix it:

```jsx
const handleAdd = useCallback(() => setCartCount(c => c + 1), []);
// functional update (c => c + 1) means no dependencies — the function never goes stale

<ProductList products={filtered} onAdd={handleAdd} />
```

Now all the pieces line up: `memo(ProductList)` + stable `filtered` (from `useMemo`) + stable `onAdd` (from `useCallback`). Only *now* does `ProductList` actually skip re-renders on unrelated updates.

**Interview line:** "`useCallback` only matters when a stable function reference is actually needed downstream — as a prop to a `memo` child or a dependency of another hook. Without that, it's pure overhead."

> ⚠️ Gotcha: `useCallback` without a `memo`-wrapped consumer does nothing useful. And an empty dependency array can capture stale values — use functional state updates (`setX(prev => ...)`) to avoid needing dependencies.

### 8. `useTransition` & `useDeferredValue`

*(The concurrent-rendering theory is in the Internals file, #10 — here they're used as performance tools.)*

**What it is:** Two hooks that let you mark an update as **non-urgent**, so urgent updates (typing, clicking) stay responsive while React handles the expensive part at lower priority — and can interrupt it if something more important arrives.

- `useDeferredValue(value)` returns a copy of a value that "lags behind" and updates in the background.
- `useTransition()` gives you `startTransition(() => setState(...))` to mark a *state update* as low-priority.

**Why it exists:** Some renders are expensive no matter what (like filtering a huge list on every keystroke). Instead of making them faster, these hooks make them *not block* the interaction that triggered them.

**Mental model:** A two-lane road. Typing gets the express lane and stays instant; the heavy list re-render travels the slow lane and may catch up a moment later.

**Connect it to the example:**

```jsx
const [query, setQuery] = useState('');
const deferredQuery = useDeferredValue(query);

const filtered = useMemo(
  () => products.filter(p => p.name.toLowerCase().includes(deferredQuery.toLowerCase())),
  [deferredQuery]
);

<input value={query} onChange={e => setQuery(e.target.value)} />  {/* urgent — always instant */}
<ProductList products={filtered} />                               {/* low priority — may lag, interruptible */}
```

The input updates immediately with `query`; the list re-renders in the background using `deferredQuery`, and React can abandon that work if you type again.

**Interview line:** "`useDeferredValue` and `useTransition` mark work as non-urgent so typing stays responsive while the heavy render happens at lower priority. Unlike debounce, there's no artificial delay, and React can interrupt the low-priority render."

> ⚠️ Gotcha #1: They don't make a render *faster* — they change its *priority*. And interruption happens *between* components; a single component that takes 300ms in one function call still blocks while it runs.
>
> ⚠️ Gotcha #2: For `useDeferredValue` to skip work, the expensive child should be wrapped in `memo` — otherwise it still re-renders in the urgent pass with the old value. Also, the controlled input's own `value` state can't be the transitioned one; keep it urgent.

## Part 3: Do Less Work, Ship Less Code

### 9. Code Splitting: `React.lazy` + `Suspense`

**What it is:** Splitting your JS bundle into separate chunks loaded **on demand**. `React.lazy` wraps a dynamic `import()`, and `Suspense` shows a fallback while the chunk downloads.

**Why it exists:** Initial JS size drives load time. Users shouldn't download code for a drawer they may never open or a route they may never visit.

**Mental model:** Packing a suitcase. Carry the essentials; get the rest delivered only if you need it.

**Connect it to the example:** `CartDrawer` is only needed after a click, so it doesn't belong in the first bundle:

```jsx
import { lazy, Suspense } from 'react';

const CartDrawer = lazy(() => import('./CartDrawer')); // declared at module level

function CartButton({ count }) {
  const [isOpen, setIsOpen] = useState(false);
  return (
    <>
      <button onClick={() => setIsOpen(o => !o)}>Cart ({count})</button>
      {isOpen && (
        <Suspense fallback={<Spinner />}>
          <CartDrawer />
        </Suspense>
      )}
    </>
  );
}
```

The most common real-world use is **route-level splitting** — each page is its own lazy chunk, so visiting `/home` doesn't download the `/admin` code.

**Interview line:** "Code splitting with `React.lazy` and `Suspense` loads code on demand — usually per route — so the initial bundle stays small and first load is faster."

> ⚠️ Gotcha #1: `React.lazy` expects a **default export**. For a named export: `lazy(() => import('./X').then(m => ({ default: m.X })))`.
>
> ⚠️ Gotcha #2: Declare `lazy(...)` at the **module level**, never inside a component — otherwise a new lazy component is created every render and its state resets.
>
> ⚠️ Gotcha #3: Don't lazy-load small or above-the-fold components — the extra request and loading flash cost more than they save. And wrap lazy sections in an **error boundary** to handle chunks that fail to load.

### 10. List Virtualization (Windowing)

**What it is:** Rendering **only the rows currently visible** in the viewport (plus a small buffer) instead of the entire list. As the user scrolls, rows are swapped in and out. Libraries: `react-window`, `react-virtuoso`, TanStack Virtual.

**Why it exists:** Each row is a React component *and* a DOM node — 5,000 of them means slow initial render, slow updates, and heavy memory use. Virtualization keeps the DOM at ~20–30 nodes no matter how big the data is.

**Mental model:** A train window. You only see the scenery passing the window right now, not the entire journey at once.

**Connect it to the example:** Replacing 5,000 `<li>` elements with a virtualized list. Here's the core idea in a simplified fixed-height version — worth understanding because interviewers sometimes ask you to *build* it:

```jsx
function VirtualList({ items, itemHeight = 40, height = 400 }) {
  const [scrollTop, setScrollTop] = useState(0);

  const start = Math.floor(scrollTop / itemHeight);              // first visible index
  const visibleCount = Math.ceil(height / itemHeight);           // how many fit on screen
  const end = Math.min(items.length, start + visibleCount + 5);  // +5 buffer rows

  return (
    <div
      style={{ height, overflowY: 'auto' }}
      onScroll={e => setScrollTop(e.currentTarget.scrollTop)}
    >
      {/* a tall spacer so the scrollbar reflects the FULL list */}
      <div style={{ height: items.length * itemHeight, position: 'relative' }}>
        {items.slice(start, end).map((item, i) => (
          <div
            key={item.id}
            style={{ position: 'absolute', top: (start + i) * itemHeight, height: itemHeight }}
          >
            {item.name}
          </div>
        ))}
      </div>
    </div>
  );
}
```

The trick: a tall empty container gives the correct scrollbar, and only the slice of rows near `scrollTop` are actually rendered, absolutely positioned where they'd be in the full list. In production, use a library — they handle variable heights, resizing, and scroll edge cases.

**Interview line:** "Virtualization renders only the visible rows plus a buffer, so DOM size stays constant regardless of list length. I'd use it once a list reaches hundreds or thousands of rows — via `react-window` or TanStack Virtual, not hand-rolled."

> ⚠️ Gotcha: Virtualization has trade-offs — browser find-in-page (Ctrl+F) can't see off-screen rows, variable-height rows are harder, and accessibility needs care. For moderately large lists, **pagination** or "load more" is often simpler and good enough.

### 11. Debounce & Throttle

**What it is:** Two ways to limit how often a function runs when events fire rapidly.

- **Debounce** — wait until the events *stop* for N ms, then run once.
- **Throttle** — run at most once every N ms, no matter how many events arrive.

**Why it exists:** Keystrokes, scrolls, and resizes fire dozens of times per second. Running an API call or an expensive filter on every single one is wasteful.

**Mental model:** *Debounce* is an elevator door that keeps waiting as long as someone's still walking in — it only closes once nobody has arrived for a moment. *Throttle* is a turnstile that lets exactly one person through every few seconds, however long the queue is.

```js
function debounce(fn, delay) {
  let timer;                                  // closure keeps the timer between calls
  return (...args) => {
    clearTimeout(timer);                      // reset the countdown on every call
    timer = setTimeout(() => fn(...args), delay);
  };
}

function throttle(fn, limit) {
  let last = 0;
  return (...args) => {
    const now = Date.now();
    if (now - last >= limit) {                // only run if enough time has passed
      last = now;
      fn(...args);
    }
  };
}
```

In React, the cleanest pattern for a search box is a **debounced value** hook:

```jsx
function useDebounce(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);           // cleanup resets the timer on each change
  }, [value, delay]);
  return debounced;
}

const debouncedQuery = useDebounce(query, 300);   // use this for the API call / filter
```

**Interview line:** "Debounce runs after the user stops — ideal for search inputs. Throttle runs at a steady maximum rate while events continue — ideal for scroll and resize. Both rely on closures holding a timer."

> ⚠️ Gotcha #1: Creating a debounced function *inside a component body* makes a brand-new one each render, so its timer state is lost. Stabilize it with `useMemo`/`useRef`, or use the debounced-*value* pattern above, which avoids the problem.
>
> ⚠️ Gotcha #2: Debounce and `useDeferredValue` (#8) solve different things — debounce is right for *network calls* (fewer requests); deferred values are right for *local rendering work*. They can be combined.

### 12. Bundle, Asset & Network Wins

**What it is:** A grab-bag of load-time improvements that often matter more to real users than render tuning:

- **Analyze the bundle** — `webpack-bundle-analyzer`, `source-map-explorer`, or Vite's visualizer plugin shows what's actually big.
- **Tree shaking** — import only what you use so unused code is dropped: `import debounce from 'lodash/debounce'` instead of `import _ from 'lodash'`.
- **Swap heavy libraries** — e.g., `moment` → `date-fns` or `dayjs`.
- **Images** — `loading="lazy"` for below-the-fold images, modern formats (WebP/AVIF), correctly sized files, and explicit `width`/`height` to prevent layout shift.
- **Cache and dedupe API data** — RTK Query / React Query instead of refetching everywhere.
- **Avoid network waterfalls** — fire independent requests in parallel; prefetch what's likely needed next.
- **Compression and CDN** — gzip/Brotli and a CDN for static assets.

**Why it matters:** A user's first impression is load time. Rendering can be flawless and the page still feels slow if the bundle is huge or requests run one after another.

**Mental model:** Weight loss for the bundle before coaching the runner's stride.

```js
// ❌ pulls the entire library into the bundle
import _ from 'lodash';
const d = _.debounce(fn, 300);

// ✅ pulls in just one function
import debounce from 'lodash/debounce';
const d = debounce(fn, 300);
```

**Interview line:** "Beyond render tuning, I look at bundle size with an analyzer, tree-shake and swap heavy dependencies, lazy-load images, cache API data, and avoid request waterfalls — those usually move load-time metrics the most."

> ⚠️ Gotcha: Optimize what the analyzer or profiler actually shows, not folklore. Shaving 2KB off something while a 500KB library sits unused is wasted effort.

## Part 4: Putting It Together

### 13. How to Optimize a Slow React App (the interview answer)

**What it is:** The "how would you optimize a slow React app?" question, which is close to guaranteed. A great answer isn't a list of hooks — it's a **process**.

**The playbook:**

1. **Clarify and measure.** Is it slow to *load* or slow to *interact*? Use Lighthouse/Web Vitals for load, the React Profiler for interaction. Get a baseline.
2. **Fix the free stuff first.** Colocate state (#3), use composition (#4), hoist constants out of components.
3. **Add memoization where the profiler proves it.** `memo` + stable props via `useMemo`/`useCallback` (#5–#7) — on expensive components only.
4. **Reduce the work.** Virtualize or paginate big lists (#10), memoize expensive calculations (#6), debounce inputs (#11), use transitions to keep typing responsive (#8).
5. **Reduce the load.** Code-split routes and heavy components (#9), analyze the bundle, optimize images and dependencies (#12).
6. **Fix the data layer.** Cache and dedupe requests, avoid waterfalls, avoid storing server data in ways that cause needless re-renders.
7. **Re-measure.** Prove the improvement with the profiler — otherwise it didn't happen.

**Symptom → cause → fix (quick reference):**

| Symptom                                      | Likely cause                        | Fix                                             |
| -------------------------------------------- | ----------------------------------- | ----------------------------------------------- |
| Typing lags                                  | Heavy list re-renders per keystroke | `memo`, deferred value/transition, debounce   |
| Everything re-renders when one thing changes | State too high / context too broad  | Colocate state, split contexts                  |
| Scrolling a long list is janky               | Thousands of DOM nodes              | Virtualization / pagination                     |
| Slow first load                              | Big bundle                          | Code splitting, tree shaking, analyze bundle    |
| `memo` isn't helping                       | Unstable props                      | `useMemo` / `useCallback` / hoist constants |
| Layout jumps while loading                   | Images without dimensions           | Set`width`/`height`, lazy-load              |

**Interview line:** "I'd start by measuring — Lighthouse for load, the React Profiler for interaction — to find the real bottleneck. Then I fix in order of cost: structural changes like colocating state first, then memoization where the profiler justifies it, then virtualization, code splitting, and bundle work — and I re-measure to confirm."

> ⚠️ Gotcha: The weak answer is "I'd wrap everything in `useMemo` and `useCallback`." It signals you optimize by folklore. Leading with *measurement* and *cheapest-fix-first* is what separates a senior answer.

---

### 14. React Compiler (Auto-Memoization)

**What it is:** A build-time tool (a Babel plugin) that analyzes your components and **automatically inserts memoization**, so you often don't need to write `useMemo`, `useCallback`, or `memo` by hand.

**Why it exists:** Manual memoization is tedious and easy to get wrong — forgotten dependencies, unstable references, over-memoizing. Since the rules for *when* memoization is safe are mechanical, a compiler can apply them consistently.

**Mental model:** Auto-pilot for memoization. You still need to know what the plane is doing — but you're not hand-flying every moment.

**Connect it to the example:** With the compiler enabled, `ProductPage` could be written *without* `useMemo` on `filtered` or `useCallback` on `handleAdd` — the compiler memoizes them for you.

**Interview line:** "The React Compiler auto-memoizes components and values at build time, reducing the need for manual `memo`, `useMemo`, and `useCallback` — but understanding manual memoization still matters, both to explain what the compiler does and because many codebases don't use it."

> ⚠️ Gotcha: The compiler assumes your code follows the **Rules of React** (pure render, no mutating props/state). It doesn't fix algorithmic slowness, giant lists, or bundle size — those still need virtualization, code splitting, and better data handling. Check whether the project you're joining has it enabled.

### 15. Practice: Will It Re-render?

Predict the console output first, *then* open the answer. Same trace-don't-guess approach as the event-loop drills.

**Q1 — Inline function**

```jsx
const Child = React.memo(function Child({ onClick }) {
  console.log('Child rendered');
  return <button onClick={onClick}>Go</button>;
});

function Parent() {
  const [n, setN] = useState(0);
  return (
    <>
      <button onClick={() => setN(n + 1)}>+</button>
      <Child onClick={() => console.log('hi')} />
    </>
  );
}
```

Click "+". Does `Child` log?

<details>
<summary>Answer</summary>

**Yes — logs "Child rendered" every click.** The inline arrow function is a new reference every render, so `memo`'s shallow comparison sees a changed prop. Fix: `const handleClick = useCallback(() => console.log('hi'), [])`.

</details>

**Q2 — Stable function**

Same as Q1, but `Parent` uses `const handleClick = useCallback(() => console.log('hi'), [])` and passes `onClick={handleClick}`. Click "+". Does `Child` log?

<details>
<summary>Answer</summary>

**No.** The function reference is stable, so `memo` finds identical props and skips the re-render.

</details>

**Q3 — Children as props**

```jsx
function Wrapper({ children }) {
  const [n, setN] = useState(0);
  console.log('Wrapper');
  return <div onClick={() => setN(n + 1)}>{n}{children}</div>;
}
function Expensive() {
  console.log('Expensive');
  return <p>hi</p>;
}
function App() {
  return <Wrapper><Expensive /></Wrapper>;
}
```

Click the div. What's logged?

<details>
<summary>Answer</summary>

**Only "Wrapper".** `<Expensive />` was created by `App`, which didn't re-render — so `children` is the same element reference and React skips `Expensive`. No `memo` needed.

</details>

**Q4 — `memo` with JSX children**

```jsx
const Card = React.memo(function Card({ children }) {
  console.log('Card');
  return <div>{children}</div>;
});

function Parent() {
  const [n, setN] = useState(0);
  return (
    <>
      <button onClick={() => setN(n + 1)}>+</button>
      <Card><span>static</span></Card>
    </>
  );
}
```

Click "+". Does `Card` log?

<details>
<summary>Answer</summary>

**Yes.** `<span>static</span>` is a new element object on every `Parent` render, so the `children` prop changes by reference and `memo` is defeated. Fix: hoist the element outside the component, or wrap it in `useMemo`.

</details>

**Q5 — `memo` and context**

```jsx
const CountContext = createContext(0);

const Display = React.memo(function Display() {
  const count = useContext(CountContext);
  console.log('Display');
  return <p>{count}</p>;
});

function App() {
  const [count, setCount] = useState(0);
  return (
    <CountContext.Provider value={count}>
      <Display />
      <button onClick={() => setCount(count + 1)}>+</button>
    </CountContext.Provider>
  );
}
```

Click "+". Does `Display` log?

<details>
<summary>Answer</summary>

**Yes.** `memo` only guards against re-renders from a *parent*. `Display` subscribes to the context directly, so a context value change re-renders it regardless of `memo`.

</details>

**Q6 — Array literal**

```jsx
const List = React.memo(function List({ items }) {
  console.log('List');
  return <ul>{items.map(i => <li key={i}>{i}</li>)}</ul>;
});

function Parent() {
  const [n, setN] = useState(0);
  const items = [1, 2, 3];
  return (
    <>
      <button onClick={() => setN(n + 1)}>+</button>
      <List items={items} />
    </>
  );
}
```

Click "+". Does `List` log?

<details>
<summary>Answer</summary>

**Yes.** `[1, 2, 3]` is a new array every render, so the `items` prop changes by reference. Fix: move `const items = [1, 2, 3]` *outside* the component (a module-level constant), or use `useMemo`.

</details>
