## The Big Picture First (read this once, it ties everything together)

Advanced React questions fall into two families:

**Family A — APIs that escape React's normal flow.** React normally works like this: data flows *down* through props, output is rendered *inside* the parent's DOM node, and a crash anywhere brings the tree down. Four tools break out of that in a controlled way: **error boundaries**, **portals**, **refs** (`forwardRef` / `useImperativeHandle`), and **layout effects**.

**Family B — Patterns for reusing logic and UI.** How do you share behavior between components? The answer has evolved: **mixins → HOCs → render props → custom hooks** — plus **compound components** for reusable *UI structure*.

And underneath it all sits the "why" question interviewers love: **why do the Rules of Hooks exist?**

**The running example — a design-system `<Modal>`.** Building a good modal needs all of it:

| Requirement                                                      | Solved by                                     |
| ---------------------------------------------------------------- | --------------------------------------------- |
| Content shouldn't crash the whole app if it throws               | Error boundary (#1)                           |
| Must escape parents with`overflow: hidden` / `z-index` traps | Portal (#2)                                   |
| Parent needs to focus the modal or close it imperatively         | `forwardRef` + `useImperativeHandle` (#3) |
| Measure and position without a visible flicker                   | `useLayoutEffect` (#4)                      |
| Reusable open/close and scroll-lock logic                        | Custom hooks (#7)                             |
| Flexible`Modal.Header` / `Modal.Body` / `Modal.Footer` API | Compound components (#9)                      |

## Part 1: APIs That Escape the Normal Flow

### 1. Error Boundaries

**What it is:** A **class component** that catches JavaScript errors thrown while rendering any component *below* it, logs them, and shows a fallback UI instead of crashing. It uses two special methods:

- `static getDerivedStateFromError(error)` — runs during render; returns state that switches to the fallback UI.
- `componentDidCatch(error, info)` — runs after commit; used for side effects like logging to a monitoring service.

**Why it exists:** By default, an uncaught error during rendering **unmounts the entire React tree** — the user sees a blank white page because one small widget broke. Error boundaries contain the damage to just the broken part.

**Mental model:** A circuit breaker in a fuse box. One appliance shorts out, that circuit trips, and the rest of the house keeps its power.

```jsx
class ErrorBoundary extends React.Component {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };                      // render phase: switch to fallback
  }

  componentDidCatch(error, info) {
    logToService(error, info.componentStack);       // commit phase: side effects / logging
  }

  render() {
    return this.state.hasError ? this.props.fallback : this.props.children;
  }
}

<ErrorBoundary fallback={<p>Something went wrong.</p>}>
  <ModalContent />     {/* if this throws while rendering, only the fallback shows */}
</ErrorBoundary>
```

**Interview line:** "Error boundaries are class components that catch errors during rendering, lifecycle methods, and constructors of their child tree, and render a fallback — so one broken component doesn't take down the whole app."

> ⚠️ Gotcha #1 — **what they do NOT catch:** errors in **event handlers** (use `try/catch`), **asynchronous code** (`setTimeout`, promises, `fetch`), **server-side rendering**, and errors thrown **in the boundary itself** (those bubble up to the next boundary above).
>
> ⚠️ Gotcha #2: There's no hook equivalent — a boundary must be a class. In practice most teams use the `react-error-boundary` library, which wraps this and adds a `resetErrorBoundary` function and reset keys.
>
> ⚠️ Gotcha #3: Placement matters. Use a few *granular* boundaries (per widget or route) plus one top-level one — a single boundary at the root just gives you a nicer white screen. React 19 also added `onCaughtError` / `onUncaughtError` options on `createRoot` for centralized error reporting.

### 2. Portals

**What it is:** `createPortal(children, domNode)` renders children into a **different DOM node** (usually `document.body`), while they *remain part of the React tree* — same context, same props flow, same event bubbling.

**Why it exists:** Modals, tooltips, dropdowns, and toasts get clipped by an ancestor's `overflow: hidden`, or trapped under a parent's stacking context (`z-index`, `transform`). Rendering them at the body level escapes those CSS traps — without breaking React's component structure.

**Mental model:** A teleporter. The character (the DOM node) appears somewhere else on the map, but is still on the same team (the React tree — context and events still connect it to its original parent).

```jsx
import { createPortal } from 'react-dom';

function Modal({ isOpen, onClose, children }) {
  if (!isOpen) return null;

  return createPortal(
    <div className="backdrop" onClick={onClose}>
      <div className="modal" role="dialog" aria-modal="true" onClick={e => e.stopPropagation()}>
        {children}
      </div>
    </div>,
    document.body
  );
}
```

**Interview line:** "A portal renders children into a different DOM node — like `document.body` — while keeping them in the same React tree, so context works and events bubble through React parents. It's how modals and tooltips escape overflow and z-index issues."

> ⚠️ Gotcha #1: **Events bubble through the React tree, not the DOM tree.** A click inside the portal triggers `onClick` handlers on the *React* ancestors, even though the DOM nodes are far apart. (See drill #5.)
>
> ⚠️ Gotcha #2: CSS inheritance follows the *DOM* tree, so a portaled element doesn't inherit styles from its React parent's wrapper.
>
> ⚠️ Gotcha #3: Portals aren't supported during server rendering (`document` doesn't exist there) — render them only after mount on the client. Also, you still own accessibility: focus trapping, the Escape key, and `aria-modal`. The native HTML `<dialog>` element with `showModal()` handles much of this and renders in the browser's top layer, so it's worth knowing as an alternative.

### 3. `forwardRef` & `useImperativeHandle`

**What it is:**

- **`forwardRef`** lets a component receive a `ref` from its parent and pass it down to an inner DOM element.
- **`useImperativeHandle(ref, () => ({...}), deps)`** customizes *what* the parent's ref exposes — a small, curated API instead of the raw DOM node.

**Why it exists:** Sometimes a parent genuinely needs imperative control — focus an input, scroll a list, play a video, open a modal. Before React 19, function components couldn't receive `ref` as a normal prop, so `forwardRef` was the way through. And handing over the raw DOM node exposes *everything*; `useImperativeHandle` exposes only the methods you choose — encapsulation.

**Mental model:** `forwardRef` is a receptionist who forwards a caller to the right desk. `useImperativeHandle` is that receptionist handing out a short phone directory of extensions — not the keys to the whole building.

```jsx
const FancyInput = forwardRef(function FancyInput(props, ref) {
  const inputRef = useRef(null);

  useImperativeHandle(ref, () => ({
    focus() { inputRef.current.focus(); },
    clear() { inputRef.current.value = ''; },
  }), []);

  return <input ref={inputRef} {...props} />;
});

function Form() {
  const fancyRef = useRef(null);
  return (
    <>
      <FancyInput ref={fancyRef} />
      <button onClick={() => fancyRef.current.focus()}>Focus it</button>
    </>
  );
}
```

**React 19 update:** function components now receive `ref` as a **regular prop**, so `forwardRef` is no longer needed for new code:

```jsx
function FancyInput({ ref, ...props }) {
  return <input ref={ref} {...props} />;
}
```

`forwardRef` still works (and you'll see it everywhere in existing codebases), but it's expected to be deprecated eventually. React 19 also lets ref callbacks return a **cleanup function**.

**Interview line:** "`forwardRef` passes a parent's ref through to an inner element, and `useImperativeHandle` lets me expose a limited imperative API — like `focus()` — instead of the whole DOM node. In React 19, `ref` is just a prop, so `forwardRef` is no longer required."

> ⚠️ Gotcha #1: Prefer declarative props and state — reach for imperative refs only for things props can't express (focus, scroll, media playback, measuring).
>
> ⚠️ Gotcha #2: `ref.current` is `null` until after the component mounts — never read it during render, only in effects or event handlers.
>
> ⚠️ Gotcha #3: In React 18 and earlier, passing a `ref` to a plain function component gives a warning and `ref.current` stays `null`. (See drill #6.)

### 4. `useLayoutEffect` vs `useEffect`

*(Phase order is covered in the Internals file #5 and Output file #14 — this is the "when do I actually use it" version.)*

**What it is:** Same signature, different **timing**. `useLayoutEffect` runs **synchronously after DOM changes but before the browser paints**. `useEffect` runs **after** paint.

**Why it exists:** Sometimes you need to read the DOM (size, position) and adjust something *before* the user sees the first frame. With `useEffect`, the user would briefly see the wrong layout — a visible flicker.

**Mental model:** Fixing a painting *before* the gallery doors open (layout effect) versus fixing it after visitors have already walked in and seen it (regular effect).

```jsx
function Tooltip({ targetRect, children }) {
  const ref = useRef(null);
  const [top, setTop] = useState(0);

  useLayoutEffect(() => {
    const { height } = ref.current.getBoundingClientRect();   // measure the real DOM
    setTop(targetRect.top - height - 8);                      // adjust before paint → no flash
  }, [targetRect]);

  return <div ref={ref} style={{ position: 'fixed', top }}>{children}</div>;
}
```

**Interview line:** "`useLayoutEffect` runs before the browser paints, so I use it to measure and adjust the DOM without flicker. Everything else should be `useEffect`, because layout effects block painting."

> ⚠️ Gotcha #1: Default to `useEffect`. A slow layout effect **freezes the screen**, because the browser can't paint until it finishes.
>
> ⚠️ Gotcha #2: Layout effects don't run during server rendering, so anything that depends on measuring the DOM for its first paint can flash or mismatch on SSR — guard it or defer it until after mount.

## Part 2: Reuse Patterns

*The story to tell in an interview:* React needed a way to share *stateful logic* between components. **Mixins** (with `createClass`) were the first attempt — they caused name clashes and were removed. **HOCs** came next, then **render props**, and finally **custom hooks** won as the flat, simple default.

### 5. Higher-Order Components (HOC)

**What it is:** A function that takes a component and returns a **new component** with extra behavior or props: `withAuth(Dashboard)`.

**Why it exists:** Before hooks, class components had no clean way to share cross-cutting logic — auth checks, data injection, logging. HOCs let you wrap once instead of copy-pasting the logic into every component.

**Mental model:** Gift wrapping — the wrapper adds something (or guards access) around the original item without changing what's inside.

```jsx
function withAuth(WrappedComponent) {
  function WithAuth(props) {
    const { user } = useAuth();
    if (!user) return <Redirect to="/login" />;              // gate access
    return <WrappedComponent {...props} user={user} />;      // inject data
  }
  WithAuth.displayName = `withAuth(${WrappedComponent.displayName || WrappedComponent.name})`;
  return WithAuth;
}

const ProtectedDashboard = withAuth(Dashboard);
```

**Interview line:** "A HOC is a function that takes a component and returns an enhanced one — it shares logic by wrapping. It was the standard pre-hooks pattern, used by things like Redux's old `connect` and `withRouter`."

> ⚠️ Gotcha #1: **Never create a HOC-wrapped component inside `render`** — a new function each render means a new component type, so React remounts it every time and its state resets (same trap as Output drill #17).
>
> ⚠️ Gotcha #2: "Wrapper hell" — deeply nested wrappers clutter DevTools, and injected props can silently **collide** with props you already pass. It's also hard to see *where* a prop came from.
>
> ⚠️ Gotcha #3: HOCs must forward refs and copy static methods (`hoist-non-react-statics`), or they break in subtle ways.

### 6. Render Props

**What it is:** A component that takes a **function as a prop** (often `children`) and calls it with its internal data, letting the *consumer* decide what to render.

**Why it exists:** It shares stateful logic like a HOC, but more explicitly: you can *see* at the call site what data you're receiving, and there's no prop-name collision.

**Mental model:** A vending machine that hands you the ingredients (the data) and lets you decide the recipe (the UI).

```jsx
function MouseTracker({ children }) {
  const [pos, setPos] = useState({ x: 0, y: 0 });

  return (
    <div onMouseMove={e => setPos({ x: e.clientX, y: e.clientY })}>
      {children(pos)}                      {/* call the function with the data */}
    </div>
  );
}

<MouseTracker>
  {({ x, y }) => <p>Mouse at {x}, {y}</p>}
</MouseTracker>
```

**Interview line:** "A render prop is a function prop that a component calls with its internal state, so the consumer controls the UI. It's more explicit than a HOC, but nesting several of them gets ugly — which is why hooks largely replaced it."

> ⚠️ Gotcha #1: Combining several render props creates a nesting pyramid ("callback hell" for JSX).
>
> ⚠️ Gotcha #2: An inline render function is a new function every render, which breaks `memo` / `PureComponent` optimizations.
>
> ⚠️ Gotcha #3: Still alive in libraries (Formik, Downshift, headless UI kits) and whenever *inversion of control* over what gets rendered matters.

### 7. Custom Hooks (the Modern Default)

*(Basics are in the React file, #20 — this is the pattern view.)*

**What it is:** A function starting with `use` that calls other hooks to package reusable stateful logic.

**Why it won:** Compared to HOCs and render props, hooks add **no wrapper components** (flat tree), return values **explicitly**, compose freely (a hook can call other hooks), and are easy to type and test.

**Mental model:** A HOC wraps your component in a box; a hook is just a function you call — logic without the packaging.

Here's the earlier `MouseTracker` as a hook — compare it to #6:

```jsx
function useMousePosition() {
  const [pos, setPos] = useState({ x: 0, y: 0 });

  useEffect(() => {
    const onMove = e => setPos({ x: e.clientX, y: e.clientY });
    window.addEventListener('mousemove', onMove);
    return () => window.removeEventListener('mousemove', onMove);
  }, []);

  return pos;
}

const { x, y } = useMousePosition();   // no wrapper, no callback, no nesting
```

And a hook the `Modal` needs — locking body scroll while it's open:

```jsx
function useLockBodyScroll(locked) {
  useLayoutEffect(() => {
    if (!locked) return;
    const original = document.body.style.overflow;
    document.body.style.overflow = 'hidden';
    return () => { document.body.style.overflow = original; };   // restore on close/unmount
  }, [locked]);
}
```

**Interview line:** "Custom hooks replaced HOCs and render props because they share logic without wrapper components — flat, explicit, and composable. Each call gets its own state; they share *logic*, not state."

> ⚠️ Gotcha #1: Hooks share logic, **not state** — two components calling the same hook each get their own independent copy. Sharing state across components needs Context or a store.
>
> ⚠️ Gotcha #2: Hooks can't help when you need to control *where UI renders* or share *UI structure* — that's where render props and compound components (#9) still fit. And hooks don't work in class components.

### 8. HOC vs Render Props vs Custom Hooks

|                                    | HOC                                              | Render props                                        | Custom hooks                                        |
| ---------------------------------- | ------------------------------------------------ | --------------------------------------------------- | --------------------------------------------------- |
| How it shares logic                | Wraps a component, injects props                 | Component calls a function prop with data           | Plain function call inside a component              |
| Where data comes from (visibility) | Hidden — injected implicitly                    | Visible in the callback's params                    | Visible — returned by the hook                     |
| Extra components in the tree       | Yes (wrapper)                                    | Yes (the render-prop component)                     | **None**                                      |
| Naming collisions                  | Yes — injected props can clash                  | No                                                  | No (you name the return values)                     |
| Composing several                  | Nesting wrappers (`withA(withB(X))`)           | Nesting callbacks (pyramid)                         | Just call multiple hooks                            |
| Works in class components          | Yes                                              | Yes                                                 | **No**                                        |
| Best for today                     | Legacy code, cross-cutting wrappers (auth gates) | Inversion of control over rendering, some libraries | **Default choice** for sharing stateful logic |

**Interview line:** "All three share logic between components. HOCs wrap, render props inject through a callback, and hooks are just function calls. Hooks are the default because they're flat, explicit, and composable — I'd still use a render prop or HOC when I need control over rendering or must support class components."

> ⚠️ Gotcha: Don't trash the older patterns. The strongest answer explains *why* each existed and *when* it still fits — not "HOCs are bad."

### 9. Compound Components

**What it is:** A group of components that work together and **share implicit state**, so users compose them declaratively — like HTML's `<select>` and `<option>`. The parent holds the state and shares it with its children through Context.

**Why it exists:** Without it, a flexible component ends up with a giant prop list (`headerTitle`, `showFooter`, `footerButtons`, `bodyPadding`…). Compound components let the *consumer* control structure, order, and markup — the composition idea from the React Fundamentals file, taken further.

**Mental model:** `<select>` and `<option>`: an `<option>` doesn't need to be told which one is selected — it cooperates with its parent `<select>`.

**Connect it to the example:** Our `Modal`, restructured:

```jsx
const ModalContext = createContext(null);

function useModalContext() {
  const ctx = useContext(ModalContext);
  if (!ctx) throw new Error('Modal.* components must be used inside <Modal>');
  return ctx;
}

function Modal({ isOpen, onClose, children }) {
  const value = useMemo(() => ({ onClose }), [onClose]);
  useLockBodyScroll(isOpen);                      // custom hook from #7
  if (!isOpen) return null;

  return createPortal(                             // portal from #2
    <ModalContext.Provider value={value}>
      <div className="backdrop" onClick={onClose}>
        <div className="modal" role="dialog" aria-modal="true" onClick={e => e.stopPropagation()}>
          {children}
        </div>
      </div>
    </ModalContext.Provider>,
    document.body
  );
}

Modal.Header = function Header({ children }) {
  const { onClose } = useModalContext();
  return (
    <div className="modal-header">
      {children}
      <button onClick={onClose} aria-label="Close">×</button>
    </div>
  );
};
Modal.Body = ({ children }) => <div className="modal-body">{children}</div>;
Modal.Footer = ({ children }) => <div className="modal-footer">{children}</div>;
```

Usage — the consumer decides what goes where:

```jsx
<Modal isOpen={open} onClose={() => setOpen(false)}>
  <Modal.Header>Delete item?</Modal.Header>
  <Modal.Body>This can't be undone.</Modal.Body>
  <Modal.Footer>
    <button onClick={confirmDelete}>Delete</button>
  </Modal.Footer>
</Modal>
```

**Interview line:** "Compound components are a set of components that share implicit state through Context, letting consumers compose flexible UIs — like `<select>`/`<option>` — instead of one component with a huge prop API. Radix UI and Headless UI use this pattern heavily."

> ⚠️ Gotcha #1: The older implementation used `React.Children.map` + `cloneElement` to inject props into children. It's fragile — it breaks when children are wrapped in another component or a fragment. **Context is the modern approach.**
>
> ⚠️ Gotcha #2: Guard the context with a custom hook that throws a helpful error (like `useModalContext` above), so using `Modal.Header` outside a `Modal` fails loudly instead of returning `null` silently.

## Part 3: Rules of Hooks Under the Hood

### 10. Why the Rules of Hooks Exist

**What it is:** Two rules:

1. Call hooks only at the **top level** — never inside loops, conditions, or nested functions.
2. Call hooks only from **React function components** or **custom hooks**.

(The `eslint-plugin-react-hooks` lint rule enforces both.)

**Why the rules exist:** React doesn't identify hooks by name — it identifies them by **the order they're called**. Internally, each component's hooks are stored as a **linked list on its fiber**, and on every render React walks that list in the same order, matching each `useState`/`useEffect` call to "the Nth hook." Position *is* identity. If a hook is skipped in one render, every hook after it slides into the wrong slot and reads someone else's state.

**Mental model:** A row of numbered lockers. Your first `useState` gets locker 1, the next hook gets locker 2, and so on. If one call vanishes on a later render, every call after it opens the wrong locker.

```jsx
function Form({ hasNickname }) {
  const [name, setName] = useState('');            // locker 1

  if (hasNickname) {
    const [nick, setNick] = useState('');          // locker 2 … but only sometimes!
  }

  const [email, setEmail] = useState('');          // locker 2 or 3, depending on the condition 💥
}
```

A toy version makes the idea concrete — this is a **simplified illustration**, not React's real implementation:

```js
let hooks = [];   // one component's hook slots
let index = 0;    // reset to 0 at the start of every render

function useState(initial) {
  const i = index++;                               // claim the next slot, by call order
  if (hooks[i] === undefined) hooks[i] = initial;
  const setState = (value) => { hooks[i] = value; rerender(); };
  return [hooks[i], setState];
}
```

Look at how it works: there are no names anywhere — only `index++`. That's the whole reason conditional hooks break it.

**Interview line:** "React tracks hooks by call order, not by name — each component's hooks live in a linked list on its fiber, matched up in the same order every render. Calling a hook conditionally shifts that order and mismatches state, which is why hooks must run unconditionally at the top level."

> ⚠️ Gotcha #1: **The fix isn't to skip hooks — it's to put the condition inside them:** `useEffect(() => { if (x) doThing(); }, [x])`. Or split the conditional part into its own component. An early `return` *before* a hook call also breaks the rules.
>
> ⚠️ Gotcha #2: React 19's `use()` (for reading promises and context) is the one API that **can** be called conditionally — but it isn't a regular hook, so don't generalize the exception.

## Part 4: Quick Reference & Drills

### 11. Smaller APIs Interviewers Mention

| API                                   | What it does                                                 | When it matters                                                                                |
| ------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| `useId`                             | Generates a unique ID that's stable across server and client | Linking`<label htmlFor>` and `aria-*` attributes. **Not** for list keys.             |
| `useSyncExternalStore`              | Safely subscribes a component to a store*outside* React    | What Redux and Zustand use under the hood; prevents "tearing" during concurrent rendering      |
| `flushSync`                         | Forces a synchronous, unbatched DOM update                   | Rare escape hatch — e.g., reading the DOM between two updates                                 |
| `React.Children` / `cloneElement` | Inspect/modify children                                      | Legacy compound-component approach; prefer Context                                             |
| `startTransition` (standalone)      | Marks an update as non-urgent, outside a component           | Same idea as`useTransition`, usable in libraries or event code                               |
| `useDebugValue`                     | Labels a custom hook's value in React DevTools               | Debugging custom hooks                                                                         |
| `<Fragment key={…}>`               | Fragment that can take a`key`                              | Lists where each item renders multiple sibling elements (the`<>` shorthand can't take a key) |
| `useInsertionEffect`                | Runs before DOM mutations                                    | CSS-in-JS library authors only                                                                 |

**Interview line:** "Beyond the main hooks, I know `useId` for stable accessibility IDs, `useSyncExternalStore` for subscribing to external stores safely — it's what Redux uses — and `flushSync` as a rare escape hatch from batching."

### 12. Practice: What Happens Here?

Predict first, then open the answer.

**Q1 — Error in an event handler**

```jsx
function BadButton() {
  return (
    <button onClick={() => { throw new Error('boom'); }}>Click</button>
  );
}

<ErrorBoundary fallback={<p>Something went wrong.</p>}>
  <BadButton />
</ErrorBoundary>
```

Click the button. Does the fallback appear?

<details>
<summary>Answer</summary>

**No.** Error boundaries only catch errors during **rendering** (and lifecycle methods/constructors). An error in an event handler happens *outside* the render phase — it's logged to the console and the UI stays as it was. Fix: wrap the handler body in `try/catch` and set an error state (which you *can* then render).

</details>

**Q2 — Error during render**

```jsx
function Broken() {
  throw new Error('render failed');
}

function App() {
  return (
    <>
      <h1>My App</h1>
      <ErrorBoundary fallback={<p>Widget failed.</p>}>
        <Broken />
      </ErrorBoundary>
      <Footer />
    </>
  );
}
```

What's on screen?

<details>
<summary>Answer</summary>

**The heading, "Widget failed.", and the footer.** The error is thrown during rendering *inside* the boundary, so the boundary catches it and swaps in the fallback. Everything outside the boundary is untouched.

</details>

**Q3 — Error in async code**

```jsx
function Loader() {
  useEffect(() => {
    fetch('/api').then(() => { throw new Error('async boom'); });
  }, []);
  return <p>loading…</p>;
}
```

Wrapped in an error boundary. Does the boundary catch it?

<details>
<summary>Answer</summary>

**No.** It's thrown inside a promise callback, *after* rendering finished — boundaries don't catch async errors. It becomes an unhandled promise rejection. Fix: `.catch()` (or `try/await/catch`) and store the error in state — and if you want a boundary to handle it, re-throw during the *next render* (e.g., `if (error) throw error;` in the component body).

</details>

**Q4 — Error inside the boundary itself**

Your `ErrorBoundary`'s `render` throws while displaying its fallback, and there's no other boundary above it. What happens?

<details>
<summary>Answer</summary>

**The error propagates up to the next boundary above — and if there is none, React unmounts the whole tree** (blank screen). A boundary can only catch errors from components *below* it, never its own.

</details>

**Q5 — Events through a portal**

```jsx
function Parent() {
  return (
    <div onClick={() => console.log('Parent clicked')}>
      {createPortal(<button>Click me</button>, document.body)}
    </div>
  );
}
```

The button is rendered into `document.body`, *outside* the `<div>` in the real DOM. Click it. What's logged?

<details>
<summary>Answer</summary>

**`Parent clicked`.** React events bubble through the **React component tree**, not the DOM tree. The portaled button is still a React child of that `<div>`, so its click bubbles up to the parent's `onClick`.

</details>

**Q6 — A ref on a plain function component**

```jsx
function MyInput(props) {
  return <input {...props} />;
}

function App() {
  const ref = useRef(null);
  useEffect(() => { console.log(ref.current); }, []);
  return <MyInput ref={ref} />;
}
```

What's logged in (a) React 18, and (b) React 19?

<details>
<summary>Answer</summary>

**(a) React 18: `null`,** plus a warning: "Function components cannot be given refs." `ref` isn't passed to function components as a prop, so it never reaches the `<input>`. Fix: wrap `MyInput` in `forwardRef`.

**(b) React 19: the `<input>` DOM element.** `ref` is now an ordinary prop, so `{...props}` forwards it straight onto the `<input>` — no `forwardRef` needed.

</details>
