## The Big Picture First (read this once, it ties everything together)

Here's the example we'll reuse throughout this file:

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  return (
    <div>
      <button onClick={() => setCount(count + 1)}>Increment</button>
      <p>Count: {count}</p>
      <Timestamp />
    </div>
  );
}

function Timestamp() {
  return <span>{new Date().toLocaleTimeString()}</span>;
}
```

When you click "Increment," here's the journey, at a glance — each step is its own topic below:

1. **A state setter is called** (`setCount`) → this is a *trigger* for a re-render (Part 3).
2. **React schedules the work**, deciding its priority relative to anything else pending (Part 2).
3. **Render phase:** React calls `Counter()` again (and `Timestamp()`, since it's Counter's child) to get a new virtual DOM tree (Part 1, #1, #4).
4. **Reconciliation / diffing:** React compares the new tree to the previous one, using Fiber's data structure, to figure out exactly what changed (Part 1, #2, #3, #6).
5. **Commit phase:** React applies *only* the changes it found to the real DOM (Part 1, #5).

Keep this five-step skeleton in mind — it's the spine every topic below hangs off of.

## Part 1: The Rendering Pipeline

### 1. Virtual DOM

**What it is:** A lightweight, in-memory JavaScript representation of the UI — a tree of plain objects describing what the DOM *should* look like, with none of the real DOM's overhead (layout, style computation, browser reflow).

**Why it exists:** Direct DOM manipulation is expensive — reads and writes can force the browser to recalculate layout. Keeping a cheap JS copy lets React figure out "what actually changed" entirely in memory first, and touch the real, costly DOM only for the minimum necessary updates.

**Mental model:** A blueprint copy you can scribble on and revise freely, before you ever send a crew to change anything in the actual building.

**Connect it to the example:** When `Counter` first renders, React doesn't touch the DOM at all yet — it builds a virtual tree describing `<div><button/><p>Count: 0</p><Timestamp/></div>`, which is just plain JS objects:

```js
// roughly what React holds in memory after the first render:
{
  type: 'div',
  props: {
    children: [
      { type: 'button', props: { children: 'Increment' } },
      { type: 'p', props: { children: 'Count: 0' } },
      { type: Timestamp, props: {} }
    ]
  }
}
```

**Interview line:** "The virtual DOM is React's in-memory, plain-object description of the UI — it exists so React can compute what changed cheaply in JS before touching the real, expensive DOM."

> ⚠️ Gotcha: "Virtual DOM is always faster than the real DOM" is an overstatement people repeat without understanding it. It's a trade-off — extra JS work (diffing) to minimize DOM work. For a handful of static elements, direct manual updates can actually beat it; the virtual DOM wins as complexity and update frequency grow.

---

### 2. Reconciliation

**What it is:** The algorithm React uses to compare the new virtual DOM tree against the previous one and figure out the minimal set of real DOM changes needed.

**Why it exists:** A fully general tree-diff is mathematically expensive (roughly O(n³) for arbitrary trees) — far too slow to run on every keystroke. React's reconciliation uses two heuristics to get this down to practical O(n): elements of different types are assumed to produce entirely different trees, and `key` gives an explicit identity hint for children within a list.

**Mental model:** A diff tool comparing two drafts of a document — instead of checking every possible way paragraphs could correspond (slow), it assumes paragraph N in the new draft lines up with paragraph N in the old one, and only flags genuine differences.

**Connect it to the example:** On click, `count` goes from `0` to `1`. React re-renders `Counter`, producing a *new* tree: `<div><button/><p>Count: 1</p><Timestamp/></div>`. Reconciliation walks both trees together: `div` → same type, keep it, recurse into children. `button` → same type, no prop change, reuse as-is. `p` → same type, but its text child differs ("Count: 0" vs "Count: 1") → flag that text node for an update. `Timestamp` → same type, so React keeps the same component instance rather than unmounting it — but since it's a child of a re-rendering parent, it gets called again too (more on exactly why in Part 3, #11).

**Interview line:** "Reconciliation is React's heuristic tree-diffing algorithm — it assumes same-position elements of the same type correspond to each other, which turns an otherwise impractical comparison into an O(n) one."

> ⚠️ Gotcha: Reconciliation is the *algorithm*; diffing (#6) and Fiber (#3) are how it's actually carried out in practice. Interviewers sometimes use these three terms almost interchangeably — knowing the distinction (heuristic vs. data structure vs. the specific comparison step) is what shows real depth.

---

### 3. React Fiber

**What it is:** React's internal architecture (since React 16) for doing reconciliation — instead of a plain recursive tree walk, each unit of work (roughly, one component) is represented as a "fiber" object linked to its child, sibling, and parent, forming a structure React can pause, resume, reprioritize, or abandon partway through.

**Why it exists:** The pre-Fiber reconciler (React ≤15) walked the tree recursively and synchronously — once started, it couldn't stop until the whole tree was processed, which could block the main thread long enough to make typing or animations feel janky on large trees. Fiber restructures rendering into small, interruptible units of work so React can yield back to the browser mid-render if something more urgent comes up.

**Mental model:** The old reconciler is reading an entire book in one uninterruptible sitting. Fiber is reading it one chapter at a time with a bookmark — you can put it down for something urgent and resume exactly where you left off, instead of starting over or blocking everything else.

**Connect it to the example:** When you click Increment, React creates a fiber representing "re-render `Counter` with `count=1`." It processes `Counter`'s fiber, then moves to `button`, `p`, and `Timestamp`'s fibers one at a time via child/sibling pointers — rather than one unbroken recursive call stack. On a `createRoot` (concurrent-capable) root, React could in principle pause between those fibers if something more urgent (like a keystroke elsewhere) came in.

**Interview line:** "Fiber is the incremental, interruptible unit-of-work architecture underlying reconciliation since React 16 — it's what makes rendering pausable and resumable instead of one uninterruptible recursive pass."

> ⚠️ Gotcha: Fiber existing doesn't mean every render is actually interrupted — under legacy rendering, work still typically runs synchronously start to finish. Fiber is the architecture that *makes* interruption possible; concurrent features (Part 2, #10) are what actually *use* that capability.

---

### 4. Render Phase

**What it is:** The phase where React calls your component functions to figure out what the UI should look like now — this is where Fiber's work happens and reconciliation/diffing run, producing a new "work-in-progress" fiber tree. It has zero visible effect on the DOM, and in concurrent mode it's the phase that can be paused, aborted, or restarted.

**Why it exists:** Separating "figure out what changed" from "apply it" is what lets the figuring-out part be interruptible and redoable — since a render might get thrown away entirely (e.g., superseded by a newer update), it must never do anything irreversible, like touching the DOM.

**Mental model:** Drafting a plan on a whiteboard — you can erase and redo it freely, because nothing physical has happened in the real world yet.

**Connect it to the example:** Clicking Increment triggers the render phase: React calls `Counter()` again with `count=1`, gets back a new element tree, diffs it against the previous fiber tree, and marks the nodes that actually need DOM changes (here, just the `<p>` text) with an internal "effect" tag. No real DOM has been touched at this point.

**Interview line:** "The render phase is where component functions run and reconciliation happens — it's pure computation with no DOM side effects, which is exactly what allows it to be paused or thrown away in concurrent rendering."

> ⚠️ Gotcha: Because render-phase functions can be paused, restarted, or (rarely) called more than once per update under concurrent rendering, your component body — and anything called directly during render — must stay free of side effects. No direct DOM mutation, no mutating variables outside the component, during render itself.

---

### 5. Commit Phase

**What it is:** The phase after render where React actually applies the computed changes to the real DOM — inserting, updating, or removing nodes, attaching refs, running `useLayoutEffect` synchronously, and afterward running `useEffect` asynchronously. Unlike the render phase, commit is synchronous and cannot be paused partway through.

**Why it exists:** Once DOM changes start being applied, stopping halfway would leave the user staring at a visibly broken, half-updated screen. Splitting "figure out what changed" (interruptible) from "make it real" (must run to completion once started) is what lets React be smart about the first part without ever risking an inconsistent screen from the second.

**Mental model:** Actual construction based on a finalized blueprint — once the crew starts building, you don't pause halfway to rethink the plan; you finish the job in one uninterrupted pass.

**Connect it to the example:** Render phase found that the `<p>` text changed from "Count: 0" to "Count: 1" (and that `Timestamp`'s `<span>` text also changed, since the clock moved). Commit phase updates exactly those two text nodes in the real DOM — the surrounding `div` and `button` DOM nodes are never touched, because diffing never flagged them.

**Interview line:** "The commit phase is where React synchronously and atomically applies the DOM mutations computed during render — refs get attached, layout effects run synchronously before the browser paints, and `useEffect` runs afterward, asynchronously."

> ⚠️ Gotcha: `useLayoutEffect` runs synchronously as part of commit, before the browser paints — that's exactly why it's used for DOM measurement/adjustment tasks. `useEffect` runs after paint, asynchronously, which makes it unsuitable for anything the user must never see flash into an intermediate state first.

---

### 6. Diffing

**What it is:** The specific comparison step, run during the render phase, that compares the new element tree to the previous fiber tree node by node to decide what's unchanged, what's updated, what's new, and what's removed.

**Why it exists:** As in reconciliation (#2), a naive full tree comparison is too slow to run on every update. Diffing applies the same two heuristics concretely: compare by element type first (a type mismatch at a position discards and rebuilds that whole subtree), then, within a list, match by `key` instead of position.

**Mental model:** Proofreading two drafts side by side, paragraph by aligned paragraph, marking only the lines that actually changed in red — those red marks are the *only* work commit has to do.

**Connect it to the example:** On Increment: `<p>` stays a `<p>` at the same position → diff its children → the text differs → mark just that text for an update. `<button>` stays a `<button>`, no prop changed → nothing marked. If `Counter` instead conditionally rendered `<p>` sometimes and `<h1>` other times for the count, diffing would see a *type* mismatch at that position and discard + rebuild that entire subtree from scratch, rather than patching it in place.

**Interview line:** "Diffing is React's heuristic tree comparison — same type at the same position gets patched in place, a different type gets torn down and rebuilt, and it's specifically designed to stay close to O(n) instead of the impractical cost of a general tree diff."

> ⚠️ Gotcha: Swapping an element's *type* at a given position — say, conditionally rendering `<input>` vs. a custom `<StyledInput>` — discards all of that subtree's local state and unmounts/remounts it, even if the two look visually identical. This surprises people who expect state to "just carry over."

---

### 7. Keys

**What it is:** A special string prop React's diffing algorithm uses, specifically for lists, to match children in the new tree to children in the old tree by *identity* rather than by *position*. React reads it internally; your component never receives `key` as a normal prop.

**Why it exists:** Diffing's default assumption is "the child at index N corresponds to the child that was at index N before." That assumption breaks the moment a list is reordered, or an item is inserted/removed anywhere but the end — without an explicit identity hint, React would misattribute existing DOM nodes (and their local state) to the wrong logical item.

**Mental model:** A luggage claim tag, not a slot number — it lets you match each bag to its correct owner no matter how the conveyor belt shuffled the order, instead of assuming whoever's standing at position 3 owns the bag currently at position 3.

**Connect it to the example:** Given `<ul>{items.map(i => <li key={i.id}>{i.text}</li>)}</ul>`, deleting the first item lets diffing recognize every *remaining* item by its own stable `id` — it removes exactly one `<li>` DOM node and leaves the rest untouched. With `key={index}` instead, deleting the first item shifts every subsequent item's index down by one, so React believes item 1 "became" item 0 and patches props onto what should have been a stable, untouched node — a common source of state landing on the wrong row (e.g., an "expanded" toggle sticking to the wrong item).

**Interview line:** "Keys are the seam in React's diffing heuristic — they swap 'match by position' for 'match by identity' within a list, so reorders, insertions, and deletions patch the DOM precisely instead of cascading unnecessary patches through every sibling after the change."

> ⚠️ Gotcha: Index-based keys are fine for static lists that never reorder — the moment items can be added, removed, or reordered anywhere but the very end, they risk state attaching to the wrong row.

## Part 2: Scheduling & Concurrent Rendering

### 8. State Batching

**What it is:** React grouping multiple state updates that happen within the same "tick" of work into a single re-render, rather than re-rendering once per individual `setState` call.

**Why it exists:** Without batching, calling two setters in the same click handler would trigger two separate render+commit cycles — wasted work, and worse, it could briefly show the user a "half-updated" intermediate frame between the two commits.

**Mental model:** A waiter who collects your entire order before making one trip to the kitchen, instead of running back and forth after every single item you mention.

**Connect it to the example:** Suppose `Counter` also tracked `doubled`, and the click handler did `setCount(count + 1); setDoubled((count + 1) * 2);`. Even though that's two setter calls, React batches them into a single re-render where both new values apply together — not two separate render/commit cycles, and never a frame where `count` is updated but `doubled` isn't yet.

React 17 vs. 18: before React 18, this automatic batching only happened *inside* React event handlers — a `setState` inside a `setTimeout`, a promise `.then`, or a native (non-React) event listener triggered its own separate render each time. React 18's `createRoot` made batching automatic virtually everywhere, closing that gap.

**Interview line:** "Batching groups multiple state updates within the same unit of work into a single re-render — since React 18, that happens automatically almost everywhere, not just inside React event handlers the way it did pre-18."

> ⚠️ Gotcha: `flushSync` exists as an explicit escape hatch to force an update to apply synchronously and unbatched — useful in the rare case where a DOM read genuinely needs to happen between two specific state updates, but it's the exception, not something to reach for by default.

---

### 9. Scheduling

**What it is:** React's internal mechanism (its Scheduler) for assigning priority to pending units of work and deciding in what order to process them — so more urgent updates can jump ahead of less urgent ones instead of everything running strictly in arrival order.

**Why it exists:** Not all updates are equally urgent. A user typing into an input needs to feel instant; a big, unrelated re-render triggered elsewhere can wait a few milliseconds without anyone noticing. Without prioritization, React would process every update strictly in the order it was requested, which could make an urgent interaction feel laggy behind unrelated heavy work that happened to be queued first.

**Mental model:** An ER triage nurse, not a first-come-first-served line — a broken arm waits while a heart attack that just walked in gets seen immediately, regardless of arrival order.

**Connect it to the example:** Imagine clicking Increment also kicks off a heavy re-render of an unrelated 10,000-row list elsewhere on the page. Scheduling lets React start that heavy work, but if you then type into a search box, React can pause the low-priority list work, handle the keystroke immediately (high priority), and resume the list rendering afterward — instead of making the keystroke wait behind the whole list.

**Interview line:** "React's scheduler assigns priority to units of work so urgent interactions like typing or clicking can interrupt and jump ahead of lower-priority background rendering — it's the piece that makes concurrent rendering actually feel responsive."

> ⚠️ Gotcha: Priority changes *when* work runs, not *whether* it runs — a low-priority update still eventually completes; it just might get paused and resumed instead of blocking the main thread for its entire duration.

---

### 10. Concurrent Rendering Basics

**What it is:** A set of opt-in capabilities (`createRoot`, `useTransition`, `useDeferredValue`) that let React prepare a render without committing to it, interrupt an in-progress render for something more urgent, and let you explicitly mark some updates as low-priority so urgent ones stay responsive.

**Why it exists:** Before these features, an expensive render (say, typing that re-filters a huge list on every keystroke) would block the main thread until fully done, making the input itself feel janky. Concurrent rendering lets React treat that expensive re-render as interruptible and lower priority, while keeping the input's own update instant.

**Mental model:** Cooking two dishes at once with the ability to pause the slow-simmering one to plate the fast dish the moment a customer needs it — non-concurrent React can only cook one dish start to finish before touching the next, no matter how urgent the second one is.

**Connect it to the example:**

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  const [isPending, startTransition] = useTransition();

  const increment = () => {
    startTransition(() => {
      setCount(c => c + 1); // marked low-priority — interruptible
    });
  };

  return <button onClick={increment} disabled={isPending}>{count}</button>;
}
```

If Increment were clicked rapidly here, React could drop an in-progress low-priority render for an older click and start fresh from the latest one, instead of dutifully rendering every intermediate value in order.

**Interview line:** "Concurrent rendering means React can prepare a render without committing to it, interrupt it for something more urgent, or have you explicitly mark work as low-priority via `useTransition`/`useDeferredValue` — Fiber's interruptible architecture is what makes any of this possible at all."

> ⚠️ Gotcha: Concurrent features are opt-in on top of `createRoot` (React 18+) — a plain `setState` call still defaults to being treated as urgent. You have to explicitly wrap a non-urgent update in `startTransition` (or use `useDeferredValue`) to get the interruptible, lower-priority behavior for it.

## Part 3: Re-renders in Practice

### 11. Why Components Re-render

**What it is:** A component re-renders — its function is called again — for one of a small, fixed set of reasons: its own state changed, its parent re-rendered (so it re-renders too, by default, regardless of its own props), or a context value it subscribes to changed.

**Why it matters:** "My component re-renders too often" is the most common real-world React performance question there is — interviewers ask this specifically because knowing the actual short list of causes is what lets you diagnose a problem instead of guessing at it.

**Mental model:** A component agrees to redraw itself only when one of a short, fixed list of "wake-up calls" fires — never on a timer, never just because time passed, never because something unrelated elsewhere in the app changed.

**Connect it to the example:** Back to `Counter`/`Timestamp` — clicking Increment causes `Counter` to re-render because *its own state* (`count`) changed. `Timestamp` re-renders too, even though it has no state and no props of its own — purely because *its parent re-rendered*. That's the "parent re-renders → child re-renders by default" rule you saw play out in Part 1's reconciliation walkthrough (#2).

**Interview line:** "A component re-renders for one of a few specific reasons — its own state changed, its parent re-rendered, or a subscribed context value changed — never just because time passed or something unrelated changed."

> ⚠️ Gotcha: This is exactly why `Timestamp` shows a new time on every single Counter click, even though nothing about the click has anything to do with it — it's collateral re-rendering inherited from its parent, not its own logic deciding to update.

---

### 12. What Triggers Re-render

**What it is, concretely:**

- Calling a state setter with a value that's genuinely different (via `Object.is`) from the current state. If you call `setCount(count)` with the *exact same* primitive value, React compares it, sees no change, and skips re-rendering that component and its children.
- The nearest parent re-rendering — this cascades downward by default, regardless of the child's own props or state.
- A subscribed context value changing (`useContext`) — this can trigger a re-render even for a component deep in the tree that isn't a direct child of the provider, which is exactly why context is useful for skipping prop drilling.

**Mental model:** This is the "wake-up call list" from #11, spelled out as an actual checklist you can run through when debugging an unexpected re-render.

**Connect it to the example:**

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(0)}>{count}</button>; // always sets to 0
}
```

Clicking this button when `count` is already `0` does **not** cause a re-render — React compares the new value (`0`) to the current state (`0`) via `Object.is`, finds no difference, and bails out. This exact pattern is a classic interview trick question.

**Interview line:** "State setters, parent re-renders, and changing context values are the three real triggers — and even a state setter call is skipped if `Object.is` says the new value equals the old one."

> ⚠️ Gotcha: That bail-out is reference/primitive equality, not deep equality — calling `setUser({...user})` with contents identical to the current `user` still triggers a re-render, because `Object.is` compares the object reference, and spreading always creates a new one.

---

### 13. How React Decides What to Update

**What it is:** Once a re-render is triggered (#11–#12) and the render phase (#4) produces a new element tree, "what to actually update" is decided by reconciliation and diffing (#2, #6) comparing that new tree against the previously committed fiber tree — only the nodes flagged as different get touched at all, and only in the commit phase (#5).

**Why it matters:** This is the entire reason React can afford to re-run your whole component function on every trigger. Calling a function again is cheap and can happen often; mutating the DOM is comparatively expensive and should happen as rarely as possible — diffing is the bridge that keeps the expensive part minimal no matter how often the cheap part runs.

**Mental model:** The proofreading-two-drafts picture from #6, one more time — the red marks from that comparison are the *only* physical construction work commit ever has to do.

**Connect it to the example — the full trace, start to finish:**

1. Click → `setCount(count + 1)` fires — a state-setter trigger (#12) → React schedules the update, weighing it against anything else pending (#9).
2. **Render phase** (#4) calls `Counter()` again, producing a new element tree with `count: 1`. `Timestamp` is called again too, purely because it's a child of a re-rendering parent (#11).
3. **Reconciliation / diffing** (#2, #6) compares this new tree to the fiber tree from the previous commit, node by node: `div` and `button` unchanged → left alone; `p`'s text child differs → flagged; `Timestamp`'s `span` text differs (a new timestamp) → flagged.
4. **Commit phase** (#5) applies exactly those two flagged text updates to the real DOM. The `div` and `button` DOM nodes are never touched at all.

**Interview line:** "React decides what to update by diffing the newly rendered element tree against the previously committed one, flagging only the nodes that actually differ — commit then applies just those flagged changes, which is why a component re-rendering doesn't mean its whole DOM subtree gets rebuilt."

> ⚠️ Gotcha: "Re-rendered" (the function was called) and "DOM updated" (something actually changed on screen) are different events. A component can re-render every single time its parent does while its output stays byte-for-byte identical — after diffing finds zero differences, commit does zero real DOM work for it.
